# RepWorth Domain Glossary (seed)

- **Review source**: a provider adapter (Zernio today) that ingests reviews and normalizes them to the `NormalizedReview` DTO; no source-specific fields leak past it. *(draft — to be sharpened in grilling sessions)*
- **Response / draft**: the LLM-generated reply to a review; it is only a draft until an approval method is recorded. *(draft — to be sharpened in grilling sessions)*
- **Approval method**: how a response earned the right to be posted — `owner` (explicit owner action) or `auto_policy` (server-only gated runtime, disabled by default). *(draft — to be sharpened in grilling sessions)*
- **Moderation hold**: a `high`-severity moderation flag writes a `flagged_responses` row (status `open`) and suppresses owner notification. A draft is **held** while its flag is `open`; the single read-side spelling of that predicate is `openFlagExistsSql` (`src/lib/moderation/held-draft.ts`, #730 — its header also inventories the deliberately distinct consumers that do NOT consolidate onto it). Any disposition off `open` (admin `approved_for_owner_review`, `dismissed_false_positive`, `requires_regeneration`) closes held-ness; only `approved_for_owner_review` additionally re-notifies the owner. *(draft — sharpened at #730 review; was: "only admin approval releases it", which conflated flag-release with re-notification)*
- **Account**: the billing parent (subscription, quotas, stored tier prices). **Business**: one Google Business Profile location under an account. *(draft — to be sharpened in grilling sessions)*
- **Outbox job**: follow-up work recorded in `job_outbox` in the same transaction as the state change; OutboxPoller dispatches it to BullMQ. *(draft — to be sharpened in grilling sessions)*
- **Full access**: subscription statuses (`active`, `trialing`) that `subscriptionGrantsFullAccess` treats as entitled; workers gate on it, never on a raw status literal. *(draft — to be sharpened in grilling sessions)*
- **Poller cadence**: a background loop's tick interval — owned by the code default (`DEFAULT_INTERVAL_MS`), overridable per-env via its `*_INTERVAL_MS` env var. Changing cost posture means changing the code default (rides PR + staging); the env var is a per-env operational override, never the authoritative value. *(coined in the cost-optimization wayfinder effort)*
- **Watchdog**: the recovery queries inside a dispatch poller (OutboxPoller's recover/terminate/stale-dispatching UPDATEs, AnalyticsDispatchPoller's stale-reclaim) that reclaim rows orphaned by crashes — distinct from dispatch itself, and allowed to run on a slower cadence than dispatch. Its terminate arm writes `last_error = 'Stale dispatched entry exceeded max_attempts'` (`OutboxPoller.ts:140-143`) **unconditionally**, overwriting whatever was there: that text describes the **reclaim**, never the handler failure underneath it. Reading it as a diagnosis is what let #719 hide for three months — the diagnosis lives in Sentry, via the **Job-failure sink**. *(coined in the cost-optimization wayfinder effort; sharpened in #719)*
- **Drip staleness cap**: the 3-day bound owned by `DRIP_STALENESS_GRACE_DAYS` / `isDripTooStale` in `OnboardingDripWorker` — a drip whose due date passed by more than the grace window is never sent, permanently. It exists so an outage that pauses drips does not clear into a burst of late "Welcome to day 1!" emails. Sends **at** the boundary (the comparison is strictly `<`, so equality is not stale), skips past it. Enforced at **two points, and both are load-bearing**: the `OnboardingDripScheduler` producer excludes stale pairs from the candidate query, and a **fail-closed chokepoint** in `handleOnboardingDrip` re-checks before any side effect. Producer-only was the original design and was wrong — an operator re-driving a failed row, a future second producer, or a row minted just inside the boundary and stranded through a multi-day worker outage all reach the handler with the producer's check long expired; #679 reached the same conclusion for **Import consent** and for the same reason. The chokepoint runs **before** the `onboarding_drip_log` claim (a refusal must not consume the claim a legitimate re-send would need) and **completes** the row carrying `completion_reason = 'drip_too_stale'` rather than failing it — a policy refusal is the guard working, not an incident, and the marker makes a refusal separable in SQL from a genuine send. Unlike #679's guard it needs no `SELECT … FOR UPDATE`: staleness is a pure function of `subscription_activated_at` and the clock, and nothing mutates the anchor, so there is no race to serialize against. Both enforcement points leave a **durable record** since #738: the handler chokepoint completes its outbox row with `completion_reason = 'drip_too_stale'` (7-day window under ArchivalPoller's completed-row retention), and the scheduler stamps `skipped_at`/`skip_reason` on `onboarding_drip_log` (migration 104) — a table ArchivalPoller never touches, so the scheduler's record is the **permanent** answer to "which drips were dropped as too-late, and when". The stamp doubles as the candidate-query dedup, replacing the old `GRACE + 1` one-day reporting window: a too-late pair — including a backlog already past the window at deploy, which the old window skipped silently — is selected once, recorded (a guarded `ON CONFLICT … DO UPDATE` stamps a dead claim row; a sent or already-skipped row is untouched, and migration 104's CHECK makes skip-and-send unrepresentable), and excluded thereafter. Removing the outer window is re-mint-safe because archival (7 days) strictly exceeds grace (3 days): any pair archival frees re-enters the query already too late, landing in the skip branch, never the queue branch — that arithmetic is load-bearing; do not shrink outbox archival below the grace window. `skip_reason` vocabulary: `DRIP_SKIP_REASONS` in `OnboardingDripWorker.ts`, derived from `OUTBOX_COMPLETION_REASON.DRIP_TOO_STALE` so one grep finds both enforcement points. *(coined in #719; producer-only enforcement corrected at #719 step-7 review A1; observability asymmetry accepted at review A3, then closed by #738/migration 104)*
- **Job-failure sink**: `worker/job-failure-sink.ts`, attached to every BullMQ `Worker` alongside `attachEmitterErrorLogger` — on the **terminal** attempt only it raises a Sentry issue (tags `{subsystem, queue, topic}`) rather than the breadcrumb that preceded it. Its terminal test is the **`'failed'`-event** predicate `attemptsMade >= max`, deliberately NOT `isTerminalAttempt` from `src/lib/shared/outbox.ts`: that one is `attemptsMade >= max || attemptsMade + 1 >= max`, written for the **catch block** where `attemptsMade` has not yet been incremented, and using it in the event context fired one attempt early *and* again on the real last one — a duplicate issue plus a false "exhausted its retries" for a job BullMQ then retried successfully. `worker/jobs/judge/failed-hook.ts` keeps its own copy for the same reason and says "do not unify them"; treat any future shared helper here as a trap. It writes **nothing** to `job_outbox`: the **Watchdog** overwrites `last_error` unconditionally when it terminalizes, and a raw driver message can embed contact PII, so durable per-domain error text stays the job of the six domain `'failed'` hooks — Sentry is the durable record of the *handler error* specifically, not of every failure fact. Promoting these from breadcrumbs to issues moved the message onto the one Sentry field `scrubSentryEvent` did not cover, so that scrubber now redacts `exception.values` too. *(coined in #719; terminal predicate and exception scrubbing corrected at #719 step-7 review A2/A6)*
- **Connection wedge** (the "wedge"): a postgres.js pool connection stalled server-side in `state=active, wait_event=ClientRead` — a socket-level stall waiting for client bytes that never arrive. No server-side timeout heals it, and `withTimeout` does not cancel the underlying work, so the leaked slot never returns to the pool; one wedge per cycle → full-pool starvation. *(coined in the #500 pool-wedge self-heal)*
- **Boot burst**: the ~24 background-loop first cycles + ~30 BullMQ `Worker`s + ~31 `Queue`s all initializing on roughly the same tick at worker start — the leading (still UNPROVEN) candidate for triggering the connection wedge. *(coined in the #500 pool-wedge self-heal; sharpened in the #505 root-cause investigation)*
- **Boot-readiness cure**: the #505 boot-storm hardening in `worker/background/boot-stagger.ts` — BullMQ Workers build `autorun:false`; boot awaits bounded, fail-open Redis/BullMQ readiness (`awaitQueueReadiness`); then the ~24 DB-backed loops' first cycles start on a bounded (~8s), strictly-monotonic, jittered stagger (`computeBootSchedule` + `staggerBoot`); only THEN are the deferred Workers resumed. One `AbortSignal` spans the whole sequence — shutdown aborts it FIRST, before stopping loops, so a SIGTERM mid-boot cancels any pending continuation instead of racing the teardown. Toggle `BOOT_STAGGER_ENABLED` (default ON; only the literal `"false"` disables, for the T1 repro harness baseline). Validated EMPIRICALLY (zero wedge across repeated fresh treatment boots), not a proven-mechanism fix — see ADR 0008. *(coined in the #505 boot-readiness cure)*

- **Coupled terminal transition**: multi-write terminal bookkeeping (outbox close + exception/notify rows) executed atomically inside one `sql.begin` with the `markOutboxFailed` ownership CAS run FIRST — CAS `false` means a stale attempt that must write nothing; a mid-tx crash rolls everything back and leaves the row `dispatched` for the watchdog. Owned by `withOwnedTerminalTransition` (`worker/jobs/zernio/ingest-failed-hook.ts`); the crash guard never splits a coupled tx. *(coined in the #508 reliability guards)*
- **Per-widget degradation**: the dashboard failure contract — an auxiliary query failure degrades ONLY its widget to an empty-but-valid shape via `widgetOrFallbackFor(source)` and MUST report through `reportCaughtError` (degradation is never silent); only identity anchors (business lookup, aggregate locations list + baseline anchor) stay fatal. *(coined in the #508 reliability guards)*
- **Count-and-suppress window**: the per-source emitter-error throttle (`worker/emitter-errors.ts`) — first error in each 60s window is logged + Sentry-captured, the rest are counted and surfaced as `suppressed_in_prior_window` when the next window opens; prevents reconnect-loop alert storms while keeping every listener non-fatal. *(coined in the #508 reliability guards)*
- **Bounded admin client**: `supabaseServerBounded` (10s `boundedSupabaseFetch`) for worker-side admin/storage calls that must never hang a BullMQ slot — deliberately split from the unbounded `supabaseServer` used by Auth identity mutations, where an ambiguous timeout could orphan a committed signUp/invite. *(coined in the #508 adversarial review)*

- **Deployment lane** (the "lane") — which of the three environments a running process is in, in CLAUDE.md's existing "Three lanes" sense (*preview* / *staging* / *production*). Resolved by the single authoritative owner `src/lib/config/deployment-lane.ts` from `RAILWAY_ENVIRONMENT_NAME` (the Railway-injected system variable — wins whenever present), falling back to `NODE_ENV`, then `'development'`. **A lane is not `NODE_ENV`**: staging runs with `NODE_ENV=production` and production leaves `NODE_ENV` unset, so `NODE_ENV` cannot name the lane (#610/#611). It is also **not a feature flag** — it reports where the process runs and never gates a product behaviour, which is why it lives outside `src/lib/config/flags.ts`. The separate `requiresProductionConfig()` answers "must this process satisfy production-grade config?" and is deliberately the *union* of the two signals, never their precedence. *(coined in the #610/#611 deployment-lane fix; ADR 0013)*

- **Owner-unreachable outcome** — the notification result when an approval draft's account/location has zero verified channel enrollments at send time (`no_verified_enrollments`), recorded as `job_outbox.completion_reason='owner_unreachable'` on the completed `send_notification` row, and *current* only while that is the **latest** completed `send_notification` for the response. Distinct from **all-failed** (a delivery was attempted on an enrolled channel and every attempt failed) and **stale** (delivered but the owner hasn't acted). The draft stays `pending_approval` and is retried on the `NotificationFailoverPoller` cadence until a channel appears. *(coined in the F1 owner-unreachable escalation effort)*

- **Review import**: the consented, one-time storage of an owner's newest 100 Google reviews as inventory — it stores reviews and writes **no** replies (design D2). Entry point `importReview` (`src/lib/reviews/process-review.ts`), distinct from `processReview`'s live-ingest lane which drafts a reply for every new review. Insert-only: an existing review row is never mutated by an import, so a bulk import cannot supersede a response, open a `review_exceptions` row, or notify admin on behalf of the live lane; both "row already existed" and "lost the insert race" return `'unchanged'` with zero writes. It enqueues no `job_outbox` row at all, so nothing it stores can reach Google (invariant #3), and it completes its own run spine in the insert transaction because no downstream worker ever would. The mechanism keeps its existing names (`zernio_initial_backfill` topic, `zernio_backfill_runs` table, `origin_lane='backfill'`) — only the semantics changed. _Avoid_: backfill (the user-facing noun is **import**), historical sync, review sync. *(coined in #674; map #667, spec `docs/superpowers/specs/2026-08-05-consented-review-import-design.md` §6.2)*
- **Import consent**: the per-location decision record for the Review import offer — `import_decision` (`pending` | `accepted` | `declined`), `import_decision_at`, `import_offer_expires_at`, columns on `businesses` (migration 100, #673). **Expiry is derived, never stored** (#670): "expired" = `pending AND import_offer_expires_at <= now()`, computed on read by one predicate helper — no poller, no `expired` enum value, and nothing fires at the expiry moment. The single owner of the predicate and of every write is `src/lib/reviews/import-consent.ts` (#677): `importConsentStateSql` composes the derivation into a larger query (**callers must alias `businesses` as `b`**), `readImportConsent` returns the row, `createImportOffer` stamps the deadline at the junction, and `recordImportDecisionAndEnqueue` owns the acceptance transaction. Enforcement today is **at the four product enqueue paths** (#677) — connect finalize, the Stripe activation resume, reactivation catch-up, and the owner's decision route — each gating on `accepted` while holding the `businesses` row lock. The **fail-closed worker guard shipped at #679** (PR #698): `guardImportConsent` (`worker/jobs/zernio/job-eligibility.ts`) runs in `ZernioBackfillWorker` before `guardZernioJobEligibility` and before the run-row INSERT, and proceeds only on `accepted` — so declined, derived-expired, pending and a missing `businesses` row, including hand-inserted rows i.e. the admin path, all no-op-complete with a logged `reason`. Since #695 a refused row is also **marked for the archival window** — `job_outbox.completion_reason = 'import_consent_blocked'` (the `OUTBOX_COMPLETION_REASON` vocabulary, column from migration 083) — so a policy refusal is separable by SQL from a genuine completed import, which before was only inferable from the log line plus the absence of a `zernio_backfill_runs` row. **It is an operational-window signal, NOT an audit record**: `ArchivalPoller` deletes completed `job_outbox` rows 7 days after `completed_at`, and a refusal completes rather than fails, so it takes the 7-day arm — the same life `owner_unreachable` has always had (ADR 0010), a property of the sink rather than of #695. What outlives the window is `import_decision` / `import_decision_at` on `businesses`, plus the log line under the log sink's own retention. ONE marker for all four refusal states: it records THAT a refusal happened, and the state that caused it lives only in the log line — a later read of `businesses` can disagree (a `pending` refusal the owner then accepts) or find nothing (the `missing` case). Nothing reads it in code: no poller, no alert, no admin surface — a refusal is the guard working. No backfill, so a NULL on a row predating #695 is not evidence of a genuine import. The `job_outbox`-boundary alternative was weighed and declined at #695 (ADR 0016, `docs/adr/0016-import-consent-enforcement-locus.md`). D8's "admin path included" now holds at the one chokepoint every enqueue path shares. It is deliberately a SEPARATE function, not a `jobKind` branch: a merged guard would have two callers, one of which must never reach consent code, so splitting makes live-ingest independence structural rather than a runtime branch. Its whole body runs inside `sql.begin` with `SELECT … FOR UPDATE` + `markOutboxCompletedWithReason(tx, …)`, and both halves are load-bearing — without them the guard can read `pending` while the owner accepts, the acceptance's in-flight dedup inserts no replacement, and the guard completes the row: `accepted` with no completed run and no runnable outbox row, i.e. silent permanent loss for a customer who said yes. Accepted-but-never-completed stays retryable via the `completed_at IS NULL` sentinel (spec §5.1). Distinct from the solicitation **Consent attestation** / **Consent ledger** below — different domain, different tables, no shared machinery. _Avoid_: bare "consent" (ambiguous with solicitation), backfill consent. *(coined in #670; spec §5.3; worker-guard wording corrected from built to pending at #677 — round-1 cited-artifact check — then to shipped at #679, PR #698; durable block reason + enforcement-locus ADR at #695)*
- **Import offer**: the one-time, per-location invitation to run the Review import, created **server-side at the subscribe+connect junction** — activation non-NULL **and** an active `zernio_connections` row, both proven inside `createImportOffer`'s own SQL rather than trusted from callers. Its deadline is `now() + 7 days` **at creation**; there is no junction anchor (owner adjudication 2026-08-06 — anchoring was self-invented, produced two High findings across two review rounds, and was deleted). An offer is **answerable only while it exists and is live**: the guarded transition requires `import_decision = 'pending' AND import_offer_expires_at IS NOT NULL AND > now()`, so migration 100's default `pending` + NULL deadline is deliberately NOT an offer — that `IS NOT NULL` is what stops a direct POST manufacturing consent for a location nothing was ever offered for. Answering is terminal and first-write-wins; a self-healed offer (repaired by the dashboard GET when the junction-time write failed) starts a fresh 7 days at the repair, which is more generous and is the point. Surfaced by `ImportOfferBanner` through `GET/POST /api/dashboard/import-offer`, never from the Redis-cached dashboard payload. **Inheritance on re-add copies a decision, and a deadline only when that deadline is already in the past** (#677 D12): re-adding a location whose archived row `declined` or let the offer expire does not re-offer the import — the past deadline is copied so the new row still derives expired — but a **live** deadline is left NULL, so the new row earns a fresh offer at its OWN junction. Copying a live deadline would present an answerable offer for a location with no active connection, bypassing the very junction proof `createImportOffer` exists to enforce. Distinct from **Import consent**, which is the stored decision record this offer collects. _Avoid_: import prompt, backfill offer, "the banner" (that is the surface, not the offer). *(coined in #677; spec `docs/superpowers/specs/2026-08-05-consented-review-import-design.md` §3, §5.3)*
- **Import window**: the set of reviews the consented Review import may select from — `createTime` within `[now − 12 months, live-ingest cutoff)`. The 100 is a ceiling inside this window, the 12-month floor a hard stop; whichever binds first wins (spec D3/D4). The upper bound makes lane ownership **disjoint by construction**: everything at or above the cutoff belongs to the live lane (webhook + recent poller), everything below it to the import — so a review stored by `importReview` can never be one the live lane owed a draft for (the #674 lost-draft hazard, resolved structurally at #675). When a location has no `connected_at`, the poller owns nothing and the import applies no upper bound — complementarity is preserved at both ends. Selection is owned by the pure `selectImportWindow` (`worker/jobs/zernio/ZernioBackfillWorker.ts`). _Avoid_: fetch window, backfill window, gap/historical (dead vocabulary). *(coined in #675 grilling)*
- **Live-ingest cutoff**: `connected_at − ZERNIO_RECENT_REVIEW_CONNECT_GRACE_MS` (default 5 min) for a location's active `zernio_connections` row — the instant from which the live lane owns review handling. One owner: `liveIngestCutoff` (`worker/jobs/zernio/zernio-ingest-shared.ts`), consumed by the recent poller (`isRecentForConnection`, ≥ cutoff) and the Review import (Import window upper bound, < cutoff). Null `connected_at` → null cutoff; each lane interprets null per its own fail direction (poller: owns nothing; import: no upper bound). _Avoid_: recency cutoff, connect grace (that names the env var, not the boundary). *(coined in #675 grilling)*
- **Reviews list**: the owner's single inventory of every review for a location — the surface the consented Review import lands on. It is **not a new page**: `dashboard/reviews/history` (the former Past Replies archive) is widened in place to include never-replied reviews and becomes it (#671, 2026-08-08; spec §6.3a S1). Grouped `Unanswered` then `Answered` per D6, newest-first inside each group, `PAGE_SIZE` 50. Distinct from the **Needs Action** queue at `dashboard/reviews`, which survives unchanged and answers a different question: that surface filters to `pending_approval` + live auto-post veto windows off the Redis-cached dashboard payload (`ReviewFeedCard.tsx:59-66`, `LIMIT 10`) and can never show an imported review. A review with a pending draft appears in **both** — in the list as a `Draft ready` cross-link with no `Generate` button. Per-row actions split by risk: `Generate` (never-replied) expands the row inline (`InlineGeneratePanel`), `Regenerate` (already-replied) opens the `EditReplyDrawer` two-pane comparison because publishing there **replaces** the owner's live Google reply (spec §6.4). As built (#727), every affordance derives from two orthogonal axes modelled server-side (ADR 0018; replaces #678's six-valued `row_state` precedence chain `recover → regenerate → held → draft_ready → generating → generate`): the **Posted-reply axis** (`reply_state`: `none` / `posted` / `orphan`) — what exists on Google for the review; owns the Unanswered/Answered grouping and the reply panel — and the server-internal **Replacement-draft axis** (`draft_state`: `none` / `generating` / `ready` / `held`, intra-axis precedence held > ready > generating > none), which **never crosses the wire**. The card receives only `reply_state` plus the **Action slot** (`row_action`: `generate` / `generating` / `draft_ready` / `regenerate` / `recover` / `none`) — the single affordance derived from the full 3×4 cross-product (`deriveAxes` + `deriveRowAction`, `src/lib/past-replies/replies-view.ts`). A held draft never projects an affordance of its own (invariant #4 as structure): `none`×held and `posted`×held project `row_action 'none'` — a posted row keeps its live Google reply visible and silently withdraws Regenerate — while `orphan`×held keeps `recover`, because recovery addresses the orphan incident, not the draft. The `held` value itself never reaches the browser: the card reconstructs the "Reply on hold" panel for an unanswered held row from `reply_state 'none'` + `row_action 'none'`. The `gap` / `historical` section split derived from `subscription_activated_at` is deleted here, surviving only as a per-row `ProvenanceBadge` (`posted_before_joining` / `replied_on_google` / `auto_approved` / `owner_approved`); `PAST_REPLIES_VIEW_ENABLED` was **retired with it at #678** — the list renders unconditionally — while `EDIT_REPLIES_ENABLED` is kept (it gates the live-Google mutation) and `editRepliesEnabled()` (`src/lib/past-replies/flags.ts`) is now its only reader. _Avoid_: Past Replies, the archive, History tab (all name the pre-#671 surface), All Reviews page (it is a tab, not a page). *(coined in #671; spec §6.3a, §6.4; implemented at #678; remodelled at #727 per #723)*
- **On-demand generation**: owner-initiated LLM drafting from the **Reviews list** — `Generate` on a never-replied review, `Regenerate` on an already-replied one — as opposed to the live-ingest lane, which drafts automatically on every newly ingested review. It is an **owner-controlled LLM spend surface**, governed by four already-existing layers, not by new machinery (#672, 2026-08-08; spec §6.3b): a per-owner-account **rate** limit (`dashregen:owner:{acct}:burst` 10/60s + `:hour` 30/hr, **fails open**), a per-review daily cap (`regen:{reviewId}:{date}`, 3/day — advisory peek at the route, authoritative Lua INCR in `generate-draft.ts:109`, terminal), and the per-business/global **spend** reservation (`cost:daily:{bizId}:{date}`, `cost:global:{date}`). The per-account axis is denominated in **cents, not clicks**. The first `Generate` on a review is **free by construction** — `generate-draft.ts:106` charges only `version > 1`, so the sequence is one free draft then three charged regenerations per review per day; the guard stays because it is what stops the live lane's own auto-draft from eating the owner's regen budget. All three doors share **one** counter, so alternating `Generate` and `Regenerate` cannot double throughput. Because the spend ceiling is shared with the live lane and exhausting it **terminally drops** a draft, `DAILY_COST_LIMIT_CENTS_*` carries a sizing constraint rather than a reserved floor (C4). As built at #678 the two doors are `POST /api/dashboard/reviews/[reviewId]/generate` (never-replied; `origin_lane='on_demand_generate'`, always owner-only — never auto-approved) and the pre-existing `/api/dashboard/past-replies/draft` Regenerate lane, with `GET /api/dashboard/reviews/[reviewId]/draft-status` polling by `reviewId`; a moderation-held response returns `{ status: 'idle' }` and never its text. _Avoid_: on-demand drafting, manual generation, the regenerate budget (that names one layer, not the policy). *(coined in #672; spec §6.3b; implemented at #678)*
- **Review-time anchor**: `LEAST(review_date, detected_at)` — the timestamp the reputation KPIs (review velocity, rating breakdown, avg star, 8-week sentiment trend) bucket on, so a consented Review import lands in its true weeks instead of spiking the import week (and instantly yields a real historical trend). LEAST ignores NULLs: a NULL `review_date` falls back to `detected_at`; a clock-skewed future `review_date` clamps to `detected_at` (unclamped it vanishes from the trend's `generate_series` LEFT JOIN). Workflow surfaces — response rate, the All-Locations review counters, and the MonthlyImpactWorker digest — deliberately stay on `detected_at`: an import is account activity, and imported unanswered reviews are meant to drag the rate (#675 nudge reasoning). Because that workflow clock can differ from adjacent reputation charts, every owner-facing response-rate card states: "Response rate is based on reviews added to RepWorth in this period, including imported history." (#790, ADR 0019 Decision 2). Time-to-respond's companion validity filter `approved_at >= detected_at` (ADR 0019 Decision 3) is **decided but not currently implemented in code**: the only duration metric that carried it lived in the Stack A KPI service, deleted in #757 — the rule returns with the metric. One owner: `reviewTimeAnchor` (`src/lib/kpi/fragments.ts`), composed by the rendered dashboard payload — velocity, rating breakdown, avg star and sentiment trend per-location, and velocity + rating breakdown in the All-Locations aggregate (#757). _Avoid_: review_date anchor (names the column, not the clamp), import exclusion (rejected design — imported rows participate, in their true buckets). *(coined at #688 grilling 2026-08-10; legibility amended at #790 on 2026-08-12; ADR 0019)*
- **Channel actor**: the resolved identity a mobile-channel enrollment action runs as — `{ businessId, accountId, actorUserId, surface }` (`src/app/api/_shared/channels/resolve-actor.ts`), where `surface ∈ {'admin','dashboard'}` reusing `disconnectChannel`'s existing union. It is the **only axis that varies** between the two portals' 12 enrollment routes, which is why it is the seam: `resolveAdminActor` reads `businessId` from the request **body** behind `requireAdminWithAal2`, `resolveOwnerActor` reads `locationId` from the **session** behind `requireRoleOr401` and never from the body — and that asymmetry is a security boundary, not an implementation detail, so the two resolvers must never be collapsed into one function that accepts either source. The resolver also owns each portal's **gate outcome**: admin `start` applies `subscriptionGrantsFullAccess` (via `requireFullAccess`) while admin `cancel`/`disable` deliberately apply none, and owner applies `resolveWritableAccountForLocation` on all three; the runners consume the outcome and never second-guess it (spec §4.2). `surface` is not decoration — it drives the `disconnectChannel` audit tag and the `safeInvalidateChannelCache` label, so `admin.telegram.cancel` and `dashboard.telegram.cancel` stay distinct in the audit log and the cache. _Avoid_: principal, caller identity, auth context, channel session. *(coined in the PR 2 channel-route unification; spec `docs/superpowers/specs/2026-08-15-portal-audit-remediation-design.md` §4.1)*
- **Business summary**: the per-location admin DTO (`BusinessSummary`) that combines three things a caller would otherwise assemble itself — the base row (name, category, subscription status, last sync, the all-time pending-approval and pending-reconnect counts, last activity), the **trailing-30-day** response metrics (`responseRate`, `avgResponseTimeHours`, whose window is surfaced as `responseMetricsWindowDays` so no header hardcodes `30`), and the `churnScore` from `computeChurnRiskScore`. Single owner `src/lib/admin/business-summary.ts`, one exported function — `getBusinessSummaries(sql, opts?: { limit, offset })` — serving both admin surfaces: `/admin/overview` calls it unpaginated and ranks the result into the **At-risk list**, `/admin/businesses` calls it with a page and gets metrics for that page's ids only. Having one owner is the whole point: the two pages cannot disagree on how a business is counted, scored or labelled. `total` is the unfiltered `COUNT` on the paginated path and `businesses.length` on the unpaginated one, because a caller holding every row does not need a second query to be told how many it has. _Avoid_: business row (that is the DB row, one of three inputs), businesses list (named the deleted `businesses-list-service.ts`). *(coined in PR 3 of the portal audit remediation, 2026-08-15; spec `docs/superpowers/specs/2026-08-15-portal-audit-remediation-design.md` §5.2)*
- **At-risk list**: the `/admin/overview` landing list of businesses that need a look — `OverviewData.atRisk`, built by `getAdminOverview` (`src/lib/admin/overview-service.ts`) and rendered under `At risk (N of M)` beside a `View all →` link to `/admin/businesses`, where N is `atRisk.length` and M is the unfiltered `totalBusinesses`. It is **filtered, then capped, in that order**: eligibility is `churnScore.level !== 'healthy'`, and only then are the top `OVERVIEW_AT_RISK_LIMIT` (**5**) by score kept. It is **not "top 5 by score"** — an all-healthy account yields `[]` and the client renders its `EmptyState`, never five healthy businesses under an "At risk" heading; capping first would surface healthy rows whenever the first five happen to be healthy. Ordering is the pre-existing four-level comparator, moved unchanged: churn score desc → `pendingApprovalCount` desc → name asc → id asc. §5.1's "ties break on name" is the **stability** guarantee (the same data gives the same order across refreshes), not a mandate to drop the pending tier. Ranking is computed in **TypeScript and must never become `ORDER BY … LIMIT`**: `computeChurnRiskScore` is a weighted TS composite and account age contributes, so *every* business carries a non-zero score and no cheap SQL predicate is a provable superset of "at risk" — SQL ranking means reimplementing the risk model in SQL (§5.1). `OVERVIEW_AT_RISK_LIMIT` is declared and exported by the module that applies it, `overview-service.ts`, **not** `src/app/admin/page-sizes.ts` as §5.1 asks: `src/lib/**` may not import `@/app/**` (eslint `APP_LEAF_IMPORT_BAN`), and the disagreement that placement was meant to prevent cannot occur because nothing on the app side reads the number — `page-sizes.ts` carries a pointer comment instead of a second declaration (reasoning: `docs/superpowers/plans/refactor-overview-spec-alignment-deviations.md`). **Overview still reads every business row, and that is a recorded, deliberate limitation** (§5.1), not an oversight: the named rejected alternative is a SQL-ranked attention proxy (past-due, reconnect backlog ≥ 3, oldest pending, stale activity), which is genuinely bounded but drops the churn model from the landing page and would disagree with the Health column on `/admin/businesses`. Trivial at the **Capacity target** (250 locations) — do not "fix" it. _Avoid_: top 5, the churn table (names the deleted paginated `DataTable`), risk list, watchlist. *(coined in PR 3 of the portal audit remediation, 2026-08-15; spec §5.1/§5.3)*

## Capacity & scale (locked 2026-07-16 — wayfinder map #472)

- **Capacity target**: the load production is deliberately sized for — 250 locations at 6 months, ~125 reviews/day steady, a 1000-event/10-minute ingest burst drained within 30 minutes, peak 10 concurrent dashboard renders. Owned by ticket #474's resolution; ADR 0005 addendum mirrors it. Sizing beyond it requires re-opening the ticket, not silently raising numbers.
- **Design burst**: the worst-case ingest spike the pipeline must absorb without data loss — a multi-day Zernio webhook replay plus ~6 simultaneous onboardings (per-location onboarding cost is bounded by the consented Review import: ≤100 reviews inside the Import window since #675; was "backfill capped ~50" pre-#675 — same order of magnitude, burst sizing unchanged).
- **Summed LLM worker-slot cap**: the de facto global LLM concurrency limit on a single-replica worker — the sum of BullMQ `concurrency` across all non-flag-gated LLM-calling queues (≤**9**; boot-enforced by `assertSummedLlmWorkerSlots`, `worker/config/startup-assert.ts`). Flag-gated `judge_verdict` is capped at 1 separately, outside the sum. Worker *slots*, not provider calls: per-job fan-out (the demo lane's `Promise.allSettled`, ≤15 reviews) is a sanctioned unguarded lane bounded by its review-count cap and admin rate limits. Exceeding ~10 is a named trigger that forces building a global Redis semaphore first (ADR 0005 addendum). *(was "Summed LLM concurrency cap (≤8)" — #490's inventory missed `generate_demo`; renamed and corrected to the true sum, 2026-07-20)*
- **LLM provider circuit breaker**: an in-process, per-provider (`LLMProviderId`) breaker in the `src/lib/llm/` seam, consulted by `runLlmTask`. States closed/open/half-open; trips after **5** consecutive `isTransientLLMError` failures, stays **open 30s**, then admits **one** half-open probe (success or a non-transient response closes it; a transient probe failure re-opens). Open primary ⇒ skip its ~30s timeout and fail over to the fallback provider; **any provider blocked ⇒ retryable `TransientLLMError`** (never a terminal loss), terminal only when every provider was attempted and every attempt non-transient. Trip (closed→open) and recovery (→closed) emit a Sentry `warning`; other real transitions (open↔half_open churn) are structured-log-only (deviations D4). In-process ⇒ effectively global only under single-replica (ADR 0005), same posture as the Summed LLM worker-slot cap; multi-replica defers to the same Redis-semaphore trigger. Gated by `LLM_CIRCUIT_BREAKER_ENABLED` (default ON; only `false` disables). *(coined in ticket F3/P9, 2026-07-20)*
- **Backlog depth**: the count of `status='pending'` rows in a dispatch-queue table (`job_outbox`, `analytics_events`) — **total** pending, including not-yet-due retry rows (NOT "claimable only"; no `available_at <= NOW()` filter). A saturation signal against the Capacity target. Single owner: `queryBacklogDepth(sql)` (`src/lib/shared/backlog-depth.ts`), read by both the `/internal/queue-health` endpoint and the HealthAlertPoller. *(coined in the #472 observability effort, ticket #480)*
- **Backlog depth alert threshold**: the per-table pending-row count (`HEALTH_ALERT_BACKLOG_DEPTH_THRESHOLD`, default **1500**, sized to the #474 Capacity target) above which HealthAlertPoller emits a `warning` (`backlog_depth:<table>`) — a saturation nudge, not dropped work; the 5s OutboxPoller drain normally clears it. *(coined in the #472 observability effort, ticket #480)*
- **Health-bundle differential**: the checked-in `scripts/health-bundle-differential.ts` experiment (ticket #505) that isolates concurrent-`Promise.all`-vs-sequential × pool-size (`max:2` vs `max:6`) on the REAL health-check query mix (the shipped `checkXxx`/`runHealthChecks` from `worker/background/pollers/health-alert/checks.ts`), reusing the exact resolved health config so the queries fired are identical to production. Three arms — `concurrent-max2` (expect **wedged**), `sequential-max2` (the shipped cure, expect clean), `concurrent-max6` (pool-size control, expect clean) — proving the pipelining Connection wedge is pool-size×mix, not concurrency alone. Runs against an **ephemeral Supabase branch** off staging where it is the sole client, so cleanup (terminate every wedge-signature backend) needs no per-backend attribution and cannot contaminate shared staging or the #507 soak. *(coined in the #505 differential + burst-drill effort)*
- **Capacity-burst drill**: the two-arm operational drill (ticket #505/#480) driven by the checked-in `scripts/burst-drill-load.ts` against shared staging, proving outbox DISPATCH-drain of a burst of pending `job_outbox` rows plus Backlog depth observability — **not** full ingest→draft→notification (LLM) pipeline throughput. **Headroom arm**: ~1000 immediately-claimable rows paced over 10 minutes; drain rate (~600/min) outpaces injection, backlog stays low, drains ≤30 min, and `backlog_depth:job_outbox` does **not** fire — proves drain + no false alarm. **Over-threshold arm**: ~1600 future-dated rows that count toward Backlog depth but the poller cannot yet claim, so pending holds above the Backlog depth alert threshold across a poller tick and `backlog_depth:job_outbox` fires; a scoped `release` then clears the injected rows and the alert clears (pending drops below threshold **and** a subsequent HealthAlertPoller cycle completes a clean check-in emitting no such finding — `emit.ts` has no separate recovery event). *(coined in the #505 differential + burst-drill effort)*

## Solicitation (watch-mode) — locked 2026-07-23, ticket #534

- **Requests**: the owner-facing name of the Solicitation surface (`/dashboard/requests`) — the latest Solicitation batch as a funnel hero above its Spoilage report. `Solicitation` stays the internal/agent term (runs, tables, worker, flag) and `Ask` keeps its per-candidate meaning; only the screen, the nav row and the route say "Requests". *(coined in ticket #544)*
- **Solicitation batch** (a "batch"): one evaluated cohort of review-solicitation candidates — the subject of a `solicitation_batch` parent run. Its lifecycle (**built → reviewed → expired**) is owned by the batch domain entity, never by the run spine: `built` is the fact the run completed, `reviewed` is the owner opening it, `expired` is derived at read time from build age (a code-constant window, not stored). **`expired` is NOT implemented** — watch-mode has no staleness threshold and no expiry banner: the Requests screen renders a relative build time ("Built 3 days ago") and never presents a batch as out of date. The derived-expiry constant lands in send-mode, where it actually gates something (blocking sends from stale batches — `docs/superpowers/specs/2026-07-23-run-engine-executor-shape.md:87-90`). Supersedes the May reference design's "solicitation list". *(coined in the #534 executor-shape grilling; expiry scoped to send-mode in #544)*
- **Ask**: one per-candidate decision inside a batch — **send | withhold**, with a closed withhold-reason enum and the evidence that justifies it. The ask row is the authoritative decision record (it outlives run archival); the per-candidate child run is attribution. In watch-mode "send" means *would send* — nothing is transmitted. "Outreach" is reserved for send-mode's actual sends. *(coined in the #534 executor-shape grilling)*
- **Logical fan-out**: the watch-mode executor discipline — one worker job creates, steps, and completes every per-candidate child run inline under the batch parent (real parent/child graph, no per-candidate jobs, no join primitive). *Physical* fan-out (throttled spawn, `wait_for_children`, per-child retry) is send-mode machinery, built only when children genuinely run asynchronously. *(coined in the #534 executor-shape grilling; ADR 0011)*
- **Batch candidate window**: the bounded cohort a Solicitation batch evaluates from the whole accumulated location pool — never merely the upload that triggered it. Windows rotate by least-recently-evaluated ask so pools larger than one window are not stranded; this evaluation history schedules work but is not simulated contact history. *(sharpened in the #543 executor grilling)*
- **Simulated contact history**: the prior would-have-sent inclusions used by watch-mode's `over_contacted` gate. Only asks with `status='send'` enter this history; a `velocity_banked` ask is an evaluated withhold and never starts the minimum-gap clock. *(sharpened in the #543 executor grilling)*

## Solicitation (send-mode) — locked 2026-07-28 (ticket #619, wayfinder map #617)

Extends the watch-mode entries above; it never replaces them. Watch-mode reserved
**Outreach** for send-mode's actual sends and deferred the batch `expired` state to
send-mode — both land here.

- **Outreach row**: one `solicitation_outreach` row — one dispatch attempt for one **Ask**, carrying the rendered subject/body and the send lifecycle (`delivery_status` over `rendered | queued | sending | sent | withheld | cancelled | failed | unknown`, with a `disposition_reason` on every reason-bearing status and none on `rendered`/`queued`/`sending`/`sent`). This is the send-mode sense watch-mode reserved the word for: the ask says what the restraint policy decided and never changes (090 welded its status to `evidence->>'decision'`), the outreach row says what happened. One live attempt per ask (partial unique over `rendered`/`queued`/`sending`) and attempt numbers are never reused (`UNIQUE (ask_id, attempt_no)`); a regenerate terminalizes the prior row `cancelled`/`superseded` and inserts `attempt_no + 1` in the same transaction. _Avoid_: message row, ask message, send record. *(coined in the #619 executor/approval map; table created by migration 091 in #624)*
- **Send batch parent**: the `agent_runs` row of kind `solicitation_send_batch` (`subject_type='solicitation_batch'`) — the sequential sibling of watch-mode's terminal `solicitation_batch` build run. It starts when the send lane engages (generation), spans the approval wait, and terminalizes when the drip closes. Legitimately long-lived but bounded **by construction** at ≤10 days (7-day approval window + 72-hour send window), which is exactly why the spine's `stalled` threshold became kind-aware rather than raised by feel. _Avoid_: send run, drip run. *(coined in #619 D3; ADR 0014)*
- **Lazy child**: a per-dispatch-attempt `solicitation_ask` child run created **at release**, not at build — the send-mode counterpart of watch-mode's **Logical fan-out**. Children live minutes (consent recheck → dispatch → provider result → terminal), so no run is ever long-lived enough to be misread as `stalled`, the **Halt latch** has nothing to cancel in the spine, and the join needs no pre-enumeration of children. The plan stays in `solicitation_asks`; the spine records work *performed*, never work *planned* — so the spine deliberately cannot answer "how many children will this batch have." *(coined in #619 D3; ADR 0014)*
- **Settled batch**: a batch with no outreach row left in `rendered`, `queued` or `sending` — the join condition, asked of the domain table and never of `agent_runs`. Every writer that terminalizes an **Outreach row** calls `closeBatchIfSettled` in the *same* transaction, so there is no window between terminalizing and joining; it CASes `send_closed_at` on NULL (a second caller writes nothing, not even a duplicate receipt), records one close step, and terminalizes the **Send batch parent** through the disposition lookup (`exhausted`→`completed`; `halted`/`expired`→`cancelled`; `gate_closed`/`generation_failed`→`failed`). The releaser tick is a backstop calling the same function — one implementation, two callers, no join poller. Disposition is an ordered precedence over explicit sources; the status counts are the receipt's *evidence*, not the decision. *(coined in #619 D11/D14; `closeBatchIfSettled` in `src/lib/solicitation/outreach.ts`)*
- **Batch state**: the read-time `deriveBatchState(row, now)` over `solicitation_batches`' monotone timestamps — a closed union with fixed precedence `halted > closed > sending > veto_window > approved > expired > built > pending`. There is deliberately **no `status` column**: it would be a second owner of a fact the timestamps already carry, needing its own transition CHECK to stay honest. **This is where watch-mode's deferred `expired` finally lands.** The **Solicitation batch** entry above records that `expired` was specified but never implemented, because watch-mode had nothing for it to gate; here it gates approval — a batch past its 7-day approval window may not be approved by either lane — and such batches are closed through the **Halt latch** with reason `batch_expired`. `built` is the same fact watch-mode's lifecycle names; watch-mode's `reviewed` is not a member of this union, which derives send-lane facts only. *(coined in #619 D2; ADR 0014)*
- **Body redaction**: the 90-day post-send NULLing of `rendered_subject`/`rendered_body` **and emptying of `interpolation_inputs` to `'{}'`**, with `body_redacted_at` stamped and the metadata row kept forever — data minimization on third-party PII held on the contact's behalf, timed comfortably past the 14-day attribution window and past bounce/complaint feedback lag. The source goes with the prose: `interpolation_inputs` carries `contact_first_name` and `visit_note`, so redacting only the rendered text would delete the sentence and keep its ingredients. This is enforced in the schema, not merely in the sweep — `solicitation_outreach_body_presence` requires `body_redacted_at IS NULL OR interpolation_inputs = '{}'::jsonb`, so no future writer can stamp a redaction and skip the erasure. It costs the post-90-day reproducibility of the `unverifiable_fact` provenance verdict (#623 §2.4), which was already lost at the same instant anyway: that verdict is computed over `subject + body`, both of which this same sweep deletes. It is **not a delete**, which is why the retention inventory carries it as a novel shape (redact-in-place, plus purge-by-cascade). **Redaction implies TERMINAL, and that is one window on two clocks**: a `sent` row ages from `sent_at`, while a row that settled without ever sending (`withheld`/`cancelled`/`failed`/`unknown`) has no `sent_at` and ages from `rendered_at`. A LIVE row (`rendered`/`queued`/`sending`) is never redactable at any age — a bodyless live attempt can neither send nor settle, and wedges its batch behind `solicitation_outreach_one_live_per_ask`, which is the hazard the rule exists for. #624 shipped the rule as "implies **sent**", which made the stamp unrepresentable on the four never-sent terminals and left their bodies and inputs retained forever (#636 / step-7 S2); 092 widened it to the hazard's actual shape. Swept by two bounded arms of the existing `ArchivalPoller` — no new poller, because the single-replica P2 duplicate-processing budget was already spent — each oldest-first with `SKIP LOCKED`, capped at 5000 rows per cycle and logged as saturated at its own cap. A body is never logged. _Avoid_: body purge, body expiry. *(coined in #619 D6b/D6c; swept in #624; completed in #636)*
- **Halt latch**: the single monotone `halted_at`/`halt_reason`/`halted_by` write on `solicitation_batches` that stops a send batch — one mechanism, five reasons (`owner_veto`, `owner_halt`, `admin_halt`, `send_window_elapsed`, `batch_expired`). An owner veto inside the window and a mid-drip halt are the *same write with different reasons* — a veto is "halt at zero sends" — and a second halt is a no-op. It cancels outreach rows in `rendered`/`queued` and **never `sending`**: halt means "no further sends," not "undo," and the residual exposure is one child's send-transaction duration, the same honest contract the Reply lane's veto already has. It never terminalizes the parent directly; it calls `closeBatchIfSettled` like any other terminal writer, so parent terminalization keeps one owner. **There is no resume, and it is structurally prevented** — `halted_at` is monotone, the releaser predicate requires `halted_at IS NULL`, and cancelled outreach rows are terminal; to contact those people the owner builds a new batch. _Avoid_: pause, stop, cancel batch, resume. *(coined in #619 D10; ADR 0014)*
- **Attested postal address**: the owner-attested `businesses.solicitation_postal_address` plus its attestation quartet (`_attested_at`, `_attested_by_user_id`, `_attestation_version`, `_attested_digest`) — the CAN-SPAM §7704(a)(5) sender address baked **verbatim** into every ask footer, and a send precondition. Deliberately **not** `google_place_address`, which is Google's `formattedAddress`: it can be a service-area value like `"Austin, TX, USA"`, is not owner-attested, cannot express a USPS-registered PO box, and is NULLed by the offboarding purge (spec §7.5). Address and attestation are **all-or-nothing by DB CHECK**, and the attestation is welded to the address's **current bytes** by a second CHECK over `_attested_digest` — so no code path can read an unattested address as attested, and no writer can change the stored bytes without recomputing that digest. That guarantee is **narrower than "the attestation is always current"**, and the narrow statement is the load-bearing one: the digest CHECK proves the digest matches the CURRENT address, not that the preserved `_attested_at` / `_attested_by_user_id` / `_attestation_version` ever covered those bytes — a writer that changes the address AND recomputes the digest while keeping the old metadata still passes. Closing that residual needs `OLD` vs `NEW`, which a CHECK cannot see; the trigger was declined by owner decision (2026-08-04, plan "Design decisions" #1). The accidental path — a future `UPDATE … SET solicitation_postal_address = $1` that forgets the attestation — is closed; the residual is forgery rather than oversight. `_attested_by_user_id` is a **plain UUID with no FK** — a point-in-time capture, per migration 093's written lesson that 086's `ON DELETE CASCADE` meant deleting a staff member deleted their uploads. Because there is no FK, the *writer* verifies the actor. _Avoid_: business address, mailing address, footer address. *(coined in #656 — migration 099; owned by `src/lib/solicitation/postal-address.ts`)*
- **Send handoff**: the `enqueueGenerateSolicitationAsks` call at the end of `constructBatch` in `src/lib/solicitation/batch-builder.ts` — the single point where a **Solicitation batch** becomes send-mode work. It is **withheld** — not the batch, and not the individual **Asks** — when the location has no **Attested postal address** or `owner_email_bounced` is TRUE. This is why a missing address is not a **Withhold reason**: it is one per-location fact, not one decision per candidate. The precedence is first-match with `postal_address_missing` ahead of `owner_email_bounced` (it is the CAN-SPAM one), owned by `sendHandoffWithheldReason`. Spec §7.6 point 1 says "no batch produced"; that predates the shared watch/send builder and is **overridden** by §B13 of `docs/superpowers/specs/2026-07-28-send-mode-cross-spec-amendments.md` — the batch still builds, the **Spoilage report** is unchanged, and only the handoff is withheld. _Avoid_: send gate, generation gate, dispatch gate (that last is #630's, a different thing). *(coined in #656)*

- **Messaging adapter**: the channel-neutral send seam at `src/lib/messaging/messaging-adapter.ts` — **one method, `send`**, taking an `OutboundMessage` and returning the provider message id. `EmailAdapter` (Resend) is its first and today only adapter; **WhatsApp is a later *second adapter*, never a rewrite**, and `getMessagingAdapter()` is where that choice is made so no call site ever names a channel. It mirrors `ReviewPublisher` (`src/lib/publishing/review-publisher.ts`) deliberately — same seam shape, same lazy-singleton selector — because the second-adapter story is exactly the one that seam already proved. **It has zero production callers today and that is deliberate, not an oversight**: #630's dispatch worker is the first, and the hypothetical seam was accepted by map decision 14 on one condition — that it stay narrow enough to be cheap to unpick. The narrowness is the mitigation: one method, and an `OutboundMessage` whose fields are *derived* from spec §7.1's locked envelope rather than invented, so an adapter that wants a different shape is barely committed to anything. The returned id is not optional decoration — the caller MUST persist it as `solicitation_outreach.provider_message_id`, because it is the only join key the **Solicitation lane** can attribute a bounce or complaint on; a caller that discards it makes every later feedback event unattributable. Solicitation is the seam's first *tenant*, not its owner. _Avoid_: mailer, sender, transport, email service. *(coined in #657)*
- **Sending identity**: the solicitation lane's **separate sender** — three things that only mean anything together: the `reviews@feedback.<env>.repworth.net` mailbox, the `feedback.` sending domain (its own Resend domain, its own DKIM `d=`, its own DMARC record), and the domain-scoped `SOLICITATION_RESEND_API_KEY`. **Deliberately NOT the transactional identity**, and the reason is a security boundary rather than tidiness: a key leaked from this lane *cannot forge an approval email*, which would otherwise be a path around invariants #3 and #5 reached sideways, through the mail provider instead of through the approval code. The separation is only as real as its fail-closed contract, so **every solicitation config var fails closed** — unset means **no sends**, never a degraded send on the transactional key (`getSolicitationResend()` throws; `resolveFromAddress()` throws; the `'solicitation'` header category throws). The mailbox is **monitored, never `no-reply@`** — setting it creates a servicing obligation (reply-based opt-outs enter the **Suppression ledger** manually inside CAN-SPAM's 10 business days), and it is a *different* mailbox from the `SOLICITATION_UNSUBSCRIBE_MAILTO` address advertised in `List-Unsubscribe`, which carries its own daily ritual. Isolation is strong but **not total**: `feedback.repworth.net` is a child of the transactional apex, not a sibling, so organizational-domain reputation still carries some weight (spec FU-1). Stood up by `docs/runbooks/solicitation-sending-domain.md` — authored at #657, **executed at #633**. _Avoid_: from address, sender config, mail identity. *(coined in #657)*
- **Solicitation lane**: the branch of the Resend webhook ingress selected by `data.tags.lane === 'solicitation'` — **the discriminant is read before any DB lookup**, chosen over a try-table-A-fall-back-to-B chain because that chain couples the two lanes and makes a genuinely-unknown `email_id` indistinguishable from a lane mismatch. Its sibling is the untouched `notification_deliveries` path; one endpoint, one svix secret, two lanes. **Per rule DR1 the lane is not flag-gated and must never become so** — `SOLICITATION_SEND_ENABLED` masters *sending* only, so the lane, the unsubscribe ingress and the `/u/<token>` landing page all stay fully live when the flag is off; a webhook arriving for mail already sent has to be recorded regardless, and adding a gate would silently drop opt-out-bearing events. Its **write surface is deliberately narrow**: only the async signal columns migration 091 calls "columns, NOT statuses" — `bounced_at`, `complained_at`, `provider_error` — plus the **Suppression ledger**. It never writes `delivery_status` or `sent_at` (#630 owns the send lifecycle, and a webhook write would race 091's ladder CHECKs), and never `unsubscribed_at` (the RFC 8058 one-click POST lands on `worker/ingress/unsubscribe.ts`). Unmatched attribution splits by event rather than uniformly: suppression-bearing events (permanent bounce, complaint, `email.suppressed`) **throw → 503 → Resend retries**, closing the window before #630 commits `provider_message_id`, while soft bounces and `email.failed` warn and ack. _Avoid_: solicitation webhook, ask webhook, second handler. *(coined in #657)*

## Restraint policy — locked 2026-07-23, ticket #533

- **Restraint policy**: the deterministic, sentiment-blind rule set that decides send vs withhold for each Solicitation candidate — the refusal logic is the product; everything else displays its decisions. No LLM in the decision path. *(coined in the §9 solicitation roadmap; locked in ticket #533)*
- **Withhold reason**: one code from the closed six-reason enum (`no_consent`, `suppressed`, `already_reviewed`, `stale_visit`, `over_contacted`, `velocity_banked`) explaining why a candidate was not asked. Every reason is sentiment-blind by construction; `recent_negative` is permanently rejected (ADR 0012). First-match precedence; one reason per withhold. _Avoid_: refusal code, skip reason. *(locked in ticket #533)*
- **Freshness window**: the per-vertical day count beyond which a candidate's last visit is too stale for a genuine review ask (`stale_visit`). v1 is a hard window; learned decay curves are the future upgrade behind the same gate. *(locked in ticket #533)*
- **Vertical**: the coarse business-type bucket (`food_and_drink`, `retail`, `personal_care`, `fitness`, `medical_dental`, `automotive`, `home_services`, `other`) resolved deterministically from the owner-typed `businesses.category` text, falling back to `other`. *(coined in ticket #533)*
- **Velocity banking**: withholding an otherwise-eligible candidate solely because the batch cap is reached — banked most-recent-visit-first-kept, expected to return in a later batch. Volume shaping, not rejection. *(coined in ticket #533)*

## Competitor Delta (locked 2026-07-23 — ticket #532, wayfinder map #528)

- **Competitor Delta line**: the per-location weekly Insights digest line reporting the Named rival's review velocity since the most recent preceding matching snapshot and the review-count gap ("Joe's gained 4 reviews since our last check; gap now 27"), computed from that location's primary tracked keyword's local-pack snapshot. The "since our last check" interval is deliberate because Ranking tracking currently runs biweekly; it must not be described as "this week." Gap = rival's review count minus ours — never rating or rank in v1. Empty states degrade in order: never-configured → line omitted; watching-but-no-snapshot-yet → one teaser line; no preceding match → gap without velocity. *(coined in #532; cadence wording sharpened in #539)*
- **Named rival**: the single local-pack competitor the Competitor Delta line reports on — the owner's pick where one exists, otherwise the Auto-default rival. A pick survives the rival's absence from the pack: an absent pick reports the dropout ("dropped out of the local pack") while the absence spans the latest snapshot window — so the note repeats across weekly digests that read the same biweekly window — then the line falls back to the Auto-default rival until the pick reappears; a pick is never auto-removed. Mechanics: the pick is stored per location as `businesses.rival_place_id` + `rival_title_snapshot`; the live pack title wins whenever the pick is present (a renamed rival reports its current name), and the stored snapshot is only used to name the dropout. Dropout is derived, never stored — a pick absent from the latest pack but present in the immediately preceding one, read from the same two-snapshot window that drives velocity; a pick present with a NULL review count is not a dropout (it fell back, nothing left), and a pack recorded empty for the latest date never raises one. *(coined in #532; pick mechanics locked in #546)*
- **Auto-default rival**: the deterministic stand-in Named rival before any owner pick — the nearest-ahead-by-reviews competitor (smallest positive review-count gap in the latest pack; the nearest challenger tied or behind when no competitor is ahead), ties broken by rank position (NULL last) then place identity. Digest copy labels it `Auto-selected rival` so an algorithmic stand-in is never presented as the owner's choice. An owner replacing it with an explicit pick is itself probe engagement signal. *(coined in #532; disclosure sharpened in #539)*
- **Competitor pack**: the full ~20-entry `local_results` set persisted as `competitor_snapshots` rows per (business, keyword, search_location, snapshot_date) — is_self row included when the location appears, entries with missing place_id/rating/review_count kept with NULLs. Replaced atomically on re-run (replace-pack idempotency); an empty pack for a date is itself a recorded fact. *(coined in #538 grilling)*

## Solicitation contacts & visits (locked 2026-07-23 — ticket #535)

- **Contact (Solicitation)**: the deduped identity of one person at one location, keyed `(business_id, normalized handle)`. An incoming CSV row matches a contact if EITHER normalized handle (email or phone) matches; a matched contact merges in a handle it lacked; a row whose handles match two different contacts is rejected `ambiguous_identity` — never auto-merge. *(locked in ticket #535 grilling)*
- **Visit**: one append-only ledger row per contact per calendar date, unique on `(contact_id, visit_date)`, carrying the optional staff/job note and an FK to its upload. Visit dedupe makes overlapping re-uploads fully idempotent (`duplicate_visit` is informational). This is the visits-ledger tracer of design doc §9 decision 3. *(locked in ticket #535 grilling)*
- **Normalized handle**: the canonical contact identifier — lowercased/trimmed email or E.164 phone (US assumed for 10-digit) — computed once at CSV ingest and stored on the contact. It is the future suppression-ledger join key (per channel), never the contact row id: delete + re-upload must not un-suppress an opted-out person. *(coined in ticket #535 grilling)*
- **Consent attestation**: the per-upload record — attesting user id, timestamp, versioned attestation-text constant — required as a blocking step at CSV upload; contact/visit rows inherit its provenance via their upload FK. It is NOT a per-row consent claim — per-handle consent state is the **Consent ledger**'s job (below, #625). *(coined in ticket #535 grilling; per-row semantics resolved by #625)*
- **Consent ledger**: the `solicitation_consent` table (migration 093, #625) — one current-state row per `(channel, normalized_handle, business_id)` answering "which attestation covers this handle, for this channel, at this location." Written ONLY by csv ingest inside the per-business advisory-locked transaction (D8), and only for the resolved contact's RETAINED email (§7.1 deletability — `consentEligibleEmail`); phone handles mint zero rows (DR3, email-only). **Monotone forward** (§4.2): the guarded upsert (`WHERE EXCLUDED.attested_at > attested_at`) upgrades to a newer attestation and never downgrades, so replayed jobs are no-ops and an in-flight pre-deploy v1 job cannot overwrite a v2 row; a version change emits `solicitation_consent_upgraded`, a same-version re-attestation bumps silently. Send-eligibility is `attestation_version ∈ SEND_ELIGIBLE_ATTESTATION_VERSIONS` (v2-only — v1's text never named email sending, which is the `consent_attested` tautology #625 killed); an ineligible-version row withholds `no_consent` **case (b)** (upload_id + attestation_version populated), no row at all is **case (a)** (both null — the whole pre-#625 legacy cohort, no backfill by decision; #629's case-(a) copy must be self-sufficient). Revocation lives in the suppression ledger, never here (D7 — no `revoked_at`, ever): consent fails closed, suppression fails open (DR1), so consent rows hard-delete with their contact (by handle, same tx) and via an explicit purge-stage sweep (spec §7.2 as corrected — businesses are tombstoned, the cascade never fires on purge). RLS deny-all; no TTL (§7.3). _Avoid_: consent flag, attested boolean, consent snapshot (that is what #630 stamps on outreach at dispatch). *(coined in #620 grilling; shipped by #625, PR #640)*

## Solicitation suppression & unsubscribe — locked 2026-07-28 (ticket #621)

Extends the contacts & visits entries above; it never replaces them. The **Consent ledger**
records what the owner asserted, this records what the recipient revoked — and the second
outranks the first, permanently.

- **Suppression ledger**: the `solicitation_suppressions` table (migration 096, #643) — one row per opt-out, keyed on the **Normalized handle** per channel and never on the contact row id, so delete-and-re-upload cannot launder it (#535 §6). Rows are **first-write-wins** (`ON CONFLICT … DO NOTHING` against two partial unique indexes, each predicate re-spelled byte-for-byte): a `complaint` arriving after an `unsubscribe_link` leaves the earlier row alone, because the state is already correct and the history belongs in the provider webhook records #622 §5 already stores. Seven closed sources (§3.1) — `unsubscribe_one_click`, `unsubscribe_link`, `bounce_permanent`, `complaint`, `provider_suppressed`, `admin_manual`, `owner_manual` — exported as `as const` arrays by the single authoritative `src/lib/solicitation/suppression.ts`, never string literals at call sites. Soft bounces, `delivery_delayed`, `email.failed` and any ambiguous bounce classification **never** suppress (§3.2); `provider_suppressed` is the known-dirty source, because Resend's list is team-wide across every domain and API key including transactional (§3.3). **No expiry, ever** — a TTL on an opt-out is a violation with a cron job attached. Both evaluation points are **existence checks**, never a comparison against `suppressed_at`, which deliberately sidesteps the postgres.js microsecond-truncation class. The handle is stored **raw, not hashed** (§6.4). RLS deny-all — server-owned in the `auto_approval_policies` posture (invariant #14), because a direct client read would expose the `account_id` provenance §7.4 forbids surfacing. Two derived rules bound it: **DR1** — `SOLICITATION_SEND_ENABLED` masters *sending* only, so flipping it off leaves every ledger write, the ingress and the landing page fully live. **DR2** — the ledger is **solicitation-only**; a transactional or notification path that consults it stops delivering approval emails to an owner who opted out as somebody else's customer, reaching invariant #3 sideways. _Avoid_: blocklist, do-not-mail flag, opt-out table, suppression list. *(coined in #621 grilling; schema + domain core by #643, PR #647)*
- **Suppression scope**: the `scope ∈ {'global','account'}` discriminator recording **who authored the opt-out**, not how widely it happens to apply. `global` is the recipient's — or the mail ecosystem's on their behalf — keyed `(channel, normalized_handle)` across every tenant, legitimate because the recipient spoke and defensible under one shared sender (`reviews@feedback.repworth.net`), where a complaint scores against the domain no matter which business sent. `account` is the owner's `owner_manual` do-not-contact, keyed `(channel, normalized_handle, account_id)`; global would let Owner A silently degrade Owner B's reach with no recipient having said anything — a cross-tenant write dressed as a product feature. The source/scope pairing is **enforced by a DB CHECK** (G11), because `owner_manual + global` would otherwise insert cleanly; it is **one-directional** — `scope='account'` requires `account_id NOT NULL`, while a `global` row MAY still carry `account_id` as provenance. **Lookup contract**: a handle is suppressed for an account iff a `global` row exists for `(channel, handle)` OR an `account` row exists for `(channel, handle, account_id)` — owned by the one exported fragment `suppressionMatchSql` and never re-implemented at a call site (G7: no `isSuppressed()` helper, because the second consumer does not exist yet). **Global wins** when both match (G3): reporting the account row would let an owner clear it under §7.6, watch the contact stay suppressed, and have no idea why. Retention splits on the same axis (D7) — global rows are `allowed_limited_retention` and survive an account purge with `account_id` intact, account rows hard-delete. _Avoid_: per-account suppression, tenant scope, suppression level. *(coined in #621 grilling; D1/D5)*
- **Unsubscribe token**: a row in `solicitation_unsubscribe_tokens` (migration 096, #643) — a SHA-256 `token_hash` via `node:crypto` (invariant #10) plus the redemption target, deliberately a **dedicated table rather than a column on `solicitation_asks`** (D8) so redemption still works after the sender is gone. Raw tokens exist only in memory and in the sent message, never in Postgres, outbox payloads or logs (invariant #5). **No expiry**: CAN-SPAM §7704(a)(3) requires links operate ≥30 days, and there is no expiry value better than none. `account_id`/`business_id`/`ask_id` are provenance only and are **scrubbed to NULL** by the offboarding purge while `token_hash`, `normalized_handle`, `channel` and `sent_at` are kept — the row outlives the account that minted it. `outreach_id` is `ON DELETE SET NULL` (G1, amending B9): CASCADE would delete retained tokens through the `solicitation_outreach` → `solicitation_batches` → `contact_csv_uploads` chain and break §5.2, while no FK at all would leave a scrubbed row carrying a stale pointer nothing could detect. Provenance obeys a **one-way implication** (G12) — `account_id IS NULL` implies `business_id` and `ask_id` are null — deliberately excluding `outreach_id`, which SET NULL may null independently while the account is still live. A second redemption is a no-op success, and unknown and used tokens are indistinguishable to the caller (D3). _Avoid_: unsubscribe link row, opt-out token, magic link. *(coined in #621 grilling; D8; table by #643, PR #647; redemption by #644)*
- **Unsubscribe redemption**: exchanging an Unsubscribe token for a `scope='global'` Suppression ledger row — the only thing #644 does. **Claim first, then suppress**: a single `UPDATE … SET redeemed_at = NOW() WHERE token_hash = $1 AND redeemed_at IS NULL RETURNING account_id, normalized_handle, channel` is the one write-ordering primitive, and `recordSuppression` is fed from the provenance that statement locked, never from a value read earlier. **`business_id` is deliberately NOT returned** — `recordSuppression` has no field for it, so claiming it would be provenance the ledger cannot record, and G12's one-way implication (`account_id IS NULL` ⇒ `business_id IS NULL`) already makes it redundant for the null case. Ordering it the other way round lets a replayed spent link silently undo an audited **Correction path** removal, and lets a concurrent purge write a suppression carrying stale non-null provenance against §5.2. Four closed outcomes, and the third is the one that is easy to lose: `redeemed` · `already_suppressed` · `already_redeemed_not_suppressed` · `unknown_token`. **A spent token is not proof of a live suppression** — `redeemed_at IS NOT NULL` proves only that it was *once* redeemed, so the spent branch reads the ledger explicitly; with no live global row the outcome is `already_redeemed_not_suppressed`, which mints no receipt and deliberately does **not** re-suppress. This is checked against a global-only existence query rather than `suppressionMatchSql`, which answers a different question (may we contact this handle *for this account*) and would be satisfied by an `account`-scoped row that makes the success sentence false. **Honest failure**: a token that does not resolve returns `unknown_token` rather than a success-shaped no-op, because reporting success on a #630 mint race is precisely the lost opt-out this ticket exists to prevent. _Avoid_: consume the token, burn the link, mark unsubscribed. *(coined in #621 grilling; ordering locked across review rounds 2–4 of #644)*
- **Success receipt**: the server-minted HMAC that gates whether the `/u/<token>` success copy may be **shown** — `<issuedAtMs>.<base64url HMAC-SHA256>` over the token hash, keyed on `SESSION_COOKIE_SECRET`, 10-minute TTL, verified with `timingSafeEqual`. Minted only after a write commits, and only for `redeemed` or `already_suppressed`. It exists because a bare `?done=1` rendered "You're unsubscribed" with no token resolved and no suppression written. **Necessary but never sufficient**: verification proves a suppression existed when the receipt was *minted*, and the Correction path can remove it during the TTL — so the page renders success only when the receipt verifies **and** a live global row exists **at render time**. *A page may claim "you are unsubscribed" only from a ledger read taken during that render.* The receipt authorises nothing and grants no access; it is enumeration-resistance evidence, not an access token. _Avoid_: confirmation token, success flag, done parameter. *(coined in #644 owner-run adversarial reviews 1 and 3 — three false-success vectors, one root cause: asserting a fact about mutable ledger state from evidence decoupled in time from it)*
- **Neutral page**: the single identical `/u/<token>` render for unknown, malformed, and already-redeemed tokens — §5.4 enumeration resistance made structural, so no caller can distinguish the three. It carries the `SOLICITATION_UNSUBSCRIBE_MAILTO` fallback so a recipient never dead-ends, and omits that line entirely when the address is unset rather than rendering a broken one. Distinct from the **button page**, which names the originating business, and from the success view, which names **none** — the §5.5-versus-§5.4 conflict resolved in §5.4's favour, because rendering §5.5's named-business sentence on the success page would require resolving a now-redeemed token and make it distinguishable from an unknown one on that URL. _Avoid_: error page, not-found page, generic page. *(§5.5/§5.4 conflict resolved at #644 plan time with owner sign-off)*
- **Correction path**: the **admin-only, audited removal** of a suppression row that is factually wrong — an admin typo on a manual entry, an ambiguous bounce the #622 §5.3 fail-safe did not catch, or a `provider_suppressed` mirror that originated on the transactional side (§3.3). Framed as **error correction, never re-subscribe**: not exposed to owners, not to recipients, no self-serve entry point, and it writes an audit record naming who removed the row and why. It exists because "no re-subscribe" without it is itself a defect — a typo would be permanently unfixable and the answer to "please put me back" would be "we cannot, ever," a worse story than the one the rule was avoiding. **The sink is a `solicitation_suppression_corrections` row (migration 098), not `account_audit_log`** (P-1): it takes `writeAccountAuditLog`'s *posture* — the record lands with the act it describes — but deliberately not its table, because `account_audit_log.account_id` is `NOT NULL REFERENCES accounts(id) ON DELETE CASCADE` and the rows §8.2 exists to correct carry **no account** (an `admin_manual` global row entered from a forwarded mailbox reply names none; neither does a `provider_suppressed` mirror originating on the transactional side), while a CASCADE would additionally delete the compliance record along with the account it merely names as provenance. Atomicity is **structural, not conventional**: `correctSuppression` is ONE data-modifying CTE whose `DELETE … RETURNING` feeds the INSERT (P-9), so the delete cannot commit without its record even if a call site forgets a transaction, and a row already gone returns `not_found` rather than an orphan record. The table carries **no FKs at all** (P-2) — a compliance record must outlive every referent it names, and the row it describes is deleted by the same statement that writes it — but it **does** snapshot the corrected row's `normalized_handle`, `account_id`, `created_by_user_id` and `note` (P-3, D-A11). Those four are the evidence behind the assertion being corrected: `suppression_id` points at a deleted row, so without the handle the record cannot identify its subject, and without the creator and the §7.3 originating message reference it cannot show the original entry was legitimate. `account_id` is not merely provenance — for a `scope='account'` row it **is** the Suppression scope key (§1.2, non-null by construction), so omitting it left account-scoped corrections unable to say whose do-not-contact was removed. Carrying that evidence makes the table account-linked, so it is **classified** — `retain_compliance_limited_pii`, the disposition its siblings `solicitation_suppressions` and `solicitation_unsubscribe_tokens` already carry (D7) — rather than renamed to evade classification: `original_*`-style column names slip past `accountLinkedTablesFromMigrations()` on a word-boundary technicality, and naming data to dodge a governance check is worse than the gap it hides. Distinct from **§7.6 owner clearing**, where an owner removes an `account`-scoped row they created themselves because no recipient ever spoke; that act writes to **`account_audit_log`** instead (P-4), since it is account-scoped with a non-null `account_id` and is emphatically not the compliance act — different act, different sink, deliberately not interchangeable. An owner may **never** clear a `global` row, and the UI must not present the two controls as the same thing. _Avoid_: unsuppress, re-subscribe, opt back in, restore contact. *(coined in #621 grilling; D6 §8.2; shipped by #645 — migration 098, `src/lib/admin/suppressions-service.ts`, the AAL2-gated `/admin/suppressions` console under **Safety**. The P-n citations above are #645's plan decision register, `docs/superpowers/plans/2026-08-03-645-manual-suppression-paths.md`)*
- **Attestation never overrides suppression**: stated verbatim because it is the most likely way self-serve re-subscribe gets built by accident — an owner re-uploads a CSV, re-attests consent, and someone reasons "they attested, so we're covered." **Attestation is the owner asserting a relationship; suppression is the recipient revoking one. The second outranks the first, permanently.** Consent and suppression are independent inputs to `evaluateAsk`; the withhold-reason precedence (`no_consent` before `suppressed`) governs only **which reason is reported when both apply** and is not an override relationship — it will be misread as one unless this is written down. The mechanism backing the rule is #535 §6's handle keying, which is why an opt-out cannot be laundered by delete-and-re-upload. Its build-time expression is **populate, do not pre-filter** (§4.2): the batch build stamps `candidate.suppression` and `evaluateAsk` owns the withhold, so the shipped precedence-2 `suppressed` gate never becomes dead code. _Avoid_: consent overrides, re-consent, re-permission. *(coined in #621 grilling; D6 §8.1)*

## Admin invite funnel — locked 2026-08-14 (plan `docs/superpowers/plans/2026-08-14-admin-invite-funnel.md`)

- **Admin invite**: an **Account** minted by staff at `/admin/businesses/new` from exactly three facts — owner email, owner name, business name — whose owner then walks the *same* self-serve funnel every other owner walks. The durable marker is `businesses.onboarded_by IS NOT NULL`, and it is deliberately the **only** marker: no per-account comp flag, no invite table, no parallel journey. That single column carries three separate meanings downstream (who provisioned the row, the **Beta comp coupon**'s eligibility test, and the `CleanupAbandonedSignupsPoller`'s exclusion), which is why widening or reusing it is a bigger act than it looks. The form collects nothing else because everything it used to collect now has a better owner: the location comes from the owner at `/onboarding/start`, voice from the wizard, tier from `/onboarding/pay` (created on the `copilot` default). The pre-2026-08-14 shape — a 4-section form ending in a dead-end handoff screen, activated by a human out of band — is **gone**, including `pending_payment_admin_handoff` and `PendingAdminHandoffScreen`; a doc that still names them is stale. _Avoid_: hand-onboarding, manual activation, admin-activated account, "the handoff" (all name the deleted flow). *(coined in the admin-invite-funnel plan, steps 3–4 and 8)*
- **Checkout attempt**: the **Account**-owned durable lease in `accounts.checkout_attempt_*` (id, tier, variant, price ids, expiry — and since migration **105**, `checkout_attempt_coupon_id`). Every Stripe Session parameter is built from that **immutable snapshot** under a per-attempt idempotency key, never from a live env or config read. The snapshot is the point: a Session created under key *K* must be reproducible from key *K* forever, so any input that could change between the attempt's creation and its retry has to be frozen INTO the attempt or it becomes a way to send Stripe different params under the same key. **That is why the coupon had to join it** — `BETA_COMP_COUPON_ID` is an env var, and an ops flip between an owner's first click and their retry would otherwise silently change the price under a key Stripe treats as identical. It also fixes the decision's *locus*: the coupon is resolved once inside `applyTierSnapshot`'s transaction while the activation lock is held, so eligibility is read at one instant against one primary Business, rather than re-derived at each session creation from whatever the environment says now. An attempt is complete-or-cleared as a **whole** (`accounts_checkout_attempt_complete_check`, 077 as rewritten by 105): the cleared branch enumerates every attempt column, so a cleared attempt cannot retain a coupon snapshot; the active branch leaves the coupon nullable, because NULL there is not a missing value but the explicit *no-coupon* decision recorded for every non-invitee. _Avoid_: checkout session (that is Stripe's object, downstream of this), checkout lease, pending checkout, "the tier snapshot" (that names one field of it). *(coined in the admin-invite-funnel plan step 2; columns from migration 077, coupon from 105)*
- **Funnel entry**: the single server-computed destination an owner is *owed* given their state — `resolveFunnelEntry` (`src/lib/onboarding/funnel-entry.ts`), surfaced on the wire as **`funnelUrl`**. Precedence is load-bearing: `pending_payment` + demo on + no place → `/onboarding/start`; + place → `/onboarding/demo` (the drop-off return point — an owner who captured a location and left must land back on the demo they were promised, not re-capture and not skip it); `pending_payment` otherwise → `/onboarding/pay`; **Full access** + wizard incomplete → `/onboarding/business`; else `/dashboard`. It is **pure** — no DB handle, no `process.env`, no flag read (the caller passes `onboardingDemoEnabled()` in) — which is what keeps the whole matrix table-testable and keeps flag state server-side (invariant #13): the browser learns a URL, never a flag. It exists because the decision had **three** owners that disagreed, and it replaced all three: `loginDestination.ts`'s demo-blind `pending_payment → /onboarding/pay`, `POST /api/auth/verify-otp`'s private start-vs-pay branch, and `/api/dashboard`'s hardcoded `paymentUrl`. That third one is the naming trap — **`paymentUrl` is deleted, not renamed**: a field called `paymentUrl` holding `/onboarding/demo` is a lie, and the value stopped being a payment URL the moment the demo lane became a legitimate destination. _Avoid_: payment URL / `paymentUrl` (the deleted predecessor), next step URL, redirect target, onboarding step. *(coined in the admin-invite-funnel plan step 7; review-log round-2 findings 1+2 merged into one owner)*
- **Beta comp coupon**: the 100%-off, 3-month `repeating` Stripe **Coupon** auto-applied to an **Admin invite**'s checkout, so a beta tester activates through the real Stripe rails at **$0 due today with a card still collected** (`payment_method_collection: 'always'`, set explicitly — a 100%-off subscription session would otherwise skip card collection and month 4 would fail). Eligibility is exactly two facts: `onboarded_by IS NOT NULL` on the **primary** Business (`is_primary = TRUE` — the column lives on `businesses`, so an unscoped join would let a multi-location account's comp depend on an arbitrary row) AND `BETA_COMP_COUPON_ID` being set. **The kill switch is unsetting that env var, and it affects NEW attempts only** — an attempt that already snapshotted the coupon keeps it, because the **Checkout attempt** is idempotent by construction; that is the contract, not a leak. It is a *server-selected coupon*, not a promotion code, and no owner ever types anything. **On a comped session `allow_promotion_codes` is OMITTED, never sent as `false`** — Stripe treats it and `discounts` as mutually exclusive **by parameter presence, not by value**, so sending `false` beside a discount fails the entire request ("You may only specify one of these parameters"). An absent key already means "no promotion-code entry", which is all `false` was ever asking for; a full-price session still sends it explicitly. That asymmetry is load-bearing rather than incidental: the plan asserted the two could coexist, the claim survived four adversarial review rounds and every mocked unit test, and it 500'd the first real staging checkout (**D-16**). A doc that says the key "stays `false`" on the coupon path is describing the bug, not the fix. During the beta window every admin invitee is comped — there is deliberately no per-account comp flag, and a concierge-*paid* invite is the trigger to build one rather than a case to special-case now. Because silent non-application means a founding customer gets charged, the decision is both logged and emitted as the durable `checkout_coupon_decision` analytics event with a reason (`applied` / `skipped:not_invited` / `skipped:env_unset`), and a coupon Stripe rejects raises `CheckoutCouponConfigurationError` + a Sentry report rather than a generic checkout failure. _Avoid_: promo code, discount code, beta discount code, trial (a comped subscription is `active`, never `trialing` — the 30-day `TRIAL_ENABLED` trial is a different mechanism with different entitlement rules). *(coined in the admin-invite-funnel plan steps 1–2 and 11)*
