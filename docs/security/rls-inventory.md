# RLS Inventory

RepWorth uses authenticated Supabase reads for owner-facing data and service-role Postgres.js for trusted writes. Every table in `public` must keep row level security enabled even when most durable writes are enforced in application code.

**Scope of this page (#1300).** One row per member of `RLS_REQUIRED_TABLES` (`scripts/ci/rls-tables.ts`) — the registry `ci:rls-audit` enforces, and the sole owner of "this table must carry RLS". It is deliberately **not** `TENANT_TABLES` (`scripts/ci/tenant-tables.ts`), which answers the different question "is this table tenant-scope audited": `job_outbox`, `admin_audit_log`, `poller_heartbeats`, `analytics_events`, `flagged_responses`, `impersonation_sessions`, `owner_leads`, `poller_cursors`, `solicitation_send_breaker` and `users` are all registered here and all reviewed as *not* tenant-scope audited. Until #1300 both audits read `TENANT_TABLES`, so those ten had no RLS coverage at all and rested on their own migration suites. `scripts/ci/__tests__/rls-audit.test.ts` asserts this page has a row for every registered table.

**What `pnpm ci:rls-audit` enforces.** Three arms, the first two DB-free and therefore the ones that run in CI's `lint` job: (1) every registered table has an `ENABLE ROW LEVEL SECURITY` in some migration; (2) the **deny-all recurrence guard** — a table left RLS-on with zero policies must also carry an explicit `REVOKE ALL ON <table> FROM anon, authenticated`, because RLS filters ROWS and removes no table privilege, and migration 122 (#1176) left SELECT/INSERT/UPDATE/DELETE in the Supabase default privileges so the next deny-all table would inherit them; (3) a live `relrowsecurity` read when `TEST_DATABASE_POOL_URL` is set, which is also the only arm that catches a **stale** registry entry. The guard is static rather than live on purpose: the test container (`scripts/ci/test-db-bootstrap.sql`) never reproduces Supabase's default client-role table grants, so a live privilege probe would pass vacuously.

Rows marked `— (deny-all)` in the Scope column are **not** owner-scoped by an `account_id`/`business_id` predicate: RLS is on with zero policies, so every row is denied to `anon`/`authenticated` and the client-role privileges are revoked outright. Server access is via the RLS-bypassing Postgres.js `postgres` role, and their SQL touchpoints are exempted in `scripts/ci/tenant-scope-allowlist.ts` for structural reasons (provider event id, opaque slug, global retention, admin role, or offboarding job scope).

The audit is intentionally small: it verifies that required tenant tables appear in `pg_class` for the public schema and that RLS is enabled. It does not prove every policy predicate. Policy behavior remains covered by focused integration tests and route/module tests.
