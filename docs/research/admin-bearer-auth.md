## What this means for the dual-mode gate (facts, no design)

- The SDK verifies a cookie-less bearer two ways: `getClaims(jwt)` (local ES256 on both projects; blind to revocation) or `getUser(jwt)` (network; revocation-aware). Today's gate already pays two `getUser()` calls per admin request (`db/auth.ts:63`, `proxy.ts:73`).
- AAL is a claim in the bearer. `getClaims(jwt).data.claims.aal` yields it after signature verification; `getAuthenticatorAssuranceLevel(jwt)` after decoding only, plus a `getUser` call. The no-argument form the gate uses today returns nulls on a bearer-only client.
- The Admin app's challenge → verify produces an `aal2` session the API can trust for that session's life; factors are per user, so shared across apps.
- Handing the anon key to a second app adds no PostgREST exposure on prod: it reads nothing, and a non-admin JWT reads only its own owner-scoped rows.

## Open risks

1. **Revocation window.** A locally-verified bearer stays valid up to `JWT_EXP` after sign-out or admin revoke; only `getUser(jwt)` closes it, at one network call per request.
2. **`aal2 → aal1` stale JWT.** Removing an admin's factor does not invalidate outstanding `aal2` tokens.
3. **Staging `job_outbox` RLS off** (5c): the staging anon key, which the second developer holds, reads outbox payloads there. Prod is closed; lockstep needs a migration, and a `TENANT_TABLES` entry would make `ci:rls-audit` guard it.
4. **`MFA_ENFORCEMENT_ENABLED` gates the proxy's AAL check** but not `requireAdminWithAal2`; a bearer path must not inherit that flag by accident.
5. **JWKS cache per Vercel instance.** A rotation is a `kid` miss → fresh fetch; a revoked *old* key still verifies for up to 10 min.
