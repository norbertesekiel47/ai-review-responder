Contacts and reviews each carry the bound location predicate, and outreach contact IDs are restricted to the existing candidate window. Construction validates the location/account pairing at lines 838–854 before this read. Migration 091 additionally enforces composite outreach business/account, batch/tenant, contact/business and ask/tenant FKs. The new joins reject even a schema-valid foreign review pointer: migration 114's review FK alone does not enforce review location, so the explicit `r.business_id` predicate is necessary and present. No names, handles, ratings or sentiment enter the new projection.
- **Retained, missing and deleted evidence:** `batch-builder.ts:549` requires recorded attribution, a surviving review pointer, a non-null real review date and a non-deleted review. Migration 114 nulls the pointer on hard review deletion while retaining attribution provenance; the inner join then excludes it. Soft deletion is separately excluded. There is no matcher/display-window predicate and no dependency on the archived agent-run link or redacted outreach body. The latest qualifying attribution wins deterministically by attribution timestamp and unique outreach ID; filtering happens before `DISTINCT ON`, so an invalid latest pointer does not hide older valid evidence. Dates remain database text through the decision evidence.
- **Precedence and durable outcomes:** the lookup populates candidates rather than removing them. `restraint-policy.ts:496` still evaluates consent, suppression, then the matched review, and lines 516–523 return the actual ID/date. `commitAskDecisions` persists that decision as evidence, records `ask_withheld`, and links the completed child run through the unchanged write path. The existing `already_reviewed -> wrong_moment` mapping is exercised by the added integration case.
- **Atomicity, locks and retries:** the new SELECT uses the construction transaction at `batch-builder.ts:785`, after owned-outbox completion CAS, per-location advisory lock, batch row lock and account gate. It introduces no row lock and no lock-order reversal. A lookup error rejects the transaction before ask persistence. Asks, Refusals, child runs, links, parent completion, `built_at` and any follow-up outbox insert remain in the same transaction. Preparation may already have committed the existing running parent; construction retry reuses it. Committed builds are guarded by outbox ownership and `built_at`, while the Refusal writer additionally deduplicates by source/subject. No provider call or extra queue mutation is introduced.
- **Kill switch and failure propagation:** `src/lib/refusals/write.ts:1013` still owns the set write. The empty-set path issues no query; disabled recording returns before materialization/SQL; enabled failures propagate to construction rollback. The new attribution evidence is independent of recording being enabled, so disabling the ledger still withholds the ask. There is no new flag read, resolver or telemetry path in the changed construction code.
- **Bounds and index support:** the candidate ID array remains capped at `MAX_DATA_ROWS` (5,000), and `DISTINCT ON (o.contact_id)` returns at most one evidence row per candidate in one sequential query. Migration 091's `idx_solicitation_outreach_contact_business (contact_id, business_id)` supports the bounded ID/location lookup; ask/contact/review ID joins have their existing primary/composite keys. This is not a claim of constant scanned history: retained outreach history may grow, and the query may sort qualifying history before deduplicating. Migration 114's unattributed-candidate partial index is deliberately inapplicable to this attributed-history query. Existing index support is sufficient to avoid asserting an unsupported missing-index defect; no execution-plan or latency claim is made without a database measurement.
- **Archival sentinel:** `src/lib/refusals/read.ts:447` binds account/location, orders newest first with an ID tie-breaker and requests exactly 201 events. The flag is true only above 200; the extra row is removed before reversing and pairing. Thus the sentinel cannot become an invented archive start. Exactly 200 remains untruncated, 201 is disclosed, account scope returns false, and the separate full refusal count and entry truncation remain unchanged. Leading unpaired reactivations remain ignored; missing older periods are qualified even when none survive pairing. Migration 034 provides `idx_account_audit (account_id, created_at)` for scoped temporal access; location/event filtering and the ID tie-break may require additional filtering/sorting. The returned read is bounded; no claim is made that all underlying scan work is bounded.
