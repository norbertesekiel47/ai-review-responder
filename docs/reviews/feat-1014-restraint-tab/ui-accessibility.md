## ANSWERS

### 1. Heading hierarchy: is `h1 Analytics` → `h2 What we held back` → `h2` per group a correct, non-skipping outline? Are the `aria-labelledby` references valid and unique?

**Yes on both, with one caveat that is not a defect.**

- `TopBar.tsx:88` renders `<h1 className="page-title">{title}</h1>`; `DashboardStatePanel.tsx:44` sets `title: 'Analytics'` for the `restraint` surface, and `RestraintReport.tsx:263` renders `<TopBar title="Analytics">`. So the page has exactly one `h1`, identical across loading, error, empty and populated. (The screenshot harness emits `<h1 class="topbar-title">` rather than `page-title` — a harness artifact; the level is the same.)
- `RestraintReport.tsx:272` is `<h2 class="card-h2" id="rst-summary-heading">`; `RestraintReport.tsx:325` is `<h2 class="rst-group-title" id={rst-group-${category}}>`. h1 → h2 → h2. **No skipped level.** The category sections are siblings of the summary in `.rst-stack` (:267-309), so peer-level `h2`s are the structurally honest choice — an `h3` would imply containment that the DOM does not have.
- `aria-labelledby` targets: `rst-summary-heading` is a literal, rendered once. `rst-group-${group.category}` is derived from `REFUSAL_CATEGORIES`, and `groupByCategory` (:213-222) maps over that array once, so **at most one group per category** exists — ids are unique by construction. Every `aria-labelledby` resolves to an id present in the same document. Verified in all four populated/empty HTML fixtures.
- Caveat: both `<section>`s carry an accessible name, so each becomes an exposed `region` landmark. A window with 8 categories produces 9 regions. That is verbose but valid, and it is the reason the group headings are reachable by landmark as well as by heading. Not raised as a finding.

### 2. Five stacked `<p class="rst-note">` disclosure lines — readable, or do they bury the count? Especially at 390px.

**They bury it, and UA-1 is the reason.** The design intended a hairline plus 30px of separation between the count and the disclosures; `:first-of-type` (restraint.css:229) means that never renders in any state, so all five lines join the summary copy at a uniform 8px rhythm.

Concretely at 390px (`restraint-account-populated@390.png`): the card is 8 paragraphs deep. The "6" and its caption occupy the top ~120px; the four disclosure sentences occupy ~230px below it — roughly two-thirds of the card is caveat, set in the same muted grey at 13px against the summary sub-line's 14px, a difference that is not perceptible at that size. The empty state (`restraint-empty@390.png`) is worse, because there is no numeral at all to anchor the eye and the darkest text in the card is the scope disclosure (UA-12).

The count itself is not *cropped* or *pushed below the fold* — `.rst-summary-line` (`flex-wrap: wrap`, restraint.css:36-42) correctly lets the 30px numeral wrap onto its own line above the caption, which reads well. The burial is contrast and grouping, not position. Fixing UA-1 (and optionally lifting `.rst-note` into a `<div>` the divider can hang off unconditionally) addresses most of it; the maximum stack is **five** notes plus one per archived period, so a location view with two archived periods reaches six.

### 3. Is the empty state distinguishable from an error state for a screen-reader user?

**Yes, and by more than one cue — this one is clean.**

They are not, in fact, "the same card region". Empty renders `<section class="card rst-summary" aria-labelledby="rst-summary-heading">` → an exposed `region` landmark named "What we held back", containing an `h2` of the same name and the sentence "We did not hold anything back between …". Error renders an **unnamed** `<div class="card">` (`DashboardStatePanel.tsx:91`) — no landmark — containing `<h2>Unable to load your restraint record</h2>`, preceded by a `role="alert"` live region. Verified in `restraint-empty.html` vs `restraint-error.html`.

So a screen-reader user gets three independent discriminators: the assertive alert (error only), the landmark (empty only), and two heading texts that share no words. The empty state's copy is a positive factual claim; the error's is an explicit failure. No finding.

### 4. Does `LiveRegion` "Restraint record ready." announce redundantly on every window change?

**No — the risk is the opposite, under-announcement.** Two independent mechanisms suppress it:

1. **Constant message.** The string never changes (`RestraintReport.tsx:266`). A live region only announces *changes*; identical content re-rendered into an existing region announces nothing.
2. **Remount, not update.** `RestraintContent.tsx:55` returns `panel` or `<RestraintReport>`. On a window change the queryKey changes (`:34`), there is no cached data for the new key, `isPending` goes true, and the panel replaces the report — then back. Each transition destroys and recreates the `role="status"` node **with its text already inside**, which is the case `LiveRegion.tsx:9-12` explicitly says does not announce.

Window *focus* likewise does not double-announce: `refetchOnWindowFocus` defaults true, but a background refetch with data in hand leaves `isPending` false, so the panel never mounts and `RestraintReport` never remounts.

Filed as **UA-10 (LOW)**, and the useful fix is not to remove the announcement but to make it carry the result (the count and the window), so the announcement is both *different* each time and *worth hearing*.

### 5. Does the error path double-announce, rendering the message twice?

**No.** `DashboardStatePanel.tsx:90` renders the message in `<LiveRegion level="assertive">` (→ `role="alert"`, `aria-live="assertive"`, `.sr-only`) and `:93` renders it again in a plain `<p>`. The `<p>` is **not** a live region, so it is never auto-announced — it is the visible equivalent of the announcement, which is correct practice, and it satisfies DESIGN.md's "one announcer per message, never both" (the second copy is not an announcer).

One real mechanical caveat, not raised to actionable: the loading and error branches render `LiveRegion` at the **same position in the same fragment slot**, so React updates one DOM node's `role` from `status` to `alert` and `aria-live` from `polite` to `assertive` in place. Mutating `role` on a live node is not uniformly handled by AT; some readers re-derive the accessible node and skip the announcement. Since the text also changes in the same commit, most AT will announce it, and I am below 80% confident it fails — noted here rather than in the table.

What **is** actionable on this path is the content, not the count of announcements: see **UA-3** (identical heading and body, and raw `Error.message` reaching the alert).

### 7. Keyboard: `AnalyticsTabs` renders links, not tabs. Is `aria-current="page"` correct? Any focus-visible regression?

**Correct, and no regression.**

- `AnalyticsTabs.tsx:26-41` is a `<nav aria-label="Analytics views">` of two `next/link` anchors with `aria-current="page"` on the active one and `undefined` on the other. That matches `ReviewsTabs.tsx:21-36` **verbatim in structure**, and matches `docs/brand-asset-library/design-systems/console/DESIGN.md` § Tabs: *"Route tabs … are a `<nav>` with `aria-current="page"` — never `role="tab"`."* `CardViewTabs` (the `role="tablist"` form) is correctly not the precedent. Both links are in the natural tab order; `role="tab"` here would have promised arrow-key traversal of panels that do not exist.
- Focus: `console.css:26-29` applies `outline: 2px solid var(--rw-focus); outline-offset: 3px` via `.rw-console :where(a, button, …):focus-visible`. `:where()` contributes zero specificity, so **any** later rule setting `outline` would silently win — I checked: neither `.tab` (console.css:1418-1434) nor `.rst-row-link` (restraint.css:162-175) nor `.rst-group-count` declares `outline`, so both new interactive surfaces inherit the ring. `.tabs` sets no `overflow`, so the 3px offset is not clipped. No regression.
- Tab order on the populated page is: skip link → sidebar → TopBar controls → period toolbar → Metrics → Restraint → then each row link in DOM order. Logical and matches visual order at 390px; at 1440px the row links are visually right-aligned but still follow their date in DOM order, which is correct.
- Note for UA-6: the row links are keyboard-reachable and correctly ringed; the target-size problem is pointer-only.

### 8. Responsive at 390px: does anything overflow, truncate, or wrap badly? Is the group heading + count pill the offender?

**Nothing overflows or truncates. The pill pairing is imperfect but is not the worst offender.**

From `restraint-account-populated@390.png` and `restraint-empty@390.png`:

- **Group head + count pill.** `.rst-group-head` is `flex-wrap: wrap` (restraint.css:72-77) and the ≤768px query drops `margin-left: auto` (:196-199). Result is *conditional*: short headings ("Not safe to send", "Not the right moment") keep the pill inline on the same row; the long one ("Acting on your behalf paused") pushes the pill onto its own line, left-aligned. Visually inconsistent between cards but never clipped, never overlapping, and `white-space: nowrap` (:96) keeps "2 times" intact. Below the actionable bar on its own.
- **Row links.** `flex-basis: 100%` (:201-203) drops the link to its own full-width line under the date — correct and legible, but it is what creates the UA-6 target-size problem and removes the positional cue that distinguishes a link from the date beside it.
- **Long prose.** The policy-gate sentence (the longest string on the surface, 158 chars) wraps to 4 lines at 390px inside the card with no overflow. `max-width: 62ch` is inert at this width and correctly does not constrain further.
- **`.rst-summary-line`.** Wraps the 30px numeral above its caption. Reads well.
- **No horizontal scroll** in any 390px shot; `.content--analytics` drops to 14px padding (console.css:743).
- The real 390px defects are **UA-1** (no disclosure separation), **UA-6** (target size) and **UA-12** (hierarchy inversion in the empty state) — not overflow.

The genuinely bad width is **1440px**, not 390px: see **UA-8**, the ~1,600px gap between a row's date and its link.

### 9. Does `RestraintReport` render links whose accessible name is ambiguous when repeated?

**Yes.** Filed as **UA-5 (MEDIUM)**. `hrefFor` (`RestraintReport.tsx:102-113`) returns a **constant** URL for `auto-approval` and `contacts`, and `LINK_LABEL` (:90-94) gives a constant name, so N rows in one category yield N links identical in both name and destination — proven in `restraint-account-populated.html` (two `See your contacts` → `/dashboard/contacts` inside one `<ul>`). The `<time>` is a sibling of the `<a>`, never part of its accessible name, so nothing disambiguates them. The branch's own stylesheet already carries the fix (`.rst-group-link`, restraint.css:108-123) and the component simply does not use it (UA-11).

Only `review` links vary per row (`/dashboard/reviews/<subjectId>`) — and those are still all named "See the review", so a category with three held drafts also yields three identically-named links to three *different* pages, which is the sharper form of the same problem.

### 10. Is the hard-coded `en-GB` correct for this product, or a defect for non-UK owners?

Filed as **UA-9 (MEDIUM)**, with the tradeoff stated rather than assumed — the full three-option comparison is in the findings table. Short form:

- The **pin itself** is defensible and the comment's reasoning (:230-234) is sound: an unpinned formatter makes rendered-text assertions pass or fail by machine. That is a real problem and pinning is a real fix.
- The **choice of `en-GB`** is the defect, on two counts. (a) The Console's own convention is `en-US` at 17+ sites, including `RankingChart.helpers.ts:21` and `ReputationTrendChart.tsx:35` — charts on the *adjacent Analytics tab*. So the same window renders "2 Aug 2026" on Restraint and "Aug 2" on Metrics, one click apart, and `en-GB` uniquely produces the 4-letter "Sept" where `en-US` gives "Sep". (b) The comment cites `BatchReport.tsx` as its precedent, but that file (`:221`) uses `new Intl.DateTimeFormat(undefined, …)` — the viewer's locale. The cited precedent does not support the choice made.
- I am **not** asserting `en-US` is right for a UK customer; that is a product call about who the owners are. I am asserting at ≥80% that *one Analytics surface rendering the same window in two date conventions* is a defect regardless of which one wins.
