## Answers to the five questions put to this axis

**Q1 — do the two new modules survive the deletion test?**

*`src/lib/auto-approval/posting-status.ts`: yes, on precedent.* It has one production caller. Deleting it would fold fifteen lines into `settings.ts`'s `buildPostingStatus`, and complexity would not reappear across callers — so on the bare house rule ("no abstractions for a single caller") it is borderline. Two things carry it. First, it is the exact shape of `readiness.ts` sitting beside it: an impure adapter in `settings.ts` (`buildReadiness` / `buildPostingStatus`) feeding a pure fold in its own file (`buildAutoApprovalReadiness` / `buildAutoApprovalPostingStatus`). Introducing a second, different arrangement for the sibling concept would be the worse outcome. Second, `settings.ts` is already 1,289 lines; pushing the fold into it trades a justified small file for growth on a file that is 29% over the size guideline. The plan's stated reason (readiness "ships into an external API contract") is *also* true but is not the load-bearing one — the precedent is. **Verdict: keep.**

*`worker/boot-flag-summary.ts`: yes, clearly.* `worker/index.ts` cannot be imported by a test (importing it boots Fastify), so the eleven-flag list in the boot file was genuinely untestable; the module converts it into a tested unit and satisfies invariant #12. Deleting it puts behaviour back in an entry point. **Verdict: keep.** The *internal* split into `buildBootFlagSummary` + `logBootFlagSummary` is weaker — see the appendix — but the module itself earns its place.

**Q2 — is `describePolicyStatus` still coherent with a fourth branch?**

Coherent, but it has crossed into condition-ladder territory, and the cause is duplication rather than branch count. See the `:655` finding: the function now asks "is the account default armed?" four times and "how many posting overrides?" five times. Judged against what the file already did — the pre-existing branches already re-tested both predicates — the new branch conforms to the local style rather than degrading it, which is why this is [low] and not [medium]. It is the right place for the next reader to apply the subject-resolution refactor, not a blocker for this branch.

**Q3 — was the duplicated constant really collapsed?**

No. Two of three copies were collapsed. `ONBOARDING_PLAN_ORDER` (`src/app/onboarding/pay/plan-options.ts:4`) survives, is element-identical, sits in the same data flow as the copy that *was* deleted (both drive `PlanPresentationViewModel`), and the plan asserts "There are two today". The new home (`tier-config.ts`) is the right one — it owns `SubscriptionTier`, `TIER_CONFIG` and `tierGrantsAutopilot`, and 104 files already import it. Fixing the third copy is a two-line change in the same PR. This is F1 above.

**Q4 — `POSTING_BLOCK_COPY` beside `BLOCK_REASON_COPY`: duplication or two legitimate things?**

Two legitimate things, with one real duplication inside them. The unions genuinely differ (`readiness` answers "may the owner widen?", `posting` answers "does anything post?"), the value shapes differ (`ReadinessCopy` object with an optional CTA vs a plain string), and `provider_moderation_disabled` — the one key present in both unions — carries deliberately different sentences that are both correct. Keeping them separate is right. What is *not* right is `runtime_disabled` / `auto_approval_disabled`: one flag, two names, two literals sharing a byte-identical first sentence, both rendered on the same screen in the default production state. That is F3.

**Q5 — comment density and naming.**

The new code reads like its neighbours, and in places better. Comment density is high (`posting-status.ts` is 21 comment lines to 15 code lines) but that matches `readiness.ts`, `settings-guards.ts` and the surrounding auto-approval modules, and every comment states a *trap* rather than restating the code — the `tierGrantsAutopilot`-vs-`autopilotPurchasable` warning is exactly the kind of note this codebase's conventions ask for. Naming is consistent: `buildAutoApprovalPostingStatus` mirrors `buildAutoApprovalReadiness`, `AutoApprovalPostingBlockReason` mirrors `AutoApprovalReadinessBlockReason`, and the deliberate choice of the input name `tierGrantsAutopilot` (so the readiness value cannot be passed by accident) is good defensive naming. The two exceptions are the comment/icon collision at `AutoApprovalClient.tsx:755` (F4) and the phrase "the five autonomy flags", which names a term the repo already defines with six members (F2).

## Low-confidence appendix (not in the table)

- **`logBootFlagSummary` as a separate function.** One production caller, one line of body. The docblock justifies the split as "so a test can prove the record actually reaches the log", but the test that proves wiring is a TypeScript-AST scan of `worker/index.ts` source, which would work identically against an inlined `logger.log('Feature flags', { flags: buildBootFlagSummary() })`. What the split *does* buy is a unit assertion on the emitted shape (`'Feature flags'` + `{ flags }`), which is otherwise unreachable. Marginal either way; I would not ask for a change.
- **Asymmetric decomposition standard within one change.** The server-side five-boolean fold was extracted into a new 51-line module, while the client-side copy table plus a fourth branch were added to `AutoApprovalClient.tsx`, taking it from 1,426 to 1,475 lines (47% over the 1k guideline). The same reasoning that justified `posting-status.ts` argues for a `policy-status.ts` beside the client. Pre-existing size, so not charged to this branch — but the next addition to that file should carry the extraction.
- **Hand-curated flag list has no completeness guard.** `DECLARED_FLAG_KEYS` in the test is an independent hand copy, so it catches a change to the module — but nothing detects a *new* autonomy flag added elsewhere in the codebase that should be reported at boot. Given the module's premise ("the only way to confirm a flag flip reached the process"), a `ci:` sweep over `src/lib/**/flags.ts` exports would make the list self-maintaining. Out of scope for #1173.
- **`status.detail.map((line) => <div key={line}>)`** uses the rendered sentence as the React key. Safe today (all eleven strings are distinct), pre-existing pattern, noted only because the blocked branch is the first to build that array from a dynamic list.
- **Test-name convention drift.** The new suites open every title with the symbol under test ("`loadAutoApprovalSettings` returns…", "boot flag summary contains…"), while the pre-existing `AutoApprovalClient` suite uses plain prose ("names a location that posts on its own…"). Both conventions now live in the same files. Cosmetic.
