## NON-ACTIONABLE appendix (uncertain, or verified-and-cleared)

**A1 — `weekRowLabel('')` renders `Invalid Date`, but the exposure is pre-existing.**
`toIsoWeekStart` (`active-mappers.ts:40-47`) returns `''` for a null or unparseable
`week_start`. `weekRowLabel('')` → `new Date('')` → `toLocaleDateString` → `"Invalid Date"`.
Before this branch the per-location axis *already* rendered `Invalid Date` on even
indices for the same input (`datum.label` is the same formatter), so the branch does not
create the class; it does newly expose it in the stacked chart's row headers and x-axis
labels, which previously printed the raw (empty) key and nothing respectively. I could not
construct a path where `week_start` is null — the query is a `generate_series` over
non-null `gs::date` — so I am below the confidence bar for an actionable finding.

**A2 — the tooltip still papers over the thinning.** `VelocityChart.tsx:288` reads
``title={`Week of ${hoveredDatum.label || `#${hover.index + 1}`}`}``, so hovering an
odd-indexed bar shows *"Week of #3"* — the same "not a date at all" defect the branch
diagnosed for the `sr-only` table and fixed with `weekRowLabel`, left in place one file
over. `non_goals[1]` says tooltips are #1086's affordance, which is why I am not calling
this in scope; but the inconsistency is inside the file the branch already edited, and
`weekRowLabel(hoveredDatum.id)` is a drop-in.

**A3 — `weekRowLabel` is a non-component export in a `'use client'` component file.**
`velocity-math.ts:1-3` states the split exists *"so the component file exports only
components (Fast Refresh hygiene, react-doctor only-export-components)"*. The deviations
disclose the wrong home and record the follow-up, and no ESLint rule enforces it
(`rg react-refresh eslint.config.mjs` → no hits), so this is disclosed rather than hidden.
Flagging only because the *reason* recorded is the edit surface, not the convention.

**A4 — `paint-order` degradation.** Where `paint-order` is unsupported, SVG paints
stroke over fill, so a 3px `--rw-card` stroke on 9px glyphs would hollow out `avg 8.8`
rather than merely un-halo it. Support is universal in the browsers this Console targets
(Chrome 35+, Firefox 60+, Safari 8+, Edge 79+), so I do not think this is real. Separately,
the owner-authorised `avg` fix carries **no test** — reasonable, since jsdom does not
model `paintOrder`, and the deviations cite a fresh 390px render instead.

**A5 — `edge_cases[1]` (single data point) and `edge_cases[3]` (reduced motion).**
Both hold behaviourally: `trendSpanLabel(1)` → `last week`, `rankingSpanLabel` has an
explicit `dates.length === 1` arm (`RankingChart.tsx:49`), `weekShortLabel(iso, 0, 1)`
never thins, and the branch adds no animation. Neither is tested and neither is recorded
as considered. I did not raise these because, unlike F2, the code demonstrably handles
them.

**A6 — `RecentSentimentMix`'s `sr-only` "Reviews" column is a bare number**
(`RecentSentimentMix.tsx:83`) while its twin says `"7 reviews"`
(`RecentRatingBreakdown.tsx:70`). In a table the `th scope="col"` supplies the unit on
announcement, so I read this as harmless asymmetry rather than a `user_visible_behavior[1]`
miss — noting it in case the reviewer wants the twins spelled identically.

**A7 — aggregate vs per-location week counts.** I checked that
`StackedVelocityChart`'s caption (`trendSpanLabel(weeks.length)`, from the union of
per-location keys) cannot disagree with the card header's `last {data.length} weeks`
(from account-level `reviewVelocity`): both derive from the same `generate_series` in
`aggregate-queries.ts:198-213`, and `aggregate-service.ts:274` builds the account series
by folding the same per-location slices. No finding.

**A8 — `trendSpanLabel(1)` vs the card header.** The caption would read `last week`
while `VelocityCard.tsx:27` reads `last 1 weeks`. Pre-existing header wart, not touched
by this branch, and the intake's invariant 2 is about a chart and its *aggregate peer*,
not a chart and its card header.
