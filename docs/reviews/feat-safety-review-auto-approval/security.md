## Non-actionable / speculative

- **Logging and PII are clean.** `logSafetyEvaluation` (`persist.ts:188-204`) emits UUIDs, an integer, two booleans and two enums; the `safety_reviewed` step detail is four enum/boolean fields; `logger.warn` at `safety-review.ts:241` carries a count, and at `:288` carries `err.name` only — never `err.message`. `redactProviderError` (`error-classifier.ts:82-95`) copies `name` + truncated `message` and deliberately drops `cause`, so the ZodError (which for a `z.enum` mismatch can embed the received value) never reaches a log or Sentry. No `Sentry.captureException` is added on this path, and `LLMStructuredOutputError` never escapes `reviewSafety`. ADR 0032's "no draft text anywhere, input or output" rule is genuinely honoured.
- **Tenant scope is clean.** The `api_costs` write carries `businessId` (the job's) and `accountId` (`ctx.accountId`, from the same loaded `businesses` row), matching the neighbouring triage/judge writes. The spine step is written on `tx` inside the persisted-draft transaction against the run already resolved for that review. Both `agent_run_steps` readers are account-scoped (`src/lib/agents/read.ts:392` `AND ar.account_id = ...`; `src/lib/agents/operator/policy-state.ts:251` filters on a different `step_key`). No new cross-tenant query.
- **No migration is needed and none is missing.** `agent_run_steps.step_key` is plain `TEXT` with no CHECK (`071_agent_run_spine.sql:53`), and `attributed_agent` accepts `'system'` — so `stepKey: 'safety_reviewed'` cannot throw inside the persist transaction. I specifically chased the "new step key → in-tx throw → BullMQ retry → second paid draft" theory and it does not exist.
- **The gate's fail-closed shape is well covered by tests.** `auto-approval.test.ts:663-684` pins `null`, `undefined`, a verdict with no `cleared`, and a `mock` clearance all to `safety_review_unavailable`, plus two fast-check invariants over the full axis space. Nothing there covers the contradiction case (S2) or the failover case (S1), which is why both are findings rather than notes.
- **`verify-gate.sh`'s forced `DATABASE_POOL_URL` export** is net safer than what it replaces (it stops a shell that sourced `.env.local` from handing the gate's suites the production pooler), but it is unconditional whenever `TEST_DATABASE_POOL_URL` is set, including when that value was itself lifted out of `.env.local`. Worth knowing; not a defect in this diff.
- **Speculative:** `answered` accepts `typeof verdict.cleared === 'boolean'` on an in-process object today. If a verdict ever becomes durable (persisted, re-read, JSON-round-tripped across a queue boundary), `'false'`-as-string and `0`/`1` become representable inputs; the `typeof` check already anticipates this correctly, so this is a note that the check is load-bearing rather than defensive, not a finding.
