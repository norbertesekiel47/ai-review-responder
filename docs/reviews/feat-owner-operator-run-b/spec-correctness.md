## Evidence

**1 — the §1 label is missing.** Spec §1 opens with "The three-way contract every proposal card carries" and the table `Proposed rule → Active rule` / `Fact to remember → Remembered fact`; §3.3 lists the card's contents as "**the label (§1)**, the operation in plain words, the target …". The intake restates the applied half verbatim: "the card's label becomes the applied label". `label_kind` is stored (migration 120:102), surfaced on `ProposalView` (`src/lib/agents/operator/proposals.ts:180`) and set on every catalog proposable (`catalog.ts:158,167,178,187`) — and then `git grep labelKind -- src/app/(authenticated)/dashboard/operator` returns **only two test fixtures**. `ProposalCard.tsx:68` renders `proposal.describe` as the heading and `:105` renders the constant `PROPOSAL_APPLIED = 'Applied'`; `wording.ts` declares no label strings at all. `evidence/proposal-card-1440.png` and `evidence/receipt-390.png` confirm it on the built screen: the pending card reads "Set the reply tone to "warm and brief"" with no label above it, the applied card reads "Applied". Failure scenario: the pilot owner cannot tell a *rule the engine enforces* from a *fact a workflow reads* — the exact distinction §1 says v1 exists to prove — and after Apply the card says the generic word "Applied" instead of "Remembered fact", so the transcript is not the "operating rules timeline" §6.6 is designed to grow out of.

**2 — rule 11 is claimed BUILT with placeholder ids.** At head, `docs/runbooks/beta-launch-alerting.md:416` reads `**BUILT 2026-09-12, staging rule \`<staging-rule-id>\`, production rule \`<prod-rule-id>\`**`. The row it replaced said "REQUIRED BEFORE `OWNER_OPERATOR_ENABLED` GOES ON; NOT CONFIGURED BY THIS CHANGE". The pattern the intake names to follow is rule 9, one line above: `**BUILT 2026-09-04, rule \`3946648\`**` — a real integer. The spec's new §14 bullet compounds it: "BullMQ retry exhaustion reaches Sentry … under runbook **rule 11**, which Run B built in both Sentry projects before the staging flip", and the new §15 Run B entry repeats "rule 11 built in both Sentry projects". Nothing in the branch records a Sentry rule id, and CLAUDE.md's routing row for this feature states "Run B owes the rule-11 Sentry build before any flip". Failure scenario: T8 reads the runbook, sees BUILT, flips `OWNER_OPERATOR_ENABLED` on staging, and the first `agent_turn` retry exhaustion pages nobody — the precise risk `risk_reasons[2]` was written to prevent. Either fill both ids from the Sentry API, or restore the "NOT CONFIGURED" wording; a BUILT row whose ids are angle-bracket placeholders is worse than the row it replaced, because it silences the go-live checklist.

**3 — a follow-up message vanishes while it prepares.** `post()` (`OperatorClient.tsx:432`) does `setConversationId(body.conversationId ?? submission.conversationId)`. For the **second** message in a conversation, `submission.conversationId` is the existing `conversationId` and the route returns the same id, so React bails out on the identical value. The conversation effect's deps are `[disabled, fresh, conversationId, scopedLocationId, reloadEpoch, writeUrl]` (`:315`) — `turnId` is deliberately excluded, and `post()` bumps neither `reloadEpoch` nor any other dep; it also calls `conversationLoadRef.current?.abort()` at `:423`, killing any read that was in flight. Meanwhile `setDraft('')` at `:424` clears the composer and the transcript renders only stored turns (`:605`, `turn.ownerText`) with no optimistic bubble. So between Send and turn completion the owner's own words are on no part of the screen; only the first message of a conversation escapes this, because there `conversationId` genuinely changes from `null`. Failure scenario: the owner sends "actually make it shorter", the textarea empties, the transcript still shows only the previous exchange, and "Preparing your plan" gives no hint which message is being prepared — for the 20–60 s a real turn takes.

**4 — the Receipt names the operation in machine words.** `ReceiptView.tsx:57-58` renders `<dt>Change</dt><dd>{receipt.operation}</dd>`, and `receipt.operation` is `proposal.operation` copied straight out of `apply.ts` (`operation: proposal.operation`), i.e. the catalog id string. `evidence/receipt-390.png` shows `CHANGE / set_tone` under the owner-facing Receipt. Spec §3.3 requires "the operation in plain words" and the codebase already has that function — `proposal.describe`, which `mapStored` recomputes from the catalog on every read (`proposals.ts:223`) and which the same card uses as its heading eight lines above. Failure scenario: the one document §6.5 says "establishes that something changed" describes the change with an identifier the owner has never seen anywhere else in the product.

**5 — the Receipt names the actor by uuid.** `ReceiptView.tsx:65-66` renders `<dt>Applied by</dt><dd>{receipt.actorUserId}</dd>`. The evidence PNG shows `APPLIED BY / e9cffeb9-a736-497d-989d-d464f8dd4a50`. Spec §6.5 lists "actor" as a Receipt field, and the stored field is correct — the defect is the rendering: `OwnerIdentityProvider` is already mounted around this page by `(authenticated)/layout.tsx`, and the card already resolves a location uuid to a name through the injected `locationLabel`. The T7 deviation read-back recorded exactly this ("the Receipt renders `actorUserId` and the turn id as raw uuids on an owner-facing card … wording is the wave's call"), so this finding is that call. The turn id under **Reference** is defensible — §6.5 calls it a correlation id and a support reference is legitimately opaque — but "Applied by <uuid>" answers a question about a person with a database key.

**6 — two refusal codes the card cannot speak.** `apply/route.ts:83` is `case 'rejected': return jsonResponse({ error: result.reason, proposal: result.proposal }, 409)`, and `result.reason` ranges over `PROPOSAL_FAILURE_REASON`'s `contract_changed | unauthorized | account_offboarding | location_not_found` (`apply.ts` `rejected()` call sites at the actor check, the writable-subscription check, the tier check and the archived-location branch). `wording.ts:111-126` — whose docstring is "Route error codes the card and the composer **have to** speak" — declares `contract_changed` and `location_not_found` but not `unauthorized` and not `account_offboarding`, so `routeErrorSentence` falls through to `ROUTE_ERROR_FALLBACK` and `writeProposal` (`OperatorClient.tsx:523`) writes that into `cardErrors`. Failure scenario: an owner whose subscription lapsed past grace clicks Apply and sees two contradictory sentences one above the other — the card's state line "Your account can no longer make this change. Nothing was applied." (correct, from `PROPOSAL_FAILURE_WORDING`) and the refusal notice "Something went wrong. Nothing was changed — try again." (wrong: retrying can never succeed). Same for an offboarding-blocked account, which `edge_cases[9]` names explicitly.

**7 — an unusable `?locationId=` answers two different ways.** In `reads.ts` the no-conversation branch returns `null` when `activeLocationId` misses (`:226-227`), which `conversation/route.ts:58` maps to `404 conversation_not_found`; the has-conversation branch computes `summaryLocationId = … await activeLocationId(…)` (`:293-297`) and, on the same miss, returns `200` with `summary: null`. The route already owns a distinct `location_not_found` code but spends it only on a malformed uuid (`route.ts:43`). On the client, `conversation_not_found` is explicitly swallowed as "a legitimate empty screen, not an error" (`OperatorClient.tsx:256-257`), so nothing is shown. Failure scenario: a multi-location owner whose selected location was archived in another tab loads `/dashboard/operator`; before their first message they get an empty screen with no summary, no connect CTA and no explanation, while the identical condition after their first message renders the transcript with a silently missing panel. `user_visible_behavior[11]` promises the scoped summary and the connect call to action at exactly this moment.

## Appendix — low-confidence / non-actionable observations

1. `mapStored` now calls `parseVersionToken` unconditionally (`proposals.ts:224`), which **throws** on any `prepared_version_token` that is not the strict `{businessId, updatedAt}` shape. Every Run B writer produces that shape, so nothing is broken today — but the throw is inside the transcript read (`listProposalsForTurns`) and inside `readSummary`'s `listPendingProposals`, so the first slice-2 auto-approval Proposal written under the account would 500 the whole conversation GET rather than degrade one card. Worth a decision when slice 2 lands, not now.
2. `ProposalCard.tsx:59-60` calls `parseVoiceState` during **render** in a client component with no error boundary on the route; a row whose stored preview does not narrow would blank the entire screen instead of one card. Same "not reachable with today's writers" caveat as (1).
3. `recordTerminal` sets `decided_by_user_id` on a **stale** row, while `markSiblingProposalsStale` does not. Two stale rows from the same Apply therefore disagree about whether a human decided anything. `declineProposal`'s idempotency signature keys on `status='rejected' AND failure_reason IS NULL`, so nothing misreads today; flagged only because `observability[0]` lists `decided_by_user_id` as a distinguishing column.
4. The retry affordance (`OperatorClient.tsx:662-675`) appears for **every** non-OK POST, not only a lost response — including `turn_key_conflict` (whose own wording says "Start a new conversation", not "try again"), `forbidden` and `past_due_read_only`. Re-POSTing an identical payload on those cannot succeed. Low confidence that this crosses the intake's line, since `user_visible_behavior` only promises the lost-response case.
5. `isProtectedOwnerApiRoute`'s new comment (`src/lib/shared/protected-routes.ts:57-58`) says the page needs nothing here because "`/dashboard/operator` … the `/dashboard/` prefix below already admits" — but the prefix on the next line is `/api/dashboard/`, and the page is actually covered by proxy branch 7, which the same sentence goes on to say. The code is right; the middle clause of the comment is not.
6. `SummaryPanel.tsx:41-51` hand-rolls the connect call to action rather than reusing `ConnectGoogleBanner`. `user_visible_behavior[11]` says "the **existing** connect call to action"; reading that as "the existing destination `/dashboard/connect`" is defensible, so this is recorded rather than reported.
7. The poll loop's 4-minute deadline is re-armed whenever `conversationId` changes (`OperatorClient.tsx:391` deps), so a turn that is adopted mid-flight can get a longer wall-clock ceiling than 4 minutes. Rare enough, and always in the owner's favour, that it is not reported.
