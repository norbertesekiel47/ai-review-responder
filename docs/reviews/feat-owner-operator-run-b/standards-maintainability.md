## Evidence

**F1 — `catalog.ts`: `apply` and `writerFields` are the same fact written twice.**
`defineProposable` now takes both an `apply(voice, input) => VoiceConfig` and a `writerFields(input) => Partial<VoiceConfig>`, and each of the four proposables supplies both: `apply: (voice, input) => ({ ...voice, tone: input.tone })` beside `writerFields: (input) => ({ tone: input.tone })` (`catalog.ts:162-163`, and the same pairing at `:173-174`, `:182-183`, `:191-192`). `apply` has exactly one consumer — `preview()` at `:108-110`; `writerFields` has exactly one — `apply.ts:245`. So the preview the owner approves and the write that commits are computed from two independently authored expressions. A typo in one produces either a write of a field the owner never agreed to (the exact hazard `writerFields`' own docblock at `catalog.ts:68-77` was added to prevent) or a Receipt with `differsFromPreview: true` and no red test: `git grep writerFields` returns nine hits, none in a test, and `catalog.test.ts` does not mention it. **Smallest correction:** delete `apply` from the spec type and derive it — `preview(voice, input) { return { before: voice, after: { ...voice, ...spec.writerFields(input as T) } }; }` — which removes four lines from the catalog and makes the divergence unrepresentable. Behaviour is identical, including the `updatedAt` key that rides on `voice`.

**F2 — `OperatorClient.tsx` is one module carrying three machines.**
The component body runs from `:147` to `:734` and holds 14 `useState` calls (`:152-192`), 3 refs (`:163`, `:170`, `:189`), 3 effects — the ref mirror `:164`, the conversation loader `:228-315`, the poll loop `:329-391` — and 10 `useCallback`s, before a 155-line return tree; `TurnBody` (`:749-854`) is a second component in the same file. Three of the state slots (`loadEpochRef`, `pollEpoch`, `reloadEpoch`) exist only to sequence the two effects against each other, which is the signature of a state machine that wants its own module. The nearest precedent named in the brief does exactly that split in the same directory tree: `dashboard/requests/RequestsClient.tsx` is 778 lines but its component body is ~90, with `useLatestBatch` (`:492`), `useAttributedReviews` (`:654`) and `useReviewedPing` (`:734`) owning the fetch/poll state and `Screen`, `BuiltBatch`, `ChooseLocation`, `LoadingCard`, `FailureCard` owning the rendering; `src/hooks/` holds fourteen more precedents of the same shape. **Smallest correction:** two sibling hooks and one file move, no behaviour change — `useOperatorConversation()` (the GET, the load epoch, the adopt/resume decision, `:228-315`), `useTurnPoll(turnId, …)` (the deadline timer, backoff and terminal branch, `:329-391`), and `TurnBody` into `TurnBody.tsx`. That leaves the component as composition plus the write callbacks, and it makes the two hardest-won behaviours here (the epoch guard and the independent deadline) independently testable instead of reachable only through a rendered tree and a mocked `fetch`.

**F3 — the local wire types are now byte-equivalent duplicates, and one of them re-spells a status vocabulary.**
Deviation T3 #1 justifies the local declarations because T2 had not landed: against the fork point `turn.unsupported` did not exist and `conversation` was non-nullable. At head both are true of the server type — `OwnerConversationTurn` carries `locationId` (`reads.ts:113`) and `unsupported: UnsupportedView[]` (`reads.ts:121`), and `OwnerConversationView.conversation` is nullable (`reads.ts:152`) — so `TranscriptTurn` (`OperatorClient.tsx:73-84`), `ConversationViewBody` (`:86-90`) and `UnsupportedRow` (`:67-71`) are field-for-field restatements of types that exist. The "HTTP consumer" rationale (`:52-64`) is not applied consistently: the same file imports `OwnerConversationSummary`, `ProposalView` and `RenderedSegment` from `@/lib/agents/operator/{reads,proposals,render}` at `:8-10`, so three of the five wire shapes already cross that boundary as imports and two do not. Separately, `TurnStatusView = 'accepted' | 'running' | 'completed' | 'failed'` (`:65`) hand-spells the vocabulary that `schema.ts:7-13` owns as `TURN_STATUS` — the working rules forbid a string literal for a status where an authoritative TS file exists, and `reads.ts` types the same field as `TurnStatus`. The cost is already visible in the suite: `storedTurn()` and `turnBody()` fixtures are `Record<string, unknown>` (`__tests__/OperatorClient.test.tsx:66-93`), so a server-side rename would be caught by neither the client type nor the fixtures. **Smallest correction:** import `OwnerConversationTurn`, `OwnerConversationView` and `UnsupportedView`; keep only `TurnView` local if the polled route's projection is genuinely narrower than `OwnerTurnView` (it is — it drops `locationId`), and spell it `Pick<OwnerTurnView, 'id' | 'status' | 'failureReason' | 'segments' | 'proposals' | 'unsupported'>` so it cannot drift from `turns/[id]/route.ts:39-48`.

**F4 — `wording.ts` does not own the screen's words.**
Its first line reads "Every owner-facing string on the Operator screen, in ONE module." The shipped components contradict it in four files: `SummaryPanel.tsx` has essentially all of its copy inline (`:45` "This location is not connected to Google…", `:48` "Connect Google Business", `:54`/`:63`/`:72` the three block labels, `:75-76` and `:79-84` and `:92-99` the rules sentences, `:114` "As of"); `ProposalCard.tsx` inlines "This location" (`:71`), "Now" (`:85`), "After this change" (`:89`), "Cleared"/"Not set"/"Nothing" (`:198`, `:203`) and the five field labels (`:221-230`); `ReceiptView.tsx` inlines "Effective now."/"Scheduled." (`:24`), the differs-from-preview sentence (`:40`), "Still blocked" (`:46`), six record labels (`:57-71`) **and a second copy of the same five field labels** (`:80-84`); `OperatorClient.tsx` inlines "What would you like to change?" (`:591`), "Message" (`:686`), "Choose a location" twice (`:709-710`) and the scope-check sentence (`:816`). The duplicated five-label list is the concrete cost rather than a stylistic one: two renderers of one model, the class the axis checklist already ACCEPTED once ("Duplicate object renderers diverge…"), and they have *already* diverged on the fifth field — `ProposalCard` lists each sample reply (`:230`) while `ReceiptView` prints `${n} saved` (`:84`). **Smallest correction, pick one and be honest about it:** either export a single `VOICE_FIELD_LABELS` tuple from `wording.ts` and consume it in both renderers, then narrow the header to what the module actually owns (the state, failure and route-error vocabularies); or move the remaining copy in. Leaving the claim as written is the worst of the three, because the next author reads it and puts their string in the wrong place.

**F5 — the fetch decode is written three times.**
`getJson` (`:131-145`) owns the rule for reads: parse the body, lift `error` to `code`, map `404 + operator_disabled` to a `disabled` outcome, everything else to `error`. `post` (`:409-417`) re-implements it inline for the POST, and `writeProposal` (`:507-511`) re-implements it a third time, each with its own literal `'operator_disabled'` and its own `typeof body.error === 'string' ? body.error : null`. The three are not identical — only `writeProposal` also reads `body.proposal`, and only `post` distinguishes a thrown fetch as the retryable lost-response case — but the *session-ending* rule is the same rule in all three, and a fourth writer will spell it a fourth way. **Smallest correction:** a `postJson<T>(url, body?)` beside `getJson` returning the same `Fetched<T>` union plus the parsed body, so `operator_disabled` is decided in exactly one place; the two call sites then branch only on what is genuinely theirs.

**F6 — `apply.ts:169-173` documents a route that cannot be taken.**
The comment says "Reachable only for a non-pending row that fell through the pre-transaction guard", but a non-pending row has already returned: `:163` answers `applied` and `:166` answers `not_pending`, so control reaches `:171` only when the locked row is `pending`. And a locked `pending` row implies the unlocked `loaded.status` was `pending` too (proposal status transitions are pending→terminal only), which means the pre-transaction guard at `:81` already handled `!contractCurrent` and returned. The branch is therefore unreachable on every path — but it is not dead weight: `operation === null` is what narrows `operation` for `operation.parseInput` at `:242`, and without it the file does not typecheck. This is the checklist's "comment states a false mechanism" class, and the cost is the usual one: a reader who tries to construct the case the comment describes concludes the guard is wrong and deletes it. **Smallest correction:** replace the two sentences with what is true — "Unreachable: a row that reaches here is locked `pending`, so the pre-transaction guard already answered a stale contract. Kept because `operation === null` is the narrowing step 5 depends on."

**F7 — `proposals.ts` is now a repository plus one command.**
The module opens as "Proposal construction, persistence and supersession" and, at head, holds `buildProposalRows`, `insertProposals`, `supersedePendingProposals`, `mapStored`, four list reads, the unsupported entity's insert and two reads, `readProposalForAccount`, `lockProposalForAccount`, `markSiblingProposalsStale` — all of which are row-level — and then `declineProposal` (`:478-516`), which opens its own `sql.begin`, owns a lifecycle decision (an owner decline is a `rejected` row with a NULL reason, and a repeat click is idempotent) and returns a three-member `DeclineResult` union. That is the same kind of object as `applyProposal`, which got its own 437-line module. The asymmetry is the finding: a reader looking for "where an owner decision is recorded" finds one of the two commands by file name and the other only by grep, and `proposals.ts` grew 212 lines on this branch partly because of it. **Smallest correction:** move `declineProposal` + `DeclineResult` next to `applyProposal` (or into a `decide.ts` that owns both), leaving `proposals.ts` as rows-and-reads. The decline route's import is the only caller to update.

**F8 — the same 15-column projection, five times.**
`turn_id, id, operation, contract_version, label_kind, location_id, status, rationale, input, before, after, prepared_version_token, receipt, applied_at, failure_reason` appears verbatim at `:241-242`, `:267-268`, `:287-288`, `:389-390` and `:409-410`; the last two are this branch's. All five feed `mapStored` through the shared `StoredRow` type, so the list is not five independent decisions — it is one contract typed once and transcribed five times, and a column added to `StoredRow` that is forgotten in one SELECT produces `undefined` at the parse site rather than a compile error. **Smallest correction:** one nested fragment — `const proposalColumns = (db: Db) => db\`turn_id, id, …, failure_reason\`` — interpolated into the five queries; postgres.js composes nested tagged templates, and the repo already relies on that composition elsewhere.

**F9 — `computeVoiceVersionToken` buys nothing, and the drift it was written to stop is still there.**
The function (`version-token.ts:41-46`) takes `{ businessId, updatedAt }` and returns `{ businessId: input.businessId, updatedAt: input.updatedAt }` — an identity wrapper over the very object literal a caller must already build, with the two call sites in `apply.ts:214` and `:312`. Its module header (`version-token.ts:5-8`) names the problem it exists to solve: "the rule lived in a comment on the voice writer and in the literal `{ businessId, updatedAt }` object `buildProposalRows` writes". That producer was not migrated: `proposals.ts:85` still writes the literal, and `ProposalRow.preparedVersionToken` is still typed `Record<string, unknown>` (`:36`), so the one writer the docblock calls out is the one writer the new owner does not cover. **Smallest correction:** type `ProposalRow.preparedVersionToken` as `VoiceVersionToken` and build it at `:85` from the same helper, or delete the helper and keep the type as the single owner. Either is fine; what is not fine is a stated owner with an exempt producer.

**F10 — the Receipt prints internal ids where the owner expects an answer.**
`ReceiptView.tsx:66` renders `{receipt.actorUserId}` under the label "Applied by", and `:71` renders `{receipt.turnId}` under "Reference". The second is defensible — a correlation id labelled as a reference is what support asks for. The first is not the same thing: "Applied by" asks who, and a uuid does not answer it. Spec §6.5 names the *field*; it does not require the field's raw value to be the visible answer, and the codebase already has the two ingredients for a better one. Server side, the Apply transaction already reads the actor's row under the lock (`apply.ts:180-186`, `SELECT id FROM users WHERE id = … AND role = 'owner'`), so adding `name, email` to that projection and an `actorName` to the Receipt costs one column in a query that already runs, is written inside the mutation's transaction like every other Receipt field, and is correct forever because a Receipt is immutable. Client side, `useOwnerIdentity()` / `deriveDisplayName()` (`src/contexts/OwnerIdentityContext.tsx:39,58`) already exist in layout scope — but they describe the *viewer*, not the actor, so they are the wrong fix for a multi-owner account. **Smallest correction:** the server-side one; failing that, relabel the row so the uuid is presented as a record id rather than as a person.

**F11 — three composition roots, one hand-copied gate sequence.**
`turns/route.ts:32-54`, `proposals/[id]/apply/route.ts:42-65` and `proposals/[id]/decline/route.ts:23-33` each open with the identical sequence: `ownerOperatorEnabled()` → `requireWritableOwner(sql, request)` → `hasImpersonationCookie(request)` → `z.uuid()` on the route param (the two that take one) → the body-parse `try/catch` (the two that take one). Each file also carries its own prose explaining that the ORDER matters (`apply/route.ts:6-14`, `turns/route.ts:33-47`, `decline/route.ts:1-7`) — three copies of one policy statement. Invariant #12 lets entry points orchestrate, so this is not a violation; it is the duplication the protocol flags, and the branch tripled it. The same PR shows the right instinct one level down: `hasImpersonationCookie` was consolidated out of two private copies into `src/lib/admin/impersonation/cookie.ts:55` precisely because Run B would have made four. **Smallest correction:** the same move one level up — `requireOperatorWriter(sql, request): { ok: true; owner } | { ok: false; response }` in a small module beside the routes, holding the three gates and their comment; each handler then reads as one call, its own parse, and its own dispatch.

**F12 — one redundant declaration in `operator.css`, and a stylesheet outside three of the purity guards.**
On the question of literals, the file is clean: every colour, shadow, radius and font is a `var(--rw-*)`, there is no second border on a card, and the two 1024px/560px queries are within the Console's existing (admittedly ad-hoc) breakpoint spread. Two things are worth fixing. First, `.op-kv-value` (`:80-84`) sets `font: var(--rw-app-h3)` and then `font-family: var(--rw-font-display)` — the Console design doc states explicitly that the composite role tokens are declared on `.rw-console` alongside the `localFont` variables, so "`font: var(--rw-app-h1)` **alone** therefore renders Gabarito anywhere in the Console" (`docs/brand-asset-library/design-systems/console/DESIGN.md`, "And it reaches the composite roles"). The second declaration is a no-op that teaches the next author the shorthand cannot be trusted. Second, `design-token-single-source.test.ts` enforces its white-literal, `transition: all`, `(pointer: coarse)` and legacy-hex rules over a **hardcoded four-file list** (`:295-301`, `:308-315`, `:366-372`) that names only `_styles/*.css`; only the Island-colour/brand-font arm walks the directory (`:352`). `operator.css` is the second page-level stylesheet to land outside those three checks (`requests.css` set the precedent), so a future edit can introduce `#fff` or `transition: all` there with green CI. **Smallest correction:** delete the `font-family` line, and swap the three hardcoded lists for the `cssFilesUnder(AUTH_DIR)` walker that already exists in the same file.

**F13 — `UnsupportedRow` names two different things.**
`OperatorClient.tsx:67-71` declares `UnsupportedRow { id; request; context }` — the read shape, which server-side is `UnsupportedView` (`proposals.ts:322-326`). `proposals.ts:298-304` declares `UnsupportedRow { id; accountId; turnId; request; context }` — the INSERT shape. Both live in the Owner Operator feature, both describe `agent_unsupported_requests`, and they are not the same type. The repo's own convention in this feature is `…Row` for stored/insert shapes and `…View` for what a caller reads (`ProposalRow`/`ProposalView`, `StoredRow`/`ProposalView`, `OwnerTurnView`), so the client's name is the one that breaks it. Resolved for free by F3: importing `UnsupportedView` deletes the collision.

## Low-confidence appendix (reported, not counted)

1. **`repeated` on `ApplyResult`/`DeclineResult` has no production consumer.** Both routes ignore it (`apply/route.ts:79-80`; `decline/route.ts:44-46` says so in a comment); the only readers are `apply.test.ts:220,314` and `apply.integration.test.ts:258,459,567`. It is test-only production surface — but it is also the only observable that distinguishes the winner of a concurrent double-Apply, and deleting it would make the idempotency property untestable. Left alone; noted because "a field only tests read" usually is the finding.
2. **A third inline copy of the "latest `zernio_connections` row" query.** `reads.ts:428-436` joins through `businesses` for tenant proof; `admin/business-detail/queries.ts:144-151` and `dashboard/service.ts:367-374` each have their own. No canonical helper exists anywhere, so the branch could not have reused one; flagged only because the third copy is usually where someone should extract the first.
3. **A second location chooser on a screen that already has the shell's switcher.** `OperatorClient.tsx:708-724` renders one button per location; the nearest precedent points the owner at the existing switcher instead (`RequestsClient.tsx:405-415`, "Pick one from the switcher"). Deviation T3 #3 is the ACCEPTed reason the card exists at all, and the root approved the heading, so this is a UX-consistency observation for the design axis rather than a standards finding.
4. **Two new breakpoints.** `operator.css:115,120` introduce 1024px and 560px; the Console's documented thresholds are 768px (shell) and 1200px (the shared two-column rule for `.dash-pair`/`.recap-body`, which `.op-layout` structurally resembles). `console.css` already carries a long tail of one-off widths, so this is precedent-consistent noise rather than a defect.
5. **`readProposalForAccount` / `lockProposalForAccount` are the same query twice** (`proposals.ts:384-417`), differing only in `FOR UPDATE`. Two named functions is the right call over a `lock: boolean` parameter; F8's shared column fragment removes most of the duplicated text anyway.
6. **`conversation_read_failed` and `turn_read_failed` have no entry in `ROUTE_ERROR_WORDING`** (`wording.ts:111-126`), so both render the generic fallback. The fallback is explicitly designed for this, and neither code reaches a card body; noted only because the map is otherwise total over the codes the routes emit.
