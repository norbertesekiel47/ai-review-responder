## A1 — P2 / Medium — An unknown deployment lane enables the development-origin exception

**Location:** `src/lib/config/flags.ts:49–50`, consumed by `src/lib/config/admin-origins.ts:186`. **Confidence: 90%.**

**Assumption challenged:** absence of the exact value `VERCEL_TARGET_ENV=production` establishes that it is safe to admit every HTTP localhost/127.0.0.1 port. This is an approach objection to plan §5 D-1's two-state model. ADR 0026 D2 requires the exception to be inert in production; it does not require an unknown lane to receive development privileges.

**Concrete scenario:** disable access to Vercel system environment variables for the project, then create a production deployment. Vercel documents that system-variable exposure is a project setting; `VERCEL_TARGET_ENV` is available at build and runtime when exposed. The committed prebuild and startup assertions do not require this signal. With the signal absent, `isProductionEnvironment()` returns false and the terminal loopback branch returns true, even with an empty `ADMIN_APP_ORIGINS`. An `OPTIONS /api/admin/overview` carrying `Origin: http://localhost:5173` consequently receives 204 and permission to send `Authorization` on production. This is a supported configuration failure mode, not a claim that the current project's setting is disabled. [Vercel system environment variables](https://vercel.com/docs/environment-variables/system-environment-variables).

The same permissive result follows for empty or unrecognized values; the tests deliberately pin several of these to false at `src/lib/config/__tests__/flags.test.ts:69–82`, and the allowlist suite admits loopback with an undefined lane at `src/lib/config/__tests__/admin-origins.test.ts:156–167`. There is no fail-closed state for missing deployment evidence.

**Security consequence and limits:** this weakens the production origin boundary independently of the configured allowlist. It does not grant an admin identity: branch 4 still checks cookies on this SHA, and after #1185 the route gate must still verify the bearer. A non-browser caller can already omit Origin, so this is not a claim of token theft or an authentication bypass. The defect is granting a browser origin the exception that D2 specifically excludes from production.

**Smallest correction:** authorize loopback only after positively identifying a supported non-production lane, with an explicit local-development case. Missing/unknown signals in a production-mode process should deny the exception. Preserve staging's explicit allowance; substituting `requiresProductionConfig()` would incorrectly disable staging. Add the missing-signal production case to the existing predicate tests when implementing the correction. No new general environment-resolution framework is needed.

Runtime reading itself is supported. Also, the pinned Next version is 16.3.0, whose Proxy convention uses Node.js by default; the branch's Edge-safe import discipline does not establish whether its deployment signal exists. [Next.js Proxy runtime](https://nextjs.org/docs/app/api-reference/file-conventions/proxy#runtime).

## A2 — P2 / Medium — Request-time configuration failure has no controlled operational boundary

**Location:** `src/proxy.ts:125`, with the throw originating in `src/lib/config/admin-origins.ts:80–107`. **Confidence: 95%.**

**Assumption challenged:** throwing on every admin request is sufficient operational handling for invalid configuration, and its effective blast radius is just the separate Admin app. **Decision-level objection:** this challenges the approved plan's §2 unconditional, uncaught read and §5 D-8/D-11, and ADR 0026's outage rationale insofar as it endorses that operational result. It is not a spec-conformance finding. ADR 0026 D2's requirement that the parser throw on `*` can remain intact; letting that exception escape the exported proxy is a separate choice.

**Concrete scenario:** an operator supplies `https://admin.repworth.net/overview` instead of the bare origin and redeploys. The value is rejected correctly, but only once an admin request reaches line 125. `scripts/prebuild-assert-client-config.ts:17–19` validates client configuration, and `src/instrumentation.ts:63` validates core app configuration; neither exercises the new parser. The new deployment can therefore build successfully before its first admin request reveals the fault.

Every admin API request then throws before authentication or response creation, including no-Origin GETs, valid same-origin legacy mutations, and `/api/admin/impersonation/end`. `/admin/login` may still render while the administrative operations behind it are unavailable. The post-stamp at lines 140–147 never runs. The normal JSON refusal, `Vary`, and CORS response handling are replaced by framework/platform error handling; Vercel documents unhandled middleware exceptions as an HTTP 500 failure. Cross-origin script cannot read the intended API error contract without ACAO. [Vercel middleware invocation failure](https://vercel.com/docs/errors/middleware_invocation_failed).

**Operational consequence:** the unchanged deployment configuration makes each retry repeat the same failure. There is no parser-side backoff or once-only reporting, so unauthenticated requests and any client retries repeatedly enter exception logging. No automatic client or Vercel retry policy is assumed here. Re-reading the environment cannot heal it: changes apply to a new deployment, as the plan's rollback section correctly acknowledges. [Vercel environment-variable deployment scope](https://vercel.com/docs/environment-variables).

**Smallest correction:** retain unconditional validation, but catch `AdminOriginConfigError` at the CORS boundary and map it to an explicit fail-closed response, such as the existing 403 origin envelope with `Vary: Origin`, no ACAO, and `Cache-Control: no-store, private`. Report the configuration failure through a bounded, sanitized diagnostic; do not convert an invalid list to an empty list or log the raw rejected entry. This requires amending the approved proxy-rejection tests, not weakening the parser's mandated throw. A controlled 403 still denies the legacy API during misconfiguration; to prevent that outage, also reuse the parser in the existing prebuild assertion path so the bad deployment fails before promotion. No per-route CORS wrapper is needed.

**Wrapper and downstream-ticket implications:** the extracted `handleProxy()` body was confirmed byte-identical to the previous exported body. Mutating the returned `NextResponse.next()` is a supported way to supply response headers; `NextResponse.redirect()` also creates a mutable NextResponse. The wrapper does not add a second network request or buffer the eventual route response. Per-exit stamping would not repair the configuration exception either. The missing seam is error mapping before the response stamp. [Next 16.3.0 NextResponse implementation](https://github.com/vercel/next.js/blob/v16.3.0/packages/next/src/server/web/spec-extension/response.ts#L108-L140).

This failure remains ahead of #1185's bearer bypass and #1203's narrower cookie branch, including the permanent impersonation exception. #1190 must account for this boundary's refusal in addition to branch 4's historical errors; a platform-generated 500 does not provide its promised API envelope. #1192's page redirects do not restore API availability. These are consequences of A2, not four separate findings or objections to those tickets' locked designs.

## Low-confidence appendix

**Potential later loss of final response headers — below 80% as a defect in this branch; not a requested correction.** The wrapper stamps the proxy's response/control object, not a response returned after the route handler executes. A future route header writer or infrastructure-generated redirect/error can therefore fall outside its coverage. No current conflicting admin header writer was established. Next 16.3.0 appends its own framework Vary tokens, and Vercel now documents support for arbitrary Vary request-header cache keys, excludes Authorization requests from CDN caching, and requires cache-enabling directives. The inspected admin GET routes are dynamic. Accordingly, there is insufficient evidence to report the commonly asserted “Vercel ignores Vary: Origin” failure or to replace the wrapper with per-exit stamping. [Next 16.3.0 Vary handling](https://github.com/vercel/next.js/blob/v16.3.0/packages/next/src/server/base-server.ts#L1923-L1947), [Vercel CDN cache](https://vercel.com/docs/caching/cdn-cache).
