## Answers to the seven questions put to this axis

**Q1 — is `SnapshotPosting`'s four-field shape right? Is `correctionOwed` doing two jobs? Are `reasons` and `sentences` redundant?**

The shape is wrong in two independent ways, and `correctionOwed` is the one field that is right.

`correctionOwed` does exactly one job and does it in the only place that can: it is a predicate over the *whole account* (account default armed, **or** any active location override armed), and the snapshot deliberately projects operating rules for the selected location only, so the model provably cannot re-derive it. That justification is real, load-bearing, and the docblock states it correctly. Keep it, keep it named that, keep it server-computed.

`reasons` is dead weight — see F2. Nothing reads it. Its only effect is to put the internal enum vocabulary in the model's user message.

`sentences` is right to exist and wrong to be unconditional — see F3. The stated reason ("These are account DATA, not correction copy. Whether the model may say them is `correctionOwed`'s job alone") is a clean-sounding separation that buys nothing, because there is no second consumer of the un-gated data. What it costs is two of the five prompt rules, and it hands the model the exact prose it must not emit. The strongest evidence that it is wrong is internal: the sibling consumer on this same branch, `ProposalView.postingBlockSentences`, makes the opposite choice, and its card needs no rule at all.

So: **two fields, not four.** `{ correctionOwed: boolean; sentences: string[] }`, with `sentences` non-empty exactly when `correctionOwed`. That also makes `blocked` unnecessary, since rule `:82`'s "even when `snapshot.posting.blocked` is true" clause is the field's only reader.

**Q2 — is `ReadContext` a real concept or two values in a bag?**

A bag — see F9 — but a shallow one, and the seam it sits at is defensible. There *is* a real concept here: "the read-time facts a card's friction needs that the stored row cannot carry." The problem is that `status` is not one of those; `status` is on the stored row (`row.status`, parsed at `:513`), so calling it "read context" is a category error, and it collides lexically with the other member. The narrow fix is naming. The wider fix I considered and rejected: compute `corrected` in `mapStored` and thread a plain `string[]` down. That fails, because the third condition (`storedAfter.threshold !== null`) is only known after `parseStoredPolicyState`, which happens in both `cardFacts` and `restoreCardFacts` — threading the boolean would duplicate the parse. `policyCardFacts` is the correct convergence point for the three-condition test. Keep the structure; fix the name and the docblock's double use of "status".

**Q3 — deletion test on `posting-block-copy.ts`.**

**Passes clearly.** Three production consumers in three different layers (settings page, model snapshot, proposal card), and they are not variations of one call site — the settings page renders to a React list, `context.ts` serialises into an LLM prompt, `proposals.ts` builds a DTO field. Delete the module and five owner-facing sentences duplicate across three files with no owner, which is the precise drift the #1314 work and this branch both exist to prevent. The exhaustive mapped type is a real guard (a new `AutoApprovalPostingBlockReason` without a sentence is a compile error at one site rather than a blank `<li>` at three). This is not a pass-through: it is a copy-ownership seam with a type-level completeness property, and its `docs/directory/lib-reviews-responses.md:37` row states that correctly.

The `postingBlockSentences` *function* is the weaker half — it is `reasons.map((r) => COPY[r])` and one of the three consumers doesn't call it (F5). I would keep it, because two callers use it and it is where the ordering contract is written down, but the third consumer should call it or the function should go.

**Q4 — have five more rules broken the prompt constant?**

Yes, on findability, and the insertion point makes it worse than the count alone — see F10. Thirty-one flat bullets with no headings, and the new group was dropped in the middle of a related pair. The prompt is also the least testable layer in the system (a constant whose behaviour is exercised only by `prompt.test.ts` string pins and the LLM eval harness), so growth there should be under more pressure than growth in TypeScript, not less. Two of the five rules would not exist at all if F3 were fixed, which is the better lever: shrink the list by fixing the data shape, then group what remains.

One thing the branch got right and should keep: no owner sentence is spelled in the constant, with the reason stated (`operatorSystemPromptHash()` is recorded on every `api_costs` row, so a copy edit must not move it). That is a genuine, non-obvious architectural constraint and the comment at `:75-80` earns its lines.

**Q5 — two `<ul className="op-readiness">` blocks in `ProposalCard.tsx`.**

**Correctly separate, and I would not merge them.** They differ in three ways that matter: the render conditions are different (`requiresConfirmation && readinessBlockReasons.length > 0` versus `postingBlockSentences.length > 0`), the data is different (enum reasons mapped through `READINESS_WORDING` versus already-rendered strings), and the concepts are the two the whole branch exists to keep apart — "may the owner widen?" versus "does anything post?". Merging them into one list would be the exact conflation `posting-status.ts` and ADR 0034 spend their comments warning against, and a shared `<ul>` would silently imply one is a continuation of the other. The shared `className` is correct: it is a presentational class, and the two lists *should* look identical to the owner. If anything is off here it is that a hypothetical third such list would make the pattern worth a `<ReasonList>` component; at two, extracting would be an abstraction for a single shape with no second decision in it.

**Q6 — comment density.**

Measured on the added production lines only (tests excluded, `git diff --unified=0`): **98 code lines, 186 comment lines, 9 blank — a 1.9:1 comment-to-code ratio.** For comparison, the sibling review measured `posting-status.ts` at 1.4:1 and accepted it as matching its neighbours.

My judgement is **mixed, and the split is clean.** The comments that state a *trap* earn their keep and are the reason this subsystem has survived two reviews: the `settings.readiness` warning (`context.ts:185-193`), the "field by field, never a spread" rule with its stated failure mode, the hash/copy-edit constraint in `prompt.ts`, and the three-condition explanation in `policyCardFacts` are all things a reader cannot recover from the code and would otherwise break. Keep every one.

The comments that are going stale are the ones that state *facts about other files*: three line-number citations (F8), one mechanism that is false for six of seven callers (F12), one that names one of three callers (F7), and a long recitation of the ADR 0034 history that now appears in **five** places — `readiness.ts:7`, `settings.ts:1218`, `settings.ts:1238`, `posting-status.ts:28`, `context.ts:185` — plus the ADR itself, plus two doc pages. That is not density, it is a fact with seven owners, and `.claude/CLAUDE.md` names "one authoritative owner per fact" as the rule. The ADR is the owner; the five code sites should point at it in one clause each rather than each re-telling the paused-sale story. This branch has already corrected three stale comments (`9bfc3491f`, `c08e0e9c5`); a fact restated seven times is the mechanism that produced those.

**Q7 — `postingBlockSentences` as both a function and a field.**

Confusing, and cheap to fix — see F11. The tell is that the author had to alias at the import (`postingBlockSentencesFor`) to write the assignment `postingBlockSentences: postingBlockSentencesFor(...)` on one line. Rename at the definition, not the import.

## Approval bar

No structural regression, no file pushed past 1,000 lines, no ad-hoc branching bolted onto an unrelated flow, no boundary leak, no invariant violation. The central design decision — putting the fix in `mapStoredRows`, the single convergence point of all seven readers, so "pending only" becomes a row predicate an eighth reader cannot forget — is the right one and is the strongest thing on the branch. The new module passes the deletion test on its own merits. `policyCardFacts` gaining a required parameter rather than an optional one is the correct instinct.

**Not a block.** Land after F1 (one-line guard, removes a provably wasted query and an in-transaction read), F2 (delete a field with zero consumers) and F4 (the two reference pages need a split, not one more word). F3 is the largest quality win available here and I would push for it, but it is a redesign of a shape that is already behaviourally correct, so it is legitimately a follow-up if the branch is time-boxed — provided it is recorded, because the asymmetry between the two consumers is the kind of thing that ossifies. F5–F12 are one- to three-line corrections.

## Low-confidence appendix (deliberately not in the table)

- **`blocked` as a snapshot field.** If F3 is taken, `blocked` goes with `reasons`. If F3 is *not* taken, `blocked` has exactly one reader — the "even when `snapshot.posting.blocked` is true" clause of prompt rule `:82` — and I am not confident enough that removing it is safe while the un-gated `sentences` design stands, since the rule is doing real work against a model that can see the sentences anyway. Judge it as part of F3, not separately.
- **`SnapshotPosting.reasons.slice()` (`context.ts:204`).** The defensive copy is consistent with the file's field-by-field discipline, but `settings.posting.reasons` is a fresh array from `buildAutoApprovalPostingStatus` on every call and nothing mutates it. Harmless; noted only because the surrounding code is explicit about why every other line exists and this one is not.
- **`<li key={sentence}>` in `ProposalCard.tsx:207`.** Using the rendered sentence as the React key. Safe today (the five strings are distinct by construction, and the mapped type prevents a duplicate slipping in unnoticed), and it matches the precedent flagged in the sibling review at `status.detail.map((line) => <div key={line}>)`. Not worth changing; worth knowing.
- **The ADR 0034 history retold in five code comments.** Raised inside Q6 rather than as a finding, because each individual restatement is currently accurate and the "one owner per fact" rule is about facts that can drift, which these have not yet. The reason I would still collapse them: a seven-owner fact is how the three stale comments this branch already had to fix came to exist.
