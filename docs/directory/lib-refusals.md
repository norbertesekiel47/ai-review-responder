## `src/lib/`

### `refusals/`

The Refusal ledger — the two closed axes every `refusal_events` row is written
against, the one statement that writes it, and the one function that reads it
back (map #994, schema locked in #1001, table shipped by #1008 as
`supabase/migrations/116_refusal_events.sql`; `docs/context/refusal-ledger.md` → **Refusal**,
**Refusal source**, **Refusal category**, **Restraint tab**, **Coverage start**,
all LOCKED). The read half is #1014's `read.ts`, and it re-derives nothing:
#1002 decided there is never a backfill, so the ledger IS the history.

| File | What it does |
|------|--------------|
| `read.ts` | **(#1014)** The **Restraint tab**'s only data source and the ledger's only reader — `getRefusalLog(sql, scope, window)`, four sequential scoped queries behind one interface (coverage, entries, the scope-specific third — archived-location footnote in an account scope, archived periods in a location scope — and a separate `COUNT`), shaped after `getAgentTeamSummary`. Traps: (a) it selects NEITHER `all_refusal_codes` NOR `refusal_code` — the first is non-owner-facing under ADR 0023 and RLS filters rows not columns, so the omission IS the access control; (b) the account arm excludes archived locations with `EXISTS`, never a JOIN through `businesses`, which is the shape that multiplied one account-wide `autonomy_suspended` event per location in the parent effort; (c) the two scope arms are spelled out rather than composed, because `ci:tenant-scope` reads query blocks and each must carry its own tenant keys; (d) the REVIEW link's authority is the server-resolved `linkKind`, never the **Refusal category** — two lanes share `unsafe_content` and both carry a response subject; the other two links ARE category-keyed, which is safe only because their destinations are fixed pages identical for every lane that maps to them. Injected `Sql` (invariant #15). |
| `vocabulary.ts` | Single owner of the ledger's two closed axes: `REFUSAL_SOURCES` (**seven** lanes — `held_draft`, `auto_post_revoked`, `autonomy_suspended`, `ask_withheld`, `outreach_withheld`, `batch_halted`, `policy_gate_held`) and `REFUSAL_CATEGORIES` (**eight** owner-facing categories, ordered safety-bearing first so a surface forced to pick one for a mixed group picks the one that matters most). Also `REFUSAL_SUBJECT_TYPES` (the four things a Refusal can name; `autonomy_suspended` is deliberately absent — it takes NULL, which is a statement, not a missing value), the frozen literal `REFUSAL_VOCABULARY_VERSION` stamped on every insert, and **all seven lane vocabularies** — `AUTONOMY_SUSPENDED` (#1009), plus `ASK_WITHHELD`, `OUTREACH_WITHHELD_DISPATCH`, `OUTREACH_WITHHELD_RENDER`, `BATCH_HALTED` and `AUTO_POST_REVOKED`, landed together ahead of their write sites so slices #1010/#1011/#1012 could run in parallel without three branches editing this one file, and finally `HELD_DRAFT_REFUSAL_CATEGORY` + `POLICY_GATE_HELD_REFUSAL_CATEGORIES` (#1013). Each is `satisfies Record<Enum, …>` against the enum its lane already owns, so a member added upstream without a category decision is a compile error — `satisfies` demands every key whatever the value type is. Each array is the TypeScript VIEW of migration 116's matching CHECK, in its order; `vocabulary.test.ts` parses 116 and compares, which is why the migration stays the authority and no member is restated as a literal in a test. **Traps:** every import is `import type` ON PURPOSE — the Restraint tab (#1014) is a `'use client'` surface that will need this module, and one value import whose graph reaches a `node:` builtin drags it into the browser bundle silently (invariant #1's ESLint ban covers `src/app/**` + `src/components/**`, not this file); the module is PURE — no DB handle, no clock read, no flag read; ADDING a lane or category is **migration-bearing** (the column CHECK must admit it first, and a new lane also needs a C1 arm), REORDERING is presentation only (#995), renaming is forbidden outright — old rows keep the old spelling and #1002 ruled there is never a backfill. `| null` in a map's constraint appears ONLY where a null member exists — four of the seven maps omit it — and what that buys is that `null` is UNSPELLABLE in a lane where every code is a Refusal, NOT protection against an omission (`satisfies` already covers that); `null` MEANS "this code is not a **Refusal**" (`velocity_banked` is a deferral, and four of six halt reasons are the owner's decision or a deadline). The dispatch and render halves of `outreach_withheld` are SEPARATE constants over different enums and must stay so — they overlap on `lint_failed`/`moderation_high` because the dispatch gate re-lints and re-moderates at send time, and the eval pins that they agree. `BATCH_HALTED`'s key type is re-composed from `OwnerHaltReason | 'admin_halt' | SystemHaltReason` rather than importing `approval.ts`'s `LatchHaltReason`, which is private BY DESIGN (it spans actor classes; `approval.test.ts` pins the non-export) — so a reason joining either public union is a compile error here, while a bare literal added to the private union is caught by the eval instead. `HELD_DRAFT_REFUSAL_CATEGORY` is a single frozen literal rather than a map, because C4 makes that lane's `refusal_code` NULL biconditionally — there is nothing to key a map on. `POLICY_GATE_HELD_REFUSAL_CATEGORIES` carries all 22 `AutoApprovalBlockReason` members with SEVEN mapped `null`, and its companion `AUTO_APPROVAL_BLOCK_PRECEDENCE` is #1003's locked order over the remaining fifteen — an EXPLICIT member constant, never `REFUSAL_CATEGORIES` order, because #995 ruled a category reorder is presentation only and deriving rank from it would silently change future writes. This file also owns the one WRITE-TIME resolver, `resolvePolicyGateRefusal`: `null` vetoes the whole row whatever its position, an unmapped code throws, and the winner is returned inside the verbatim co-occurring set C5 requires it to belong to. Owner-facing LABELS remain #1014's — the boundary here is presentation, not "no functions". |
| `write.ts` | `writeRefusalEvent(tx, input)` and — since **(#1010)** — `writeRefusalEvents(tx, inputs)`, the SET-BASED arm beside it; every `refusal_events` row in the codebase is one of those two statements, on `audit/log.ts`'s model (one helper, one INSERT, the id minted by the writer, the DB client an explicit parameter — invariant #15, and it must be the caller's **deciding** transaction, never `@/lib/db/server`). No seam and no factory, deliberately: eleven call sites land across #1009–#1013 and nothing varies. It also owns the `REFUSAL_LEDGER_ENABLED` kill switch (read live per call inside the body, so a mid-process toggle takes effect at once; off ⇒ return before touching the transaction), the kill-switch warning — one per **disabled episode**, NEVER per process: the latch clears when the flag is next observed enabled, so a second outage in one process still warns. The **structured log line is the durable signal**, emitted FIRST and OUTSIDE the Sentry guard, because `captureMessage` returns on QUEUE rather than delivery and swallows transport failures internally — so no latch on it can detect a real delivery failure (`WARN_RETRY_COOLDOWN_MS` covers only a synchronous SDK throw; `resetRefusalLedgerWarningForTests` clears both pieces of state). **Since (#1105) a SECOND signal sits beside it, and the two are not variants of each other:** `noteUnmappedBlockReasons(unmapped)` reports that a block reason has no entry in `POLICY_GATE_HELD_REFUSAL_CATEGORIES` — a defect in the map, never a ledger gap — at Sentry level `error` (against the kill-switch warning's `warning`), tagged `fault=unmapped_block_reason`. The capture MESSAGE is the constant `UNMAPPED_BLOCK_REASON_MESSAGE` and the codes ride `extra` — verbatim, in input order, duplicates kept — because Sentry groups by message and an interpolated code list opens one issue group per distinct set, scattering one fault and defeating per-issue throttling. Its latch is per **CODE** and per **PROCESS**, deliberately unlike the episode latch named above: a map hole does not end when an operator flips the flag back, so it never re-arms, and it keeps its own `resetUnmappedBlockReasonSignalForTests`. It is BOUNDED at `UNMAPPED_SIGNAL_CAP` distinct codes, because the keys are exactly the values the type system did not vouch for; reaching the cap emits one `fault=unmapped_block_reason_overflow` marker naming no code, then silence. It is a pure TRANSPORT — **the caller owns the precondition** and hands it already-unmapped codes; the `Object.hasOwn` test lives in `unmappedBlockReasons`, beside `wouldRecordRefusal` in `worker/jobs/response-generation/persist.ts`, because the lane suite mocks this module and a membership test in here left four of its five cases unable to tell a signalled hole from a handed-over healthy set. **The fault CLASS is not closed codebase-wide** — five lanes index a category map directly (`MAP[reason]` → `undefined`, no throw) and with the ledger off raise the ledger-dark line instead, claiming a gap for a row 116 would reject; different mechanism, separate ticket. **Trap:** both transports carry ONE joined string — `createWorkerLogger` runs object args through `sanitizeAnalyticsProperties`, which DROPS ARRAYS silently, so a `codes: string[]` value logs as an absent key. And `occurredAtFragment` — two arms, one statement. **Traps:** the `ON CONFLICT (refusal_source, subject_id) WHERE subject_id IS NOT NULL` predicate is re-spelled **byte-for-byte** from `refusal_events_subject_uniq` and may NOT be parameterised — a bind parameter inside `ON CONFLICT … WHERE` defeats partial-index inference (invariant #2), and the second write then raises 23505 inside the transaction that IS the decision; `DO NOTHING` is REQUIRED for the same reason, and because the index is PARTIAL, `autonomy_suspended`'s NULL subject is never deduplicated (two suspensions stay two Refusals); `occurredAt` is REQUIRED with a `'transaction_time'` sentinel and no default — an optional field lets a late-deciding lane record persist time silently — and no site may round-trip `transaction_timestamp()` back through a JS `Date` (postgres.js truncates microseconds, #520, and those digits carry the `account_audit_log` join #1006 accepted instead of a `suspension_event_id` column); the INSERT is caught for **Ledger attribution** and RETHROWN AS THE SAME INSTANCE (#1083) — a 116 CHECK violation is still a writer bug and still aborts the decision that names it, and catch-and-rethrow is the PROPAGATING side of "facts propagate, observations swallow" rather than an exception to it; the Sentry warning around it is genuinely swallowed, and so is the attribution capture itself. **`captureLedgerWriteFault(error, lane, extra)` is that attribution** — module-private, never exported, exactly two callers (both write arms), which is what covers all seven lanes without one call site changing and makes the omission that produced #1083 unspellable. On the SET arm the guard starts at the ROW MAP and **not** at the INSERT, because `toISOString()` on a type-valid `new Date(NaN)` and `uuidv7()` both throw during materialization; its lane string is the distinct sources sorted and comma-joined, computed in the `catch` from `inputs` and never from `rows`, which may not exist when materialization is what failed, and `row_count` reads `inputs.length` for the same reason. **BOTH CAPTURES CARRY A `fault` TAG** — `fault=ledger_write` here, `fault=ledger_vocabulary` on `persist.ts`'s wrapper — because without one the two classes are byte-identical in every tag on the `policy_gate_held` lane, and a Sentry alert rule cannot filter on `extra` (#1083 round 1; the `fault=` convention is this module's own and `beta-launch-alerting.md` states it as a rule). **`extra` IS A CLOSED KEY SET ON BOTH ARMS, asserted by exact sorted key list and never by presence** — single-row `{ subject_type, subject_id, account_id, business_id }`, set arm `{ row_count, account_id, account_count }` — because a presence-asserted payload accepted a smuggled unbounded `refusal_codes` with the whole suite green. Neither arm repeats its lane into `extra`: the tag carries it, and a tag is filterable where `extra` is not. **THE TWO ARMS PROTECT `uuidv7()` BY DIFFERENT MECHANISMS, and reading them as one is how a later edit breaks the weaker case.** The SINGLE-ROW arm interpolates `${uuidv7()}::uuid` inside the tagged template, so it evaluates when the tag function runs — already inside the `try` — and hoisting it to a `const` above the `try` silently moves it out; one eval case exists solely to fail on that. The SET arm calls `uuidv7()` in the `rows` map instead, and it is inside the guard ONLY because the guard was moved to start at the map. Neither fact implies the other. It does not validate C1–C5 (the database owns those five facts, #1001) and it does not read. **The set arm (`writeRefusalEvents`)** exists for one lane and one reason: `ask_withheld` can propose up to `MAX_DATA_ROWS` (5,000) mapped Refusals in one build, and a loop over the single-row helper would hold the per-Business advisory lock AND the batch row lock across 5,000 sequential round trips behind the `db/admission.ts` chokepoint. It lives HERE and never in a lane module (#1001 owns the statement); it follows `commitAskDecisions`'s `jsonb_to_recordset` idiom but deliberately does **not** copy that function's affected-row-count assertion — under `ON CONFLICT DO NOTHING` a subject stored by an EARLIER call legitimately lowers the count and the throw would land inside a decision transaction. An EMPTY input issues no statement at all (an INSERT of zero rows is not a decision), and the check runs BEFORE the kill-switch read so a build that withheld nothing raises no disabled-ledger warning. Its `ON CONFLICT` clause is re-spelled byte-for-byte from the single-row arm and `write.test.ts` compares the two out of the module source — that comparison is the compensating control for the second spelling, so neither may be "tidied" into an interpolated constant. Per-row `occurred_at` rides the JSONB payload as ISO text with NULL standing for the `'transaction_time'` sentinel, resolved by `COALESCE(…, NOW())`. |
