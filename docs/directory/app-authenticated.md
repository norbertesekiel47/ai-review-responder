| `dashboard/requests/page.tsx` | **(#544)** "Requests" — the owner-facing Solicitation surface. Server component so the `SOLICITATION_WATCH_ENABLED` gate stays server-authoritative (invariant #13): `notFound()` when off, then renders `RequestsClient`. |
| `dashboard/requests/RequestsClient.tsx` | **(#544)** Client island: fetches `GET /api/dashboard/solicitation/batch` for the selected location, polls every 2s while a batch is `building` **or while a per-ask regeneration is in flight** (#860; 5-minute ceiling → `stalled`), POSTs `batch/reviewed` once a built report renders, and renders one screen per phase (loading / ready / stalled / error / `gone` on a mid-session 404). Phase is keyed by the location scope it was fetched for, so a superseded response never renders against the switched-to location. **Exposes `refetch(mode: RefetchMode)` — NOT a bare `retry()` (#860 round-1 R1/R2).** `RefetchMode` is `Exclude<LaneRefresh, 'none'>`, so `refetch('none')` is a `tsc` error rather than a silent no-op: `'none'` is a member of the PANEL's `LaneRefresh` vocabulary and is consumed in `onLaneChanged`, which skips the read entirely and never reaches `refetch`. Of the two the hook does take, `replace` sets `phase: LOADING` (terminal verbs: approve, halt) and `in_place` bumps the fetch attempt WITHOUT touching `phase`, so the read is real and server-authoritative while `ApprovalPanel` stays mounted. A regeneration is **non-terminal** — it returns to the same approvable panel — so settling it through `replace` unmounted the panel and silently re-selected every deselected ask. Both the `ready` and `stalled` arms return `BuiltBatch` at the same position for a built view, or that fix would reintroduce the unmount. |
| `dashboard/requests/ApprovalPanel.tsx` | **(#629; #872 adds the withdraw lane)** Client island for the owner approval lane, rendered above `BatchReport` only when `view.sendLane !== null` (invariant #13 — the browser learns the flag from the response shape, never a `NEXT_PUBLIC_*`). Owns exactly four things: which asks are excluded (keyed on **`askId`**, never `outreachId` — a regeneration mints a new outreach id, and keying on it silently re-selected a deselected contact), the armed-withdraw state (`armedAskId`, #872 — ONE pending confirmation at a time, disarmed on a refetch that drops the row; a render-time adjust, NOT an effect, because `react-hooks/set-state-in-effect` is `error` repo-wide — deviations D4a), the in-flight POST, and the error copy — it never mutates the view it was given, and `onChanged(message, outcome, refresh)` routes the refetch through `RequestsClient`'s `refetch(mode)` so that path keeps one owner. **The third argument is the terminal/non-terminal distinction, and it lives on the WRITE rather than in the parent (#860 round-1 R1/R2):** approve/halt pass `replace`, regenerate and withdraw pass `in_place` (the panel must survive its own refetch or `excludedAsks`, `pendingRegen` and `armedAskId` die on unmount), the settle report passes `none`. Every future lane verb owes the same declaration, which is why it is a required field rather than an optional one. The withdraw write ANNOUNCES the server's `remainingLive`/`closed` — never a client-side subtraction, because the client cannot see an in-flight row. Three exhaustive switches with no `default`: `panelMode` (one arm per **Batch state**), `panelCopy`, and `actionVerb`; the `askDisplay` facet gained `withdrawable` (post-approval `veto_window`/`approved`/`sending`), which renders `WithdrawableAskList`. The list markup lives in `AskList.tsx`, the two buttons in `ApprovalActions.tsx`, and the four writes (approve, halt, regenerate, withdraw) in the sibling `lane-writes.ts` (**#886** — extracted when this file crossed 1,000 lines; three of the four hooks stay file-local, `useLaneWrites` does not), so the component itself is state + composition. **`toRows` is the ONE place in the lane that touches an `AskAttemptView`, and the D6a rule it enforces is CONDITIONAL: it drops every `redacted` attempt outright, and carries `subject`/`body` through for the unredacted arm — because the owner must READ what they approve (`user_visible_behavior[0]`), and the 15-minute veto window is an undo rather than a review window precisely because they already have.** An earlier revision projected the copy away for *every* attempt, so the owner approved messages they could not see; that shipped because the check verified the dangerous thing was absent and never that the required thing was present (round-1 review; deviation D13). `AskRowView` has no redacted arm, so reading `attempt.subject` without narrowing past the guard is a `tsc` error rather than a matter of care; held rows surface only as a reason chip plus `sendLane.moderationWithheld`. **No EDIT affordance anywhere — D22 stands and the copy says so** ("You can ask for a new version of any message, but you cannot write one yourself"). The **regenerate** affordance now exists (#860): a per-ask control on `rendered` rows in `approvable` mode only, absent on withheld rows and once approved, disabled while deselected, while any regeneration is in flight, or once the ask has spent its 3/day budget. The **withdraw** affordance (#872, **Ask withdrawal**, ADR 0021) is the post-approval counterpart: a per-ask `Withdraw` control on live rows only, in `withdrawable` mode only. The owner's two verbs became four — approve, exclude, ask for new bytes, withdraw — and never write bytes. |
| `dashboard/requests/lane-writes.ts` | **(#886; the section is #629's, moved)** The approval lane's WRITE seam, split out of `ApprovalPanel.tsx` when that file crossed 1,000 lines (982 → 1,109; only ~94 of them #872's). Owns `useLaneWrites` — approve, halt, regenerate, withdraw over ONE settle path — plus `postLaneAction`, the `LaneStatus` union taken from the four route result types (so a new refusal is a `tsc` error here rather than silent generic copy), `LANE_REFUSAL_COPY` + `NOT_REGENERABLE_COPY`, the four `Announce` sentences, and `countPhrase`. **`LaneWriteOutcome` and `LaneRefresh` are exported from HERE, not from the panel** — they are the write's vocabulary, and `RequestsClient` imports them from here. Traps: (a) the seam is the four verbs and nothing else — `useExcludedAsks`, `usePendingRegeneration` and `useArmedWithdrawal` stay in the panel because they are about what is on SCREEN, not what is on the WIRE; (b) nothing here refetches — `onChanged` is the parent's cue and the `LaneRefresh` each verb passes says which kind (`replace` for the two terminal verbs, `in_place` for the two that come back to the same panel); (c) `countPhrase` moved WITH the section because the panel's prose reads it too, and leaving it behind would make this module import from its own importer. |
| `dashboard/requests/AskList.tsx` | **(#629; #872 adds the third form)** The approval lane's ask list in its three forms — `SelectableAskList` (per sendable ask: a checkbox while the owner is still choosing, plus — since #860 — the **Ask regeneration** control and its "N of 3 today" counter), `WithdrawableAskList` (**#872**, post-approval: per `rendered`/`queued` row a `Withdraw` control behind an inline two-tap confirm — "Withdraw this message?" [Withdraw] [Keep], both `btn btn-secondary` since `.btn-danger` lives only in `settings.css`, which the requests route never loads (deviations D4b); accessible names carry the contact name (WCAG 2.5.3); ABSENT on `sending`/`sent`/`withheld`/`failed`/`unknown` rows) and `AskList` (names and statuses on the read-only halted / nothing-left-to-send screens; a closed **Settled batch** shows a count, not a list) — plus the `AskRowView` row type and the `delivery_status` → label map, keyed on the union so a widened vocabulary is a compile error. **Takes `AskRowView` and never `AskAttemptView`**: it sits downstream of `ApprovalPanel`'s `toRows` choke point, so a rendered subject or body is not reachable here (D6a) — widening these props is exactly how that guarantee would be lost. Three SIBLING components rather than one `selectable`/`withdrawable` flag on `AskList`: the read-only list has no toggle to call, no exclusion set to read, no regenerate handler and no withdraw handler, so it is structurally unable to offer a control. **#860 put the regenerate affordance HERE, on the row, not in `ApprovalActions`** — it is per-ask, so it belongs beside the per-ask checkbox; `ApprovalVerb` was never widened. `AskRowView` gained `askId` and `attemptNo`: the exclusion set keys on `askId` (a regeneration mints a NEW outreach id, and keying on that silently re-selected a deselected contact), and `attemptNo` is how a landed regeneration is told from one that settled without changing anything. The control is ABSENT on withheld rows and once approved, and disabled while deselected, while any regeneration is in flight, or once the ask has spent its budget — an ask ABSENT from `regenBudgets` is UNKNOWN, which renders no counter and leaves the control ENABLED (fail-open). Its accessible name is built FROM its visible label (WCAG 2.5.3), so the in-flight swap is announced. |
| `dashboard/requests/ApprovalActions.tsx` | **(#629)** The owner's two **batch-level** verbs — approve (whose label carries the live count) and stop. (The owner has three verbs since #860; the third, **Ask regeneration**, is per-ask and renders on the row — see below.) It renders the lane's *verb* buttons; the exclusion checkbox is `SelectableAskList`'s, so this is **not** the only file in the lane that renders a control — an earlier revision of this row claimed it was and rested D22's checkability on that false exclusivity (round-1 review). `ApprovalVerb` is `'approve'` or `'halt'`; WHICH verb a state offers is a lifecycle question answered upstream by `actionVerb` in `ApprovalPanel`, exhaustive over the panel mode with no `default`, so a new mode must state whether it is actionable. **No EDIT affordance — D22 stands** and the panel copy says so out loud ("You can ask for a new version of any message, but you cannot write one yourself"). The **regenerate** affordance now exists (#860) but is NOT here: it is per-ask and lives on the row in `SelectableAskList`, so `ApprovalVerb` was never widened — an earlier revision of this row predicted the opposite. Props are `busy` AND `unavailable`, and the split is load-bearing: `busy` drives the label ("Approving…"/"Stopping…") as well as `disabled`, so passing `busy || regenerating` would have made the button announce an act that is not happening while the owner waits on a regeneration. `unavailable` disables without claiming. |
