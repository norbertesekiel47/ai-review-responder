## `src/lib/`

### `agents/operator/`

**Owner Operator** — the turn pipeline behind `OWNER_OPERATOR_ENABLED` (Run A),
plus Apply and Decline (Run B), policy consequences and confirmation (Run C),
durable recovery (Run D), and receipt-based Restore and refusals (Run E).
The sibling `agents/` rows (`run-spine.ts`, `read.ts`) stay on
[lib-platform.md](lib-platform.md); this folder sits here because both default
pages are at the 3,000-word cap. Glossary: `docs/context/owner-operator.md`;
spec of record: `docs/roadmap/2026-09-11-owner-operator.md`.

| File | What it does |
|------|--------------|
| `consequence.ts` | Pure `simulateRule`: excludes imported reviews, uses the shared star threshold and platform-cap resolver, counts eligibility and hold reasons per location/UTC day, and returns the scope's daily histogram and busiest-day count. Review timestamps and UTC day keys are supplied by server reads; no database or model call occurs here. |
| `policy-state.ts` | One-statement policy snapshot: full effective dials, opaque row tokens, active locations and a 30-day review cohort with confirmed ingestion origins. Maps that fixed cohort through `simulateRule`, preserving location overrides. The retained-veto read counts approved auto-policy drafts against their latest immutable approval grant, locking only audit rows; Apply supplies the account lock. |
| `schema.ts` | Strict model-output contract with eight ordinary proposal inputs, scope-only Restore preparation and closed refusal reasons; no model fields for counts, approval, confirmation, inverse state or receipts. Owns turn/proposal/failure vocabularies, full voice and policy state, frozen consequences and readiness reasons, and voice/policy Receipt schemas. `parseReceipt` preserves legacy voice receipts and returns `null` for an un-applied row. |
| `catalog.ts` | Operation registry: three reads, four voice proposables, four policy proposables, `restore_last` preparation and capability capture. Proposables remain contract version 1. Owns per-operation inverse mapping, changed writer fields, policy previews, shared-writer patches, final-state exposure, confirmation phrases and descriptions. Trusted inverses preserve nullable tone, absent rows and exact prior policy dials without expanding ordinary model inputs. |
| `operation-inputs.ts` | Strict input schemas shared by the catalog and model-output validator, keeping operation shapes consistent without a catalog/schema import cycle. Policy value domains are checked against the shared settings writer. |
| `restore-inputs.ts` | Strict server-owned Restore provenance envelope and pure inverse validation against a same-account, same-scope applied source Receipt, operation and contract. Resolves one immutable receipt without recursively following undo history. |
| `restore.ts` | Shared button/worker Restore preparation. Locks the stored location then account with `FOR NO KEY UPDATE`, revalidates the actor, selects the latest exact-scope receipt under locks, prepares current versions/consequences, and reuses one pending proposal per source/version without reparenting its owning turn. Never applies settings. |
| `refusals.ts` | Six closed refusal reasons with server-owned owner wording and ledger lane mapping. Content reasons bind the stored location; policy reasons bind the account. All use the owner-safe `request_not_allowed` category. |
| `refusal-completion.ts` | Mints a distinct subject per refusal after the winning completion fence and writes through the single refusal ledger writer. Duplicate reasons reject before writes; errors propagate so the caller rolls back completion, proposals and refusals together. |
| `render.ts` | The **Pasted-review scrub**, the semantic validator (invented counts and completion claims over `text` AND `question`, dangling refs, scope rules — returning the proposals it parsed), `materializeReply` (the write-path transform: `status_ref` → a frozen value, `proposal_ref` → a stored id, scrub notice prepended), and the deterministic read-path renderer. |
| `context.ts` | `buildSnapshot`, plus the reusable `readPosted7d` and `RECENT_COMPLETED_DAYS`. The one star-band query (pending_approval, held drafts and soft-deleted reviews excluded, grouped by location and star). The `Snapshot` type has no field that could hold review text, response text, a reviewer name — or `sampleResponses`. **(#1352)** `projectPostingBlock(settings)` adds `posting: SnapshotPosting` — `blocked`, `reasons`, `sentences` (from `posting-block-copy.ts`, the one copy owner) and `correctionOwed`, read FIELD BY FIELD so a new `AutoApprovalPostingStatus` field cannot ride in on a spread. `correctionOwed` is the sole suppression switch — blocked AND the account default or ANY active location override is armed, the settings page's own test (`AutoApprovalClient.tsx:705`, armed-override shape at `:684-686`) — and the model cannot re-derive it, since the snapshot projects **Operating rules** for the selected location only. `settings.readiness` stays untouched: the Posting block rides beside readiness, never derived from it. |
| `prompt.ts` | `OWNER_OPERATOR_SYSTEM_PROMPT`, its version label (`OWNER_OPERATOR_PROMPT_VERSION`) and SHA-256 hash (recorded on every `api_costs` row), and the untrusted-data envelope builder. **(#1352)** The **Posting block** rules make `snapshot.posting.correctionOwed` the server's decision about UNSOLICITED wording: true ⇒ say the account is not set up to post automatically and state each `snapshot.posting.sentences` string verbatim, inventing nothing; false ⇒ volunteer nothing even when `posting.blocked` is true, though a direct owner question may still be answered from those same sentences verbatim. The model re-derives neither `correctionOwed` nor account-wide armed state. A block never withholds a proposal, and a suspended account default is stated first — the block sentence after it follows those same two branches (unprompted only when `correctionOwed`, otherwise only in answer to a direct question), stated at most once, with neither wording replacing the other. Separate from all of that, an always-on wording rule — say "set to post", never "posts" — is about promise level, not the block, and is gated on nothing. No owner sentence is spelled here: the constant is hashed, so copy lives in `posting-block-copy.ts` and an edit to it cannot move the hash. |
| `model-call.ts` | One cost-guarded `owner_operator` call with at most one validation retry. Every attempt is billed and audited — including the invalid one. Transient and budget errors propagate; only the `api_costs` write is best-effort. |
| `turns.ts` | Turn WRITES: creation, claim/predecessor protocol and fenced terminal transitions. Claim release binds the current token to the exact outbox attempt; healthy predecessor waits refresh liveness atomically, transient releases do not, and failed outboxes reconcile on yield. Poller exhaustion locks the stored tenant/turn identity without blocking completion: accepted or expired claims fail atomically, live/contended claims keep a recoverable outbox. Owner reads live in `reads.ts`. |
| `reads.ts` | The account-scoped owner READS: `getTurnForOwner` (the polled turn) and `getConversationForOwner` (the transcript, bounded to the 50 most recent turns, plus the live summary panel — `null` when there is no turn to scope it to, never a zeroed one). Proposals come from one batched `listProposalsForTurns`, never a query per turn. **Run B added `?locationId=` and `connectionStatus`**: the caller-supplied location scopes the summary ONLY when the conversation has no turns yet (the latest-turn scoping still wins whenever a turn exists), and an owner with no conversation at all receives the empty view with a scoped summary rather than a 404 — an id that is not an active member of the account scopes nothing and the summary stays `null`. |
| `proposals.ts` | **Proposal** and **Requested capability** construction and persistence, account-scoped reads, row locks, and idempotent actor-recording Decline. Policy preparation freezes full before/after consequences, row tokens and expansion-readiness reasons; the owner view derives confirmation from stored dials. Supersession matches operation and nullable scope across earlier turns. Apply invalidation follows the changed token domain: voice siblings on one location, policy siblings on one location, or all account policy siblings after an account-default write. **(#1352)** `mapStoredRows` is the ONE place all seven reads converge, so it reads the account-wide **Posting block** there — once per batch via `getAutoApprovalPostingStatus`, sequentially (one pooled connection, no `Promise` combinator). TWO cases skip that read, each passing a neutral `{ blocked: false, reasons: [] }`: an empty read, which returns before any statement at all; and a non-empty batch in which no row is `PENDING` and none is `APPLIED` — a rejected, stale, superseded or failed page — because those two statuses are the only ones the card predicates answer. It yields TWO fields, both derived at READ time from current account state unlike the frozen `readinessBlockReasons`, because they gate nothing and a stale copy could only be a false or missing warning. `ProposalView.postingBlockSentences` is the PENDING card's pre-Apply warning: non-empty only when the account is blocked, the row is still `PENDING`, and its stored `after` is armed — a proposal that turns auto-posting OFF is already truthful. `postingBlockNowSentences` carries the same sentences on an APPLIED armed rule, so the card cannot say "Active rule / Effective now" while the account cannot post; it states the account as it stands NOW and never repaints the Receipt beside it. The two share the blocked-and-armed test and differ only in the row status they require, so they are mutually exclusive by construction. Both are predicates on the ROW, not a choice of reader, so an eighth reader cannot forget either; a voice proposal claims nothing about posting and always carries `[]` for both. `postingBlockNowSentences` is optional on `ProposalView` but required on `CardFacts`, so a server branch that forgets it fails to compile while a view built before the field existed still renders a card. |
| `authorize.ts` | Worker step 3: re-resolves actor, subscription posture and location from the database before any snapshot is built. |
| `flags.ts` | `ownerOperatorEnabled()` — the single reader of `OWNER_OPERATOR_ENABLED` (the **Operator flag**). Server-only; no `NEXT_PUBLIC_*` companion (invariant #13). |
| `apply.ts` | Apply dispatches from the stored token domain after checking the contract. Voice locks the business before the proposal; policy locks the account before the proposal. Both revalidate the actor and compare current/prepared/expected tokens before a shared-writer mutation and atomic Receipt. Policy expansions require readiness and an exact stored-state phrase before mapping to the settings writer's `standard` confirmation; mismatch leaves the proposal pending. Policy receipts include actual dials, consequences over one pre-write cohort and the immutable-grant veto count. Repeated Apply returns the stored Receipt; thrown post-write failures roll back the transaction. |
| `version-token.ts` | Strict voice and policy version tokens, their JSONB parser and structural equality. Policy tokens distinguish absent rows and include the account default in every location token. Timestamps remain opaque text to preserve PostgreSQL microseconds. |

### `demos/`

The rest of `src/lib/demos/` is inventoried here rather than on [lib-platform.md](lib-platform.md), which sits at the 3,000-word cap; that page's Pages-table row records the move (#1104).

| File | What it does |
|------|--------------|
| `generator.ts` | `generateDemoResponses(reviews, context)` — calls `generateResponse` in `demo` mode for each review. |
| `types.ts` | Demo types (`DemoRequest`, `DemoResult`); `DEMO_GENERATION_STATUS` (= migration 032's CHECK set, pinned by `generation-status-contract.test.ts`); `NO_DEMO_SENTINEL_STATUS` (`'skipped'`), a never-persisted `/onboarding/demo` view state (#1104). |
| `fallback-content.ts` | `getFallbackDemo(category)` — curated fallback reviews + responses for the demo when live content is unusable; normalizes a free-text category to a canonical key, every key currently sharing the general-business fixture (`__fixtures__/fallback-source-reviews`). |
| `fetch-reviews.ts` | `fetchSerpApiReviews(placeId)` — up to 15 reviews via `SerpApiSource`, or `MockReviewSource` when `MOCK_EXTERNAL_APIS=true`; fails fast at module load if `SERPAPI_API_KEY` is missing outside mock mode. Extracted from `generator.ts` so the worker does not choose the source. |
| `generate-responses.ts` | `generateResponsesForReviews(sql, reviews, businessContext)` — `Promise.allSettled` over `generateResponse` in `demo` mode (or `generateMockResponse`), mapping a failed review to `null` and returning success/failure/cost/duration metadata. Extracted from `generator.ts`. |
| `lifecycle.ts` | Demo-row state machine over `onboarding_demos` / `prospect_demos`: `claimDemo` (queued → running CAS, >5-min stale-running reset; returns `claimed` / `already_terminal` / `not_found` / `reset_to_queued` / `race_lost`), `completeDemo` (row + outbox in one tx; the 23505 race-loser archives itself and closes its outbox), `failDemo`. Called by `DemoGenerationWorker`. |
| `select-qualifying.ts` | `selectQualifyingReviews(reviews, opts)` — picks ≤3 demo reviews: `newest` (first three) or `positive-with-moderate-tail` (rating ≥3; a substantive 5-star anchor, up to two 4-stars, one trailing 3-star; returns `[]` when no ≥4 anchor so the caller falls back to curated content). |
| `view-tracking.ts` | **(#1369)** `recordDemoView(demoId)` — fail-open, ONE atomic Lua eval (INCR + SET + SADD; cache Upstash instance, never the queue Redis) called from the public demo viewer page; never throws, reports via `reportCaughtError` on failure. `drainPendingDemoViews()` — a second Lua eval per pending demo atomically GETDELs its counter AND its last-viewed timestamp and SREMs it from the pending set, for `DemoViewFlushPoller` (`worker/background/pollers/`) to batch into Postgres; EVAL, not MULTI/EXEC, is the atomicity mechanism (module doc explains why), which is also what rules out the race a split GETDEL/GET/SREM sequence had. |
