## `worker/`

### `worker/ingress/` — Inbound Webhook Handlers

Each handler is registered as a Fastify route in `worker/index.ts`. **Provider webhooks** all follow the same pattern:

1. Verify the request signature.
2. Write an `inbound_events` row first (deduplication — rejects duplicate event IDs).
3. Execute business logic (update DB, write to `job_outbox`).
4. Return `200` quickly.

**`unsubscribe.ts` is the one exception and follows none of it** — it is a
*recipient-facing* route, not a provider webhook. There is no signature to verify
(the mail client is anonymous), no `inbound_events` dedup (idempotence comes from
the token's own `redeemed_at` claim), and no `rawBody`. It is also the only ingress
route **exempt from the rate limiter**, because §9.2 forbids throttling a statutory
opt-out. Do not "fix" it to match the table above.

| File | Route | What it does |
|------|-------|--------------|
| `shared.ts` | *(utility)* | `claimInboundEvent()`, `markInboundEventProcessed()`, `markInboundEventStaleIgnored()`, `markInboundEventFailed()` — atomically insert/update `inbound_events` rows. Used as the dedup guard in every other ingress handler. The reclaim predicate accepts a stale `'received'` row plus every member of `RECLAIMABLE_INBOUND_EVENT_STATUSES` (`'failed'`, `'stale_ignored'`) — spelled literally in the SQL; `'processed'` is deliberately NOT reclaimable, which is why an acked-for-age event is closed as `'stale_ignored'` and an operator resend still reprocesses. |
| `stripe.ts` | `POST /ingress/stripe` | Verifies Stripe webhook signatures and deduplicates delivery. Checkout completion provider-reads and validates the authoritative attempt before the single status/snapshot projection; subscription/invoice handlers converge provider-current status through the exact entitlement-locked account and durably enqueue deprecated mirror repair. Threads `StripeEventContext` (`{id, created}`) into both subscription handlers as a REQUIRED argument, and closes the `inbound_events` row as `'stale_ignored'` — never `'processed'` — when a handler acked the event for age (read from `processSubscriptionUpdated`'s outcome reason `stale_no_account`, and from `processSubscriptionDeleted`'s returned `StripeSubscriptionAck.ackedForAge`). Both arms report through a RETURN VALUE — an earlier `AsyncLocalStorage` channel was replaced because an ingress hot path should not carry an invisible side channel. |
| `resend.ts` | `POST /ingress/resend` | Verifies Svix signature. Maps `email.delivered` / `email.bounced` / `email.complained` events to `notification_deliveries` status updates and `owner_email_bounced` flag; **WS6** classifies `autonomy_suspended_notice` as owner-directed for hard-bounce suppression. |
| `unsubscribe.ts` | `POST` + `GET /ingress/unsubscribe/:token` | **(#644, #651, #652)** RFC 8058 one-click opt-out. `POST` redeems the token into a `scope='global'` suppression (`source='unsubscribe_one_click'`) by injecting `sqlUnsubscribe` — the fixed-two local redemption pool, so valid-token traffic cannot consume the shared worker write slots; the mandatory admission wrapper queues above two — into the **module-owned** transaction (#652: this adapter opens none, so it cannot pick an isolation level or hold the token row lock around remote work). It answers `200` **before** logging, so telemetry cannot turn a committed redemption into a `500`; `unknown_token` → `503` (never a success-shaped no-op, so a #630 mint race stays recoverable). `GET` always `302`s to `<APP_URL>/u/<token>` — including for a forged token, since `503`-ing there would be the one answer that distinguishes forged from real. No signature, no dedup row, no rate limit. Owns the 60s unknown-token aggregate (+ shutdown flush), a per-token single-flight, and `assertUnsubscribeIngressConfigured()`. |
| `twilio/twilio-intent.ts` | *(utility)* | `classifyIntent(body)` — shared STOP/START keyword detection used by WhatsApp ingress. |
| `twilio/twilio-verify.ts` | *(utility)* | Verifies Twilio request signatures (HMAC-SHA1 on URL + params). |
| `twilio/twilio-whatsapp.ts` | *(barrel)* | Re-exports both WhatsApp ingress handlers and shared helpers for unit tests. Mounts were moved to focused modules. |
| `twilio/twilio-whatsapp-status.ts` | `POST /ingress/twilio/whatsapp-status` | WhatsApp delivery status callback. Signature verify → dedup on `${MessageSid}:${MessageStatus}` → first-wins terminal state → update `notification_deliveries`. |
| `twilio/twilio-whatsapp-inbound.ts` | `POST /ingress/twilio/whatsapp-inbound` | WhatsApp inbound message handler. Routes: ButtonPayload (Approve/Regenerate tap) → `approveViaCallback`; `start-<token>` deep link → enrollment; STOP keyword → opt-out; everything else → log + mark processed. |
| `twilio/whatsapp-shared.ts` | *(utility)* | `fullUrl()` and redaction helpers shared by both WhatsApp status and inbound handlers. |
| `telegram/telegram.ts` | `POST /ingress/telegram` | Orchestrator. Verifies webhook secret, dispatches to `telegram-enrollment.ts` (`/start <token>`) or `telegram-callback.ts` (callback_query). Rejects group/channel chats on `/start`. PII stripped before `inbound_events.payload` write. |
| `telegram/telegram-enrollment.ts` | *(called by telegram.ts)* | Handles `/start <rawToken>` — looks up `channel_enrollments` by SHA-256(token), flips status to `verified`, stores `chat_id` as handle. Model A ack ordering: `markInboundEventProcessed` before confirmation `sendMessage`. |
| `telegram/telegram-callback.ts` | *(called by telegram.ts)* | Handles `callback_query` (Approve / Regenerate button taps). Model A ack ordering: validate → `answerCallbackQuery` → approval tx → `editMessageText`. Permanent link-state errors edit message in place; unexpected errors return 503 for retry. |
| `telegram/telegram-shared.ts` | *(utility)* | Narrow Telegram update DTO type, link-state error classifier, and small helpers shared by `telegram-enrollment.ts` and `telegram-callback.ts`. |

| `zernio/zernio.ts` | `POST /ingress/zernio` | Zernio event webhook handler. HMAC-SHA256 verification (via `zernio-verify.ts`). Routes: `account.disconnected` → marks `zernio_connections` disconnected + enqueues `send_owner_email` (connection_lost). Reads nested `body.account.id` per spec §5.4. |

| `conversational-seam.ts` | *(utility)* | Future-agent seam (ADR 0003) — deliberately a NO-OP today: `handleConversationalMessage({channel, senderHandle})` logs an acknowledgement and sends no reply. `isAuthorizedConversationalSender` is the auth boundary any future reply must sit behind: a `verified`, non-archived `channel_enrollments` row on an account `checkSubscription` still allows (past_due honours the grace window). #### `worker/ingress/stripe/` — per-event Stripe handlers

Per-event handlers `stripe.ts` dispatches to after signature verification and dedup; every status change routes through the single applier.

| File | What it does |
|------|--------------|
| `apply-subscription-state.ts` | The SINGLE applier of `accounts.subscription_status` — Stripe is the source of truth. `mapStripeStatus`, the monotonic `ALLOWED_TRANSITION_SOURCES` table (`cancelled` terminal; stale/out-of-order → `changed:false`), `applyStripeSubscriptionState(tx, ref, stripeSub)` (resolves by account id or customer+subscription, takes the entitlement lock) and `applyStripeSubscriptionStateUnderEntitlementLock` for callers already holding it. Both funnel through one internal function, which is where `acquireStripeCustomerBindingLock` is taken (D8) so NEITHER entry point sits outside it — the lock closes the window in which a `COALESCE(stripe_customer_id, $1)` binding could land between the offboarding redaction guard's sharing count and its Stripe call. Inside the caller's tx it writes status/`trial_ends_at`/`subscription_activated_at`, the audit row, the overage-recompute + mirror-sync enqueues and trial analytics facts. Also called by the reconcile poller. |
| `checkout-completed.ts` | `processCheckoutSessionCompleted(session)` — validates the ref id (UUID; account or legacy business), `mode=subscription`, paid/`no_payment_required`, then `projectCheckoutSubscription`: under `acquireTierBillingActivationLocks` provider-reads the Session (+line items) and subscription and requires the account's `checkout_attempt_*` lease, the line items and the provider subscription to agree before the status applier + tier-snapshot write; a mismatch cancels the unexpected subscription (`CheckoutRemediationRequiredError`), marks the attempt remediated and pages. Post-commit: `synchronizeBusinessTierMirror` when needed, `resumePrimaryBusinessBackfill` on activation. |
| `invoice-paid.ts` | `processInvoicePaid(invoice)` — resolves the account by `stripe_customer_id` + the invoice's subscription id, then in one tx takes the entitlement lock, retrieves the provider-current subscription (20s timeout) and runs the applier. A no-op where DB and provider both still read `past_due` THROWS so Stripe redelivers (stale-read suspect); an activating transition resumes the primary business backfill. |
| `invoice-payment-action-required.ts` | `processInvoicePaymentActionRequired(invoice)` — SCA/3DS pending at a charge is entitlement-equivalent to a payment failure, so it delegates straight to `processInvoicePaymentFailed`. |
| `invoice-payment-failed.ts` | `processInvoicePaymentFailed(invoice)` — resolves the account by customer AND the failed invoice's subscription (one customer can map to several accounts), then under the entitlement lock retrieves the provider-current subscription and runs the applier (→ `past_due`, 7-day grace). On an `active→past_due` transition within 3 days of `trial_converted`, enqueues `trial_payment_failed` so net conversions stay accurate. |
| `shared.ts` | Utilities for the Stripe handlers: `LOG_PREFIX`, re-exported `getStripe`, `extractCustomerId`/`extractSubscriptionId`/`invoiceSubscriptionId` (across API-version shapes), `UUID_RE`, and `AccountNotProvisionedYetError` (thrown when a subscription.* event precedes its checkout — the wrapper answers 500 so Stripe redelivers). Single owner of the out-of-order retry bound: `OUT_OF_ORDER_RETRY_WINDOW_SECONDS` (900), the pure predicate `outOfOrderRetryWindowOpen(created)` (age > 900 closes it; a negative or non-finite age leaves it OPEN so skew fails toward retry), the `StripeEventContext` type, the operator warning `warnStripeSubscriptionEventAckedForAge`, and the `StripeSubscriptionAck` type with its two frozen values `HANDLED_NORMALLY` / `ACKED_FOR_AGE`, which is how `processSubscriptionDeleted` reports an age-ack to the dispatcher. `resumePrimaryBusinessBackfill(businessId)` is the ONE post-commit "activation → resume Zernio import" hook (**#266**): best-effort; in one tx holding the `businesses` row lock it creates the Import offer and, if `zernioPublishingEnabled()` and consent is `accepted`, calls `enqueueInitialImport`. |
| `subscription-deleted.ts` | `processSubscriptionDeleted(sub, eventContext): Promise<StripeSubscriptionAck>` — loads every account under the customer; none → throws `AccountNotProvisionedYetError` while the out-of-order retry window is open, else warns and returns `ACKED_FOR_AGE`, which is what makes the dispatcher close the row `stale_ignored` rather than `processed`; every other path returns `HANDLED_NORMALLY`; acts on the one whose CURRENT `stripe_subscription_id` matches, skipping a subscription that only matches an active offboarding snapshot; then under the entitlement lock runs the applier (→ `cancelled`). |
| `subscription-updated.ts` | `processSubscriptionUpdated(eventSnapshot, eventContext)` → `SubscriptionUpdatedOutcome` (`updated | variant_mismatch | status_only | ignored`). Resolves the account by customer + subscription (stale/offboarding-snapshot subscriptions ignored; none → `AccountNotProvisionedYetError` inside the out-of-order retry window, else a Sentry warning + `ignored`/`stale_no_account`, which is what tells the dispatcher to close the row as `stale_ignored`), then in one tx under `acquireTierAndBillingLocks` retrieves the provider-current subscription, runs the status applier (a resolved no-op still enqueues mirror sync), resolves base/overage items via `resolveSubscriptionBilling` and writes the tier snapshot + `locations_paid`. Post-commit `synchronizeBusinessTierMirror`; alerts (unmapped price, variant mismatch, untrusted overage, Autopilot-while-unavailable) → Sentry. |

#### `worker/ingress/resend/` — the Solicitation lane and its shared classifier

`resend.ts` above serves **two** lanes on ONE endpoint. The
`notification_deliveries` path is unchanged; the **Solicitation lane** is selected
by the echoed `lane` tag **before any DB lookup**, so a genuinely-unknown
`email_id` stays distinguishable from a lane mismatch. Per glossary rule **DR1**
the lane is **not** flag-gated: `SOLICITATION_SEND_ENABLED` masters *sending*
only, and a webhook arriving while sending is off must still be recorded.

| File | What it does |
|------|--------------|
| `bounce-classifier.ts` | **(#657)** `extractBounceType` / `isHardBounceType` / `classifyBounce`, moved **verbatim** out of `resend.ts`. It moved for exactly one reason: the Solicitation lane must reuse it, and exporting it from `resend.ts` would make the lane import its own parent — a cycle. A second classifier would be a second owner of "what counts as permanent". Behaviour unchanged: `'unknown'` classifies **soft** (fail-safe), and `classifyBounce` normalizes to the `bounced:hard:<raw>` / `bounced:soft:<raw>` prefixes the admin overview SQL filters on, so the webhook and the admin red-state query cannot disagree. |
| `solicitation-lane.ts` | **(#657, spec §5)** `isSolicitationLane(data)` (the tag discriminant, tolerant of Resend's object-map *and* array tag shapes) + `handleSolicitationResendEvent(sql, eventType, emailId, data)` over the seven subscribed events. **Write surface is deliberately narrow:** only `bounced_at`, `complained_at`, `provider_error` and the **Suppression ledger** — never `delivery_status` or `sent_at` (#630 owns the send lifecycle, and a webhook write would race migration 091's ladder CHECKs) and never `unsubscribed_at` (that is `worker/ingress/unsubscribe.ts`'s RFC 8058 POST). §5.3's `delivered_at` effect is dropped — no such column, no migration. `withAttribution` is the ONE transaction owner: the `FOR UPDATE OF o` attribution read, the outreach UPDATE and the optional ledger write are one commit or none, and it returns a value **only on a committed write** so nothing logs a fact the database does not hold. Unmatched ids split by event (**#967**): suppression-bearing ones (hard bounce, complaint, `email.suppressed`) write the recipient's **global** opt-out from the SIGNED payload with `accountId: null` and **ack**; soft bounce and `email.failed` warn and ack. They used to throw → 503 → retry, which could never help two of the three unmatched causes — an account purge deletes the `solicitation_contacts` row `loadAttribution` joins, and a send whose terminal CAS lost never persisted a `provider_message_id` at all. **Exactly one entry in `to`, or throw** — `readRecipients` returns entries UNFILTERED so a non-string member is counted, not silently dropped into a false "exactly one". `reportUnattributedSuppression` raises a Sentry warning post-commit, because acking removes these events from `checkFailedInboundEvents`' `status='failed'` set and a log line replaces no pager. Two rows on one `provider_message_id` throws rather than mutating an arbitrary one. `email.suppressed` emits the loud §6.2 divergence warning **only when a ledger row was really written** — a first-write-wins no-op means the two lists agree, the one case where the divergence claim is false. Logs the bounce **kind**, never the raw provider string (it can carry an address); the full value lands in `provider_error`, a column, not a log. Takes `sql` as a parameter (invariant #15); the attribution `SELECT` is cross-account by construction and allowlisted in the tenant-scope audit. |
