## Owner Operator — coined 2026-09-11, Run A intake

The conversational surface an owner uses to configure RepWorth by talking. Spec of record: `docs/roadmap/2026-09-11-owner-operator.md`. Runs A and B added the turn pipeline, voice proposals, Apply, Decline, receipts and the Console screen. Run C extends those contracts to auto-reply policy changes. Run D's final timing decision retains the 180-second claim lease, 1,200-second predecessor stall limit and 10,000-millisecond recheck delay after the owner-approved early end to observation; it does not claim a full 24-hour run. Run E adds receipt-based Restore and durable policy refusals, verified on staging with completed fixture cleanup. The spec's status and acceptance sections own the certification, feature merge and post-merge deployment evidence.

- **Operator turn**: one owner message and the single model reply it earns — an `agent_turns` row carrying `owner_text`, the stored `location_id`, a `sequence` within its conversation, and a lifecycle `accepted → running → completed | failed`. **The turn, not the browser, owns the target**: the location is frozen at POST, so moving the selector afterwards retargets nothing. Idempotency is the account-scoped `(account_id, client_turn_key)` unique — a re-POST of the same key and payload returns the original ids and writes no second row; a different payload under that key is a 409, and `text` is compared verbatim. _Avoid_: message, chat turn, prompt, request. *(coined in the Run A intake, 2026-09-11)*

- **Turn claim**: the `UPDATE agent_turns SET status='running', attempt = attempt+1, attempt_token = <uuid>, claimed_at = NOW()` that one dispatch wins and every other one loses, bounded by a 180-second lease. **Zero rows returned is a normal outcome, not an error** — a live lease is held elsewhere, so the losing attempt exits without touching the outbox row, which belongs to the winner — unless the turn is already terminal, when it closes the row nobody else will. A healthy predecessor wait releases the claim and refreshes the exact outbox attempt's liveness atomically, then delays the same job without spending failed retry budget. Both ownership checks must still match; a transient-error release does not refresh liveness. The claim makes watchdog re-dispatch safe. _Avoid_: lock, reservation, job lock, lease acquisition. *(coined in the Run A intake, 2026-09-11; recovery distinction updated in Run D)*

- **Fenced completion**: the one transaction that ends a turn — the terminal `UPDATE … WHERE id = $1 AND account_id = $2 AND attempt_token = $token`, the proposal inserts and Restore preparation, the supersession, the unsupported inserts, the refusal ledger writes and stored refusal subjects, and `markOutboxCompletedIfOwned`, all or nothing. **A zero-row fenced UPDATE means the lease was lost: discard the model output and exit** — do not retry, do not fail the turn, do not touch the outbox row; the attempt that owns the lease will. The flag-off and exhaustion paths can terminate without a current turn token. Dispatch exhaustion instead requires the winning outbox attempt and its stored tenant/turn binding; it defers live or contended claims and couples any eligible turn failure to the outbox transition in one transaction. _Avoid_: commit, finalize, atomic write. *(coined in the Run A intake, 2026-09-11; recovery distinction updated in Run D)*

- **Context snapshot**: the bounded, server-built object the model is allowed to see — recent finished turns, pending **Proposals**, **Operating rules**, the catalog with expansion-readiness reasons, the location list, star-band and posted counts, the stored voice facts, and the account-wide **Posting block**. **It carries no review text, no response text and no reviewer name, ever** — `sample_responses` is EXCLUDED for that reason, which is why its `facts` is a four-field projection rather than the voice writer's own type, and why an earlier turn's `owner_text` is re-scrubbed on the way in. That is a type-level property rather than a filter: the snapshot has no field those could occupy. The **Posting block** rides as `posting` (`projectPostingBlock`, field by field, never a spread): `blocked`, its reasons, the owner sentences taken from their single owner in `src/lib/auto-approval/posting-block-copy.ts`, and `correctionOwed` — the SERVER's decision that a correction is owed, i.e. blocked AND some surface would otherwise claim posting. **The model may not re-derive `correctionOwed`, and cannot**: the snapshot projects **Operating rules** for the SELECTED location only, so an armed override on another location is invisible to it. It is **not readiness**: the catalog's expansion-readiness reasons answer whether the owner may WIDEN, a different question, and `posting` rides beside them rather than being derived from them. Status values are frozen from this snapshot; policy consequence values come from a separate server-only review-history read. Neither can be supplied by the model. _Avoid_: context, prompt context, model input, payload. *(coined in the Run A intake, 2026-09-11; policy distinction updated in Run C; Posting block added at #1352)*

- **Reply segment**: one element of the ordered list a reply is made of. The model may emit six kinds — `text`, `status_ref`, `proposal_ref`, `question`, `scope_check`, `refusal_ref` — and never returns prose paragraphs. **What is STORED is a narrower, server-owned union**: a `status_ref` supplies only a metric NAME and is replaced at **Fenced completion** by a `status` segment carrying the value, its reporting period and the instant it was read, and a scrubbed message gains a `server_notice`. A `refusal_ref` selects a closed reason; the winning completion stores a `refusal` with a server-minted subject UUID and server-owned wording. Stored refusal cards return separately as `refused`, with no Apply action. These server segments are never model-emitted, which is what makes a number on screen a frozen read rather than a claim, and what stops a refresh repainting a week-old sentence with today's count. A `text` segment with a digit next to a metric word, or a completion claim ("applied", "updated", "now active"), fails validation. _Avoid_: message part, block, chunk, response section. *(coined in the Run A intake, 2026-09-11)*

- **Proposal**: a stored `agent_proposals` row describing one catalog operation and the owner's decision about it — operation, scope, input, full-state `before` and `after`, rationale, a `label_kind` of `rule` or `fact`, and a status in `pending | applied | stale | rejected | failed | superseded`. **Preparation changes no settings**: only an authorized Apply can write through the shared voice or policy writer and store a **Receipt** in the same transaction. Policy rows also freeze the server-computed consequence of the before and after dials; expansion confirmation is derived from the stored policy state. A later turn proposing the same operation and scope marks the earlier pending row `superseded` with `superseded_by` set. _Avoid_: suggestion, recommendation, pending change, action. *(coined in the Run A intake, 2026-09-11; policy distinction updated in Run C)*

- **Requested capability**: an `agent_unsupported_requests` row — the normalized text of something the owner asked for that RepWorth cannot do, with its context. **A separate kind, not a Proposal with no button**: the two return under separate response keys (`proposals`, `unsupported`), so a renderer can never grow an Apply affordance onto one. It records demand; it does not decide the roadmap. _Avoid_: unsupported proposal, feature request, backlog item, no-op card. *(coined in the Run A intake, 2026-09-11)*

- **Contract version**: the catalog's own version for one operation's input shape and effect semantics, stored on the **Proposal** at preparation time. **It is not freshness** — it answers "does this code still mean what the Proposal meant?" Apply checks the account-scoped stored proposal against the catalog before taking a settings lock or invoking a writer; a mismatch records `contract_changed` without a settings mutation. All eight proposable operations, including `clear_location_override`, have `contract_version: 1`; `restore_last` prepares a proposal rather than writing settings. _Avoid_: schema version, catalog version, proposal version. *(coined in the Run A intake, 2026-09-11; policy distinction updated in Run C)*

- **Version token**: the settings-freshness stamp recorded as `prepared_version_token` — for voice scope, `{ businessId, updatedAt }` read from `businesses.updated_at`; for policy scope, `accountDefaultRow` and, on every location token, `locationRow`. **It records row identity and existence, not only a timestamp**: each policy row is `{ id, updatedAt }` or `{ id: 'absent' }`, and absence matches only while that row remains absent. The account default stays in a location token even when an override exists. Apply compares current, prepared and client-expected tokens after taking the domain's parent lock, preserving PostgreSQL timestamps as opaque text with their microseconds. _Avoid_: etag, timestamp, freshness check, revision. *(coined in the Run A intake, 2026-09-11; policy distinction updated in Run C)*

- **Operating rules**: the effective configuration of one scope as the owner would state it — the auto-approval threshold, veto window and daily cap from `getAutoApprovalSettings`, plus the voice config. **Effective, not stored**: a location with no override row still has Operating rules, inherited from the account default, and a **Proposal**'s `before`/`after` shows that whole effective state rather than the single named dial. A location override replaces the whole default row: its null threshold means manual approval, never fallback to the parent's threshold. Policy state carries row existence and both the stored cap and its resolved platform value so a newly created override is explicit. _Avoid_: settings, policy, config, dials. *(coined in the Run A intake, 2026-09-11; policy distinction updated in Run C)*

- **Pasted-review scrub**: the server-side replacement of a pasted review block in an owner message with `[review text removed]` before the **Context snapshot** or the prompt is built. **The stored `owner_text` is never modified** — the scrub is a read-path transform, so the owner's own record of what they typed stays intact. A scrubbed message earns a fixed, stored **Reply segment**; no fact is extracted from pasted text. _Avoid_: sanitize, redact, filter, strip. *(coined in the Run A intake, 2026-09-11)*

- **Operator flag**: `OWNER_OPERATOR_ENABLED`, server-only and default off, read through `readFlag` by `ownerOperatorEnabled()`. **Off means the surface does not exist**: the routes 404 `operator_disabled` before any write, and a dispatched `agent_turn` job fails its turn with that reason and completes its outbox row without loading tenant context. No `NEXT_PUBLIC_*` companion (invariant #13). _Avoid_: operator toggle, feature switch, kill switch. *(coined in the Run A intake, 2026-09-11)*

- **Receipt**: the server-written `agent_proposals.receipt` JSONB — operation, scope, before and actual after, `differsFromPreview`, `effectiveNow`, what it affects, what remains blocked, `appliedAt`, the actor, the VERBATIM `owner_text` of the turn that produced the **Proposal**, the turn id as correlation id, and the **Version token** on both sides of the write. Voice receipts retain the prepared before state. Policy receipts read before under the account lock and compute old-rule and new-rule consequences over the same confirmed-live 30-day cohort; imported and unknown-origin exclusions remain explicit. Their retained-veto count is an as-of read of approved auto-policy drafts with their latest immutable approval grants, including drafts still waiting after the window elapsed. **Written in the SAME transaction as the mutation, and only there**: there is no committed mutation without a Receipt and no Receipt without a committed mutation, and the client supplies no field of it. A repeat Apply returns the stored one and executes nothing. Restore derives an inverse from the validated same-account receipt, prepares against current state, and requires a new Apply. The rules timeline pages applied receipts by opaque `(applied_at, id)` descending cursors and hydrates pending restores for the visible sources. The detailed Restore contract is owned by spec §6.6. _Avoid_: confirmation, result, audit entry, changelog. *(coined in the Run B intake, 2026-09-12; policy distinction updated in Run C)*

- **Refresh plan**: the action a `stale` or `contract_changed` **Proposal** card offers — **a new Operator turn posted from that Proposal's ORIGINAL `owner_text`**, not a retry of the Apply. The settings moved (or the code did), so the plan must be prepared again against the state that exists now; the owner's own words are the only input still true. It creates a fresh **Proposal**; it never revives the stale one. A stale Restore instead prepares again from its validated source receipt, retaining server-derived inverse state. _Avoid_: retry, re-apply, regenerate, refresh. *(coined in the Run B intake, 2026-09-12)*
