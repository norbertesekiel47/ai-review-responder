## Stripe Customer redaction — locked 2026-09-03 (plan `docs/superpowers/plans/feat-stripe-customer-redaction-plan.md`)

- **Stripe Customer redaction**: the `delete_data` purge stage that detaches every PaymentMethod attached to the account's Stripe Customer, then clears the eight identifying fields on the Customer itself (`name`/`email`/`phone`/`description`/`address`/`shipping`/`business_name`/`individual_name`, all with `''`) and every pre-existing metadata key, leaving one key naming the offboarding. **The detachment is part of the operation, not a detail**: a PaymentMethod carries its own `billing_details` — name, email, phone, full address — plus card `last4` and `fingerprint`, none of which `customers.update` can reach. **Detaching is the MOST the API allows, not an erasure** — Stripe exposes `detach` and no delete, so the object outlives the purge with that data intact and merely stops appearing under the Customer; it is still worth doing because it unlinks the method and prevents reuse. An earlier version of this term said that data "is deletable" unlike a paid invoice; the 2026-09-04 staging dry-run read a detached method back in full after a completed purge and falsified it, and **Provider data retention** now carries it as its own entry. It runs BEFORE the update so a failure there leaves the Customer's own fields intact and a retry re-runs the whole sequence from a consistent state. Detaching is possible only because teardown already cancelled the subscription — Stripe refuses to detach a method a live subscription depends on — which is why this belongs to the purge and not to teardown. **Explicitly not a deletion**: `customers.del` detaches every invoice irreversibly and would destroy the financial record tax retention requires, so `customers.del` is referenced nowhere and a test asserts the injected client's `del` is never called. **The retrieve is not optional** — `customers.update` MERGES metadata, so a call sending only the offboarding key leaves every prior key live at Stripe; the retrieve supplies the key set to unset. **It runs FIRST**, before every local destruction — which INVERTS D5 (deviation D6), because D5's own rationale was false. D5 placed it immediately before `runParentTombstonePurgeStage` on the premise that by then "every local destruction has committed", but the tombstone is itself the stage that replaces names, emails, phones and addresses with sentinels and runs AFTER — so a Stripe outage that exhausted retries left auth deleted and content destroyed while `users`/`businesses`/`accounts` still held live PII, the offboarding terminal, no receipt and no automatic re-run. Running first restores fail-fast: a Stripe failure aborts with NOTHING destroyed and BullMQ retries the whole job cleanly. The hazard D5 feared — a **live** account whose billing contact is already wiped — is unreachable here, because an offboarding at this point has `purge_started_at` set and cancellation is gated on `purge_started_at IS NULL` (`keep-my-data.ts`). **The shared-customer guard, not the ordering, is what protects a co-tenant.** Retry is safe because `account_offboardings.stripe_customer_id` survives until finalize and `loadPurgeOffboarding` re-reads it. **A shared customer is SKIPPED, never redacted** (D1): `accounts.stripe_customer_id` carries no unique constraint and one customer may map to several accounts, so a sharing count precedes the Stripe call, serialized by `acquireStripeCustomerBindingLock` (D8), taken BEFORE the count and held across the Stripe call, and which `applyStripeSubscriptionState` takes on the writer side after the caller's entitlement lock. **The stage does NOT take that lock alone** — an earlier version of this term said it did, and so did the code's own comment. The disposition append takes an exclusive `account_offboardings` row lock while the binding lock is still held. The property that matters is that the order is binding-then-row and is never inverted, not that there is only one lock. That excludes simultaneity but not the sequence "redaction wins, count is zero, a writer then binds the redacted Customer to a live account"; closing that needs a durable retired-customer marker and a migration, and it is **accepted, not closed** (D10), because `buildCheckoutSessionParams` passes `customer_email` and never `customer`, so Stripe mints a fresh Customer per Session and no path can bind an existing one to a second account — a test pins that premise so a future change fails loudly. Only `resource_missing` and an already-deleted customer are success; every other error throws, because mapping all permanent types to success would finalize a purge whose redaction silently failed on bad parameters or credentials. _Avoid_: customer deletion, Stripe purge, "delete the customer". *(coined in the feat/stripe-customer-redaction grilling; D1/D5/D8/D10; ordering inverted by D6 and the ALONE/detachment claims corrected by red-team round 2 R01)*
- **Provider data retention**: the `PROVIDER_DATA_RETENTION` inventory (`src/lib/account-offboarding/table-disposition.ts`) of third-party objects that survive a purge — today two entries, the Stripe Customer and the detached Stripe PaymentMethod, both classified `retain_compliance_limited_pii`. **Deliberately separate from `TABLE_DISPOSITIONS`** (D2), and the separation is load-bearing rather than tidy: `verificationQuery` throws `missing_purge_verification_sql` for any inventory entry with no SQL branch, and a provider object has no SQL, so an entry in the table inventory would fail every purge. It therefore carries no `purgeVerification` field and never enters `ACCOUNT_OFFBOARDING_TABLES` or `PURGE_VERIFICATION_TABLES`; one file owns both inventories and a test asserts they stay disjoint. Each `reason` names the CATEGORIES that outlive redaction — paid invoices, which are immutable and keep the billing name and address they were issued with; `tax_ids`, which hangs off the Customer as its own resource `customers.update` cannot clear; and a detached PaymentMethod's own `billing_details` plus card `last4`/`fingerprint`, which no Stripe verb deletes — categories only, never a handle and never a count. **The purge receipt and the privacy policy's Retention paragraph state the SAME categories but are NOT written from it** — an earlier version of this term said they were. Neither imports the array: one is HTML for an email and the other is a legal document, and neither can render from a reason string, so the three are kept in step by REVIEW and not by the compiler. Editing a `reason` here propagates nowhere on its own. **Not to be confused with a provider disposition**, which is the admin-recorded purge-eligibility marker in `account_offboardings.provider_dispositions`; the stage's own record uses the distinct `stripe_customer_redaction` discriminator so `extractConcreteAdminProviderDispositions` cannot mistake one for the other, and it stores the customer id only as a `sha256:` hash. _Avoid_: provider disposition, retained tables, third-party purge. *(coined in the feat/stripe-customer-redaction grilling; D2; the "written from it" coupling claim corrected by red-team round 2 R01)*
