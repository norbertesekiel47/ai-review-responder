## Solicitation (send-mode) — locked 2026-07-28 (ticket #619, wayfinder map #617) (part 3 of 3 — send breaker, release & attribution)

_Part 3 of 3 — the platform-wide Send breaker, the per-child Dispatch gate, the auto-approval lane and veto notice, and review attribution. Part 1 (`solicitation-send-mode-batch-and-delivery-seam.md`) holds the batch model and delivery seam; part 2 (`solicitation-send-mode-approval-halt-lane.md`) holds the approval & halt lane._

- **Send breaker**: the platform-wide reputation circuit breaker that protects the shared **Sending identity** — one `solicitation_send_breaker` row per trip, **open while `reset_at IS NULL`**, closed only by an admin reset. **Distinct from the Halt latch**: the Halt latch stops ONE batch, the Send breaker stops ALL solicitation sending platform-wide, and it is never per-tenant because one mailbox and one sending domain are shared by every account — one account's bad list burns the deliverability every other account sends on. **It never self-clears**; there is no timeout and no automatic re-arm, because a breach is a fact someone must look at. Its read path (`readSendBreaker`) **fails CLOSED by contract**: it returns state or throws, and the throw IS the halt signal — a DB failure degrades to HALT, never to "unmeasured therefore send", so a caller that try/catches it and proceeds has broken the invariant. The `HealthAlertPoller` is its **only** tripper (`solicitation_send_breaker_tripped`, response procedure `docs/runbooks/solicitation-sending-domain.md` §8); #900's releaser is a **pure reader** — `runReleasePhase` in `src/lib/solicitation/release.ts` calls `readSendBreaker` and writes nothing to the table. First of the four send governors in the fixed order **breaker → platform ceiling → account cap → per-child** (#622 §4.3) — #898 shipped them as callable modules and #900 wired that order into the release decision, where the breaker is checked once per tick before any candidate is read. Do not confuse the dispatch vocabulary it arrives with: `no_postal_address` is a **dispatch-time row fact** on one **Outreach row**, a different fact from the **Send handoff**'s `postal_address_missing`, which is a **handoff-time location fact** about the business. _Avoid_: kill switch, global halt, halt latch, pause sending. *(coined in #898)*
- **Send breaker trip**: one `solicitation_send_breaker` row — `tripped_at`, `trip_reason` (`hard_bounce_rate` | `complaint_rate`, in that fixed precedence so the page names the metric to fix first), and the `metrics` **Breaker window** snapshot that tripped it, frozen at the instant of the trip and never recomputed. **At most one trip is open at a time**, and that invariant lives in a partial unique index rather than in application code, so a second breached poller tick is an `ON CONFLICT DO NOTHING` no-op — one trip, one row, however long the breach stands. **Paging is LEVEL-triggered and the write being a no-op does not make it edge-triggered**: the poller probes for an open trip before it measures anything and re-pages on every tick while one stands, because an open breaker is a STATE and one dropped event must never equal a silent platform-wide halt. The repeats carry a constant per-reason title under the same routing key, so Sentry collapses them into one issue that keeps receiving events. Resetting stamps `reset_at`/`reset_by`/`reset_note` on the same row — the table is append-only, so trips are a history, not a current-state flag. A **mandatory reset note** is enforced by 110's `reset_consistency` CHECK as well as by the route schema, so "who cleared this, and why" cannot be unanswerable by omission. _Avoid_: breaker event, breaker state row, incident. *(coined in #898)*
- **Breaker window**: the rolling **7 days, minimum 100 sends** measurement the **Send breaker** decides on — hard bounce rate **> 2%**, complaint rate **> 0.3%**, both strict, the volume floor checked before any rate so small-N noise cannot halt the platform. **Deliberately NOT a cohort**: the denominator is **send-dated** (`sent_at` in the window) while the numerators are **signal-dated** (`bounced_at` / `complained_at` in the window). Bounces lag their send by minutes to days, so a cohort measure would dilute a fresh bad batch with sends whose bounces have not landed yet — the fail-*open* direction. The consequence is intended, not a defect: a burst of bounces from a send nine days ago still trips it, and the ratio can exceed 1.0. Hard bounces are counted from `bounce_kind = 'hard'`, never by parsing `provider_error`. Same two rates as the §5 warm-up ramp's advance rule, checked continuously rather than by a human before each stage; never re-tune one side alone. _Avoid_: health window, bounce cohort, reputation score. *(coined in #898)*
- **Dispatch gate**: the union of per-child checks #630 runs **inside one child's short pre-send transaction**, immediately before the physical send — the last thing that can stop one message. Stated once in **B6** of `docs/superpowers/specs/2026-07-28-send-mode-cross-spec-amendments.md` (itself the union of #619 D18 as amended by #620 §6.3, #623's two re-checks and #622's byte-match). B6 numbers nine items, but **two of them are not per-child work and the gate does not run them**: item 7 (daily caps) is checked at release and the gate only asserts the release stamped `queued_at`, and amendment **B14** moved item 3 (`subscriptionGrantsFullAccess`) to release level too. The seven the child actually runs, in order: batch not halted and send window open → `SOLICITATION_SEND_ENABLED` → **suppression** lookup → consent row + `SEND_ELIGIBLE_ATTESTATION_VERSIONS` → postal address exists and byte-matches the stored footer → re-lint at current `ASK_LINT_VERSION` → re-moderation. **It is per-CHILD and therefore per-CONTACT**, which is the whole boundary: an account-level fact has no business here because every child of a batch computes the same answer for it, so account-level facts are **release-level gates** — the fixed order **Send breaker → platform ceiling → account cap → Dispatch gate** (#622 §4.3) runs the first three once per release, before any child exists. B14's move is that boundary applied: as a per-child item, a lapsed subscription had to make the child *defer*, but #900 CASes the **Outreach row** `rendered → queued` **before** the child runs, so a deferring child stranded a `queued` row the release predicate could never select again. Its dispatch-time vocabulary is a **row** fact, never a location fact: `no_postal_address` and `postal_address_mismatch` (migration 110's two new `withheld` members) say what was true of THIS attempt, and are a different fact from the **Send handoff**'s `postal_address_missing`, which is one handoff-time fact about the business. **Its writer is `applyDispatchGate` / `dispatchOutreach` in `src/lib/solicitation/dispatch.ts` (#899)**, which ships without a migration because 110 already held the vocabulary. Three implementation facts B6 does not carry, each load-bearing: (a) the two SLOW items are gathered **above** the transaction with no lock held — re-moderation is a ~10s provider call and the repo rule forbids holding a lock across one; it is safe only because ADR 0020 makes stored bytes immutable after approval, so the verdict cannot go stale, and **B6's ORDER is unchanged — only the gathering moved**. (b) The gate is **never re-run on a row already `sending`**: recording `withheld` for a message that may already have reached a real person is the same lie-with-teeth D12d cites for `unknown`. (c) Its two **defer** items defer for different reasons — `batch_open` because the **Halt latch** sweep already cancelled the row, `send_flag` because 091/110 carry no `flag_off` member and inventing one would terminalize a row the owner never withdrew. _Avoid_: send gate, pre-send check, dispatch check, per-child gate (that last names the position, not the term), release gate (those are the three governors ABOVE it). *(named in #619 D18; stated once in amendment B6; boundary, item count and provenance recorded in #898; writer + implementation facts in #899)*
- **Auto-approval lane**: the `approval_method='auto_policy'` path through the send lane — a four-condition opt-in decided **ONCE**, at the **ask-generation finale**, and never on `regenerateAsk` (a batch this lane already declined never gets a second look). The four conditions, in reason-precedence order: both server flags (`SOLICITATION_SEND_ENABLED` AND `SOLICITATION_AUTO_APPROVAL_ENABLED`), `subscriptionGrantsFullAccess`, `tierGrantsAutopilot`, the account-wide Governor suspension read (D19 widened `auto_approval_policies` so ANY suspended row on the account trips this — not merely a `persona='solicitation'` one — because design §8 defines the Governor's kill switch as per-ACCOUNT autonomy suspension: a Reply-lane trip must protect Solicitation too, with zero Governor code changes), and finally the live `persona='solicitation' AND action_class='sending' AND location_id IS NULL` policy row, whose absence is `no_policy_row` — the owner never opted in. `policy_suspended` outranks `no_policy_row` on purpose: an account-wide Governor trip is a safety fact and outranks "the owner never opted in" even when both are true at once. An owner approval that lands between the finale's last child render and the finale transaction **wins the race**: the auto CAS carries `approved_at IS NULL`, so a zero-row miss with a prior approval already stamped is a quiet `owner_won` outcome, never a throw. **Judge stays release-owned** — there is no approval-time Judge check (#900); Judge availability remains a dispatch precondition the releaser enforces separately. The release-time re-check (`findAutoDowngradeReason`) is deliberately **narrower** than the approval-time gate: it re-checks only the auto flag, the Autopilot tier, the policy row's presence, and account-wide suspension — a subscription lapse is NOT a downgrade (B14: the existing `subscription` withhold in `runAccountArm` already holds the batch and it resumes on recovery) and the master send flag is NOT a downgrade either (B15: `runReleasePhase` already stops with `flag_off` before any batch arm runs). _Avoid_: autopilot lane, auto lane (in code comments), policy approval. *(coined in #631, map #617 D7; `src/lib/solicitation/auto-approval.ts`)*
- **Veto notice**: the owner notification whose FIRST provider-accepted send — `notification_deliveries.sent_at`, the Reply lane's shipped anchor semantic (`worker/jobs/publisher/veto-window-gate.ts:84`; Telegram has no delivery receipt, so `delivered_at` was never usable) — starts the veto window's clock. Template `'solicitation_veto_notice'`, `entity_id` = batch id — the notice is about a **BATCH**, not a response or a review, and carries no reviewer/star/review-text fields, unlike every other notice in this family. Claim-before-send idempotency is backed by migration 113's `notification_deliveries_solicitation_veto_notice_claim` index. The worker (`worker/jobs/solicitation-veto-notice/`) gates on **BATCH STATE ONLY** — no flag reads anywhere in the family (owner re-lock decision 11): skip when the batch is no longer `auto_policy`, or is halted/closed. **Anchored is deliberately NOT a skip** — a retry must still be able to claim and send on any channel that hasn't delivered yet, and the **Veto anchor** itself is computed FROM this notice's own `sent_at`; refusing an already-anchored batch would starve the anchor of its input on every retry. CTA is `${appUrl}/dashboard/requests`, tokenless (decision 10 — the real Requests route; `createApprovalLink` is NOT the precedent here). _Avoid_: veto email, approval notice, delivery-anchored (it is SEND-anchored). *(coined in #631; `worker/jobs/solicitation-veto-notice/`, `src/lib/notifications/email/templates/solicitation-veto-notice.ts`)*
- **Veto anchor**: the release-cycle phase — wired immediately BEFORE the release phase in `release.ts`'s `runReleaseCycle` — that CASes `veto_deadline_at` **ONCE** from `MIN(notification_deliveries.sent_at)` (computed IN SQL, never a JS `Date` round-trip — the #520 microsecond-truncation gotcha) plus the granted `veto_window_minutes` recorded on the **Send batch parent**'s LATEST `batch_approved` spine step, and writes a `veto_window_granted` step (first send time, deadline, actor `system`). **Fail-closed per D9: no sent Veto notice, no anchor, no release, ever** — an `auto_policy` batch with zero delivered notices simply never gets a deadline, and the batch eventually dies through the `send_window_elapsed` sweep's expiry closure, not through this phase. It is a **phase, not a poller** — `anchorVetoDeadlines` (`src/lib/solicitation/auto-approval.ts`) is one more caller of the same `tallyPhase`/`alertPhaseFailure` seam every other `release.ts` phase uses, isolating one failing candidate to itself (a Sentry `warning` plus a log line) rather than the whole tick. _Avoid_: deadline sweep, anchor poller (it is a phase, not a poller). *(coined in #631 decision 4; `anchorVetoDeadlines` in `src/lib/solicitation/auto-approval.ts`)*
- **Attribution window**: the 14 days after an **Outreach row**'s `sent_at` inside which a newly ingested review may attribute to it — a FILTER constant evaluated at ingest, never a timer and never a parked step (spec D16b: May §6.3's `wait_for_async_signals` presumes a run engine that can park work, and D17 declined to build one). It is measured against the **Review-time anchor** of the arriving review, not `NOW()`, and it is inclusive at BOTH ends; a review whose anchor precedes `sent_at` is not a candidate, because it existed before the ask. One owner, `ATTRIBUTION_WINDOW_DAYS` in `src/lib/solicitation/attribution.ts`, and a different number from the presentation-only `ATTRIBUTION_DISPLAY_WINDOW_DAYS` (30). **Body redaction**'s 90 days is deliberately timed comfortably past it. _Avoid_: attribution timer, attribution wait, attribution delay. *(coined in #632)*
- **Attributed review**: a review recorded against **exactly one** **Outreach row** by the name matcher — migration 114's `attributed_review_id` / `attributed_at` / `attribution_rule` / `attribution_detail`, plus one `review_attributed` outcome on that row's **Lazy child**. It is a **shadow** metric and is **never billed** until May §6.4's M3 precision bar clears (map #617 decision 1), because D16d is binding: a Google review carries a display name and a date and there is no deterministic contact-to-review identity seam, so this is evidence about the matcher, not a settled fact about the customer. The "has this row ever been attributed" marker is **`attributed_at`, never `attributed_review_id`** — the FK is `ON DELETE SET NULL`, so deleting a review clears the id and leaves the timestamp, and all four sites (candidate query, enqueue guard, index predicate, final CAS) key on the timestamp. `attribution_detail` carries NO personal data, for the same retention reason **Body redaction** exists. _Avoid_: won review, earned review, converted review, conversion. *(coined in #632)*
- **Attribution match**: the two-rule name test — `full_name` and `first_last_initial` — that IS the matcher; there is no score, no threshold and no fallback (deviation D1, which is why the column stores the rule NAME). Both sides need **at least two tokens**, first and last must each be *compatible*, and at least **one** position must be a FULL-token match. **Compatible means equal OR one side is an initial the other starts with, on either position** — so `m. okafor` matches `michael okafor` and is recorded as `first_last_initial`; the narrower reading in which only exact first tokens match was considered and **rejected** (owner, 2026-08-24), and the `isInitial` arm of `compatible` must keep both directions. The full-token requirement is what stops `d. rodriguez` matching `dana r.` on two initials and no evidence; middles are ignored, so `dana m rodriguez` still matches `dana rodriguez`. _Avoid_: fuzzy match, name score, similarity, confidence. *(coined in #632)*
- **Ambiguous attribution**: two or more **Outreach rows** matching one review. It attributes **nothing** — a shadow metric that guesses is worse than one that abstains. **The abstention is LOGGED, not recorded** (branch-review M4, and the distinction is load-bearing): `attributeReview` returns early on every non-`attributed` resolution and writes no row, so `ambiguous`, `no_match` and `no_candidates` exist only as `attribution_resolved` lines in the worker's stdout — bounded retention, nothing SQL can join against `solicitation_outreach`. Only `attributed` has a durable row. Its RATE is the stated input to May §6.4's M3 precision bar, so **make the abstention durable before relying on that rate, or run the analysis inside the log-retention window**; a follow-up PR owns the durable event, which needs `src/lib/analytics/events.ts` and could not land inside #632's edit surface. The log line carries `resolution` and the candidate count, never the reviewer name. It is not an error and never fails the job: `no_candidates` and `no_match` are equally normal. _Avoid_: unresolved match, tie, conflict, failed attribution. *(coined in #632)*
