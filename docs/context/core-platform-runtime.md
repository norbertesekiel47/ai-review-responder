# RepWorth Domain Glossary (seed)

_Context file of the RepWorth domain glossary — the index of contexts and the file that owns each term is [`CONTEXT-MAP.md`](../../CONTEXT-MAP.md)._

_Core context 1 of 3 — platform & worker runtime: the outbox, pollers, watchdog, boot, failure sinks, and the deployment lane. Core 2 is `core-reviews-responses.md`; core 3 is `core-accounts-channels-admin.md`._

- **Outbox job**: follow-up work recorded in `job_outbox` in the same transaction as the state change; OutboxPoller dispatches it to BullMQ. *(draft — to be sharpened in grilling sessions)*
- **Poller cadence**: a background loop's tick interval — owned by the code default (`DEFAULT_INTERVAL_MS`), overridable per-env via its `*_INTERVAL_MS` env var. Changing cost posture means changing the code default (rides PR + staging); the env var is a per-env operational override, never the authoritative value. *(coined in the cost-optimization wayfinder effort)*
- **Watchdog**: the recovery queries inside a dispatch poller (OutboxPoller's recover/terminate/stale-dispatching UPDATEs, AnalyticsDispatchPoller's stale-reclaim) that reclaim rows orphaned by crashes — distinct from dispatch itself, and allowed to run on a slower cadence than dispatch. Its terminate arm writes a generic reclaim text — `'Stale dispatching entry exceeded max_attempts'` or `'Stale dispatched entry exceeded max_attempts'`, chosen by the row's status (`OutboxPoller.ts:161-163`) — but only as a **fallback**: since #736 the write is `COALESCE(NULLIF(last_error, ''), …)`, so a bounded error class a failed-hook already recorded SURVIVES. Either way that text describes the **reclaim**, never the handler failure underneath it. Reading it as a diagnosis is what let #719 hide for three months — the diagnosis lives in Sentry, via the **Job-failure sink**. The terminate arm is **topic-blind** (#1378): it owns an exhausted row in `dispatching` on EVERY topic, not only `agent_turn`, because the crash window between `claimPendingBatch` (which sets `dispatching` and bumps `attempts` to `max_attempts` in one UPDATE) and `runOutboxDispatchFailure` is general. #1291 wrote that disjunct scoped to `agent_turn` for the Operator pair; the scope left every other topic with a row no arm and no claim could select — never dispatched, never retried, never terminalized, and raising `outbox_stale_dispatching` forever under the misleading title "watchdog may be down". **The two dispatching arms use different windows, and the gap is load-bearing:** arm 3 re-pends after a hard-coded 2 minutes, the terminal arm gives up only after `watchdogStaleSecs` (`OUTBOX_WATCHDOG_STALE_MS`, 15 min). `dispatchBatch` walks topic groups SERIALLY with `markDispatched` per group, so the claim→dispatched gap is bounded only by (topics × `OUTBOX_DISPATCH_TIMEOUT_MS`) ≈ 6 min, while the 60 s overlap guard lets a superseding cycle's watchdog run against that live batch. Terminalizing at 2 minutes would kill work still in flight, and the risks are ASYMMETRIC — a premature re-pend costs one idempotent duplicate, a premature terminalization is unrecoverable and drops the row out of every `status IN ('pending','dispatching','dispatched')` dedup guard. `agent_turn` tolerated the narrow window ONLY because it alone has a rollback valve (`reconcileTurnForFailedOutbox` returning `'deferred'`); no other topic has one. **What stays Operator-scoped is the RECONCILIATION, not the termination — and the guard is NOT the `array_agg(id) FILTER` at `OutboxPoller.ts:176`.** That FILTER is a redundant pre-filter saving a round trip per non-Operator row; deleting it alone leaves every test green. The real boundary is `reconcileTurnForFailedOutbox`'s own re-select, `AND topic = AGENT_TURN` at `turns.ts:58`, which returns `'unchanged'` for anything else. **Terminalizing correctly REMOVES a signal**, which is why #1378 also opened `checkFailedOutboxByTopic`'s seven-topic allowlist: an orphan raised `outbox_stale_dispatching` forever (wrong, but the only alert it had), and a watchdog-terminated row fires no BullMQ `'failed'` event, so the **Job-failure sink** never sees it either. *(coined in the cost-optimization wayfinder effort; sharpened in #719; `last_error` preservation corrected at #736; terminal arm widened, given its own 15-min window, and the alert allowlist opened at #1378 — the FILTER-as-guard claim was wrong in this entry's first #1378 draft and was corrected by the red-team pass)*
- **Drip staleness cap**: the 3-day bound owned by `DRIP_STALENESS_GRACE_DAYS` / `isDripTooStale` in `OnboardingDripWorker` — a drip whose due date passed by more than the grace window is never sent, permanently. It exists so an outage that pauses drips does not clear into a burst of late "Welcome to day 1!" emails. Sends **at** the boundary (the comparison is strictly `<`, so equality is not stale), skips past it. Enforced at **two points, and both are load-bearing**: the `OnboardingDripScheduler` producer excludes stale pairs from the candidate query, and a **fail-closed chokepoint** in `handleOnboardingDrip` re-checks before any side effect. Producer-only was the original design and was wrong — an operator re-driving a failed row, a future second producer, or a row minted just inside the boundary and stranded through a multi-day worker outage all reach the handler with the producer's check long expired; #679 reached the same conclusion for **Import consent** and for the same reason. The chokepoint runs **before** the `onboarding_drip_log` claim (a refusal must not consume the claim a legitimate re-send would need) and **completes** the row carrying `completion_reason = 'drip_too_stale'` rather than failing it — a policy refusal is the guard working, not an incident, and the marker makes a refusal separable in SQL from a genuine send. Unlike #679's guard it needs no `SELECT … FOR UPDATE`: staleness is a pure function of `subscription_activated_at` and the clock, and nothing mutates the anchor, so there is no race to serialize against. Both enforcement points leave a **durable record** since #738: the handler chokepoint completes its outbox row with `completion_reason = 'drip_too_stale'` (7-day window under ArchivalPoller's completed-row retention), and the scheduler stamps `skipped_at`/`skip_reason` on `onboarding_drip_log` (migration 104) — a table ArchivalPoller never touches, so the scheduler's record is the **permanent** answer to "which drips were dropped as too-late, and when". The stamp doubles as the candidate-query dedup, replacing the old `GRACE + 1` one-day reporting window: a too-late pair — including a backlog already past the window at deploy, which the old window skipped silently — is selected once, recorded (a guarded `ON CONFLICT … DO UPDATE` stamps a dead claim row; a sent or already-skipped row is untouched, and migration 104's CHECK makes skip-and-send unrepresentable), and excluded thereafter. Removing the outer window is re-mint-safe because archival (7 days) strictly exceeds grace (3 days): any pair archival frees re-enters the query already too late, landing in the skip branch, never the queue branch — that arithmetic is load-bearing; do not shrink outbox archival below the grace window. `skip_reason` vocabulary: `DRIP_SKIP_REASONS` in `OnboardingDripWorker.ts`, derived from `OUTBOX_COMPLETION_REASON.DRIP_TOO_STALE` so one grep finds both enforcement points. *(coined in #719; producer-only enforcement corrected at #719 step-7 review A1; observability asymmetry accepted at review A3, then closed by #738/migration 104)*
- **Job-failure sink**: `worker/job-failure-sink.ts`, attached to every BullMQ `Worker` alongside `attachEmitterErrorLogger` — on the **terminal** attempt only it raises a Sentry issue (tags `{subsystem, queue, topic}`) rather than the breadcrumb that preceded it. Its terminal test is the **`'failed'`-event** predicate `attemptsMade >= max`, deliberately NOT `isTerminalAttempt` from `src/lib/shared/outbox.ts`: that one is `attemptsMade >= max || attemptsMade + 1 >= max`, written for the **catch block** where `attemptsMade` has not yet been incremented, and using it in the event context fired one attempt early *and* again on the real last one — a duplicate issue plus a false "exhausted its retries" for a job BullMQ then retried successfully. `worker/jobs/judge/failed-hook.ts` keeps its own copy for the same reason and says "do not unify them"; treat any future shared helper here as a trap. It writes **nothing** to `job_outbox`: a raw driver message can embed contact PII, so durable per-domain error text stays the job of the six domain `'failed'` hooks — Sentry is the durable record of the *handler error* specifically, not of every failure fact. Promoting these from breadcrumbs to issues moved the message onto the one Sentry field `scrubSentryEvent` did not cover, so that scrubber now redacts `exception.values` too. *(coined in #719; terminal predicate and exception scrubbing corrected at #719 step-7 review A2/A6)*
- **Connection wedge** (the "wedge"): a postgres.js pool connection stalled server-side in `state=active, wait_event=ClientRead` — a socket-level stall waiting for client bytes that never arrive. No server-side timeout heals it, and `withTimeout` does not cancel the underlying work, so the leaked slot never returns to the pool; one wedge per cycle → full-pool starvation. *(coined in the #500 pool-wedge self-heal)*
- **Boot burst**: the ~24 background-loop first cycles + ~30 BullMQ `Worker`s + ~31 `Queue`s all initializing on roughly the same tick at worker start — the leading (still UNPROVEN) candidate for triggering the connection wedge. *(coined in the #500 pool-wedge self-heal; sharpened in the #505 root-cause investigation)*
- **Boot-readiness cure**: the #505 boot-storm hardening in `worker/background/boot-stagger.ts` — BullMQ Workers build `autorun:false`; boot awaits bounded, fail-open Redis/BullMQ readiness (`awaitQueueReadiness`); then the ~24 DB-backed loops' first cycles start on a bounded (~8s), strictly-monotonic, jittered stagger (`computeBootSchedule` + `staggerBoot`); only THEN are the deferred Workers resumed. One `AbortSignal` spans the whole sequence — shutdown aborts it FIRST, before stopping loops, so a SIGTERM mid-boot cancels any pending continuation instead of racing the teardown. Toggle `BOOT_STAGGER_ENABLED` (default ON; only the literal `"false"` disables, for the T1 repro harness baseline). Validated EMPIRICALLY (zero wedge across repeated fresh treatment boots), not a proven-mechanism fix — see ADR 0008. *(coined in the #505 boot-readiness cure)*

- **Coupled terminal transition**: multi-write terminal bookkeeping (outbox close + exception/notify rows) executed atomically inside one `sql.begin` with the `markOutboxFailed` ownership CAS run FIRST — CAS `false` means a stale attempt that must write nothing; a mid-tx crash rolls everything back and leaves the row `dispatched` for the watchdog. Owned by `withOwnedTerminalTransition` (`worker/jobs/zernio/ingest-failed-hook.ts`); the crash guard never splits a coupled tx. *(coined in the #508 reliability guards)*
- **Per-widget degradation**: the dashboard failure contract — an auxiliary query failure degrades ONLY its widget to an empty-but-valid shape via `widgetOrFallbackFor(source)` and MUST report through `reportCaughtError` (degradation is never silent); only identity anchors (business lookup, aggregate locations list + baseline anchor) stay fatal. *(coined in the #508 reliability guards)*
- **Count-and-suppress window**: the per-source emitter-error throttle (`worker/emitter-errors.ts`) — first error in each 60s window is logged + Sentry-captured, the rest are counted and surfaced as `suppressed_in_prior_window` when the next window opens; prevents reconnect-loop alert storms while keeping every listener non-fatal. *(coined in the #508 reliability guards)*
- **Bounded admin client**: `supabaseServerBounded` (10s `boundedSupabaseFetch`) for worker-side admin/storage calls that must never hang a BullMQ slot — deliberately split from the unbounded `supabaseServer` used by Auth identity mutations, where an ambiguous timeout could orphan a committed signUp/invite. *(coined in the #508 adversarial review)*
- **Send idempotency key**: the stable `Idempotency-Key` a worker hands Resend through `sendInternalEmail`, shaped `<template>:<domain identity>`. It narrows the gap every send-then-mark worker has: OutboxPoller is at-least-once, so a crash between "Resend accepted" and "local row says sent" re-sends. **Its precondition is a BYTE-STABLE body, and that is the part that is easy to get wrong.** Resend replays the original response — original message id included — only when the retry's body is identical; when the body DIFFERS it answers 409 instead, and a delivery row then carries a synthetic id. `worker/ingress/resend.ts` correlates delivered/complained/bounced ONLY on the real Resend id, so such a row silently disables hard-bounce suppression: `businesses.owner_email_bounced` is never set and the owner keeps receiving mail at a dead address. A send that mints anything per-attempt — any caller of `createApprovalLink`, which generates a fresh `randomUUID` every call — therefore must NOT carry a key. The day_7 drip and the owner nudge are exactly that case and use mark-before-send instead (`dripBodyVariesPerAttempt` names the rule in `OnboardingDripWorker`). day_1, day_30 and the three partner alerts render from stable inputs, keep the key, and lose no email. **Scope is domain, never the Outbox job row id**: an outbox-scoped key dedupes one row's retries but not a SECOND row covering the same logical send — the drip's stale-claim takeover, and the engagement poller's re-mint after a watchdog terminalizes a crashed row, both produce one. `EngagementMonitorPoller`'s cooldowns are 3/7/14 **days** (`EngagementMonitorPoller.ts:30-35`), far beyond the provider key's **24-hour** life, so a business-scoped alert key can never suppress a legitimate second alert. That 24h life also makes the key a bound on the crash-retry window, never a durable guarantee. A worker that already marks BEFORE sending needs no key and deliberately carries none. **A handler that completes its Outbox job before sending must not rethrow a send failure** — BullMQ retries the job on its own clock and re-sends; `WeeklySummaryWorker`'s `sendSummaryReportEmail` and the owner nudge both swallow and log. *(coined in #1363; the body-stability precondition, the domain-scope rule and the no-rethrow rule all came from the step-7 review wave, which disproved the first cut of each)*
- **Idempotent replay**: a send Resend refused with 409 `invalid_idempotent_request` because the same **Send idempotency key** arrived carrying a different body — only reachable after Resend accepted a first request under that key, so it is **proof the email was delivered**, not a failure. `sendInternalEmail` reports it as `{ idempotentReplay: true }` with a synthetic `idempotent-replay:<key>` message id rather than throwing, and the caller must still write every downstream fact (sent markers, delivery rows, outbox completion) exactly as after a fresh send. **It is a partial signal, not a census:** an identical-body replay never reaches 409 at all — Resend returns the original 2xx — so it produces no flag, no log line and no row, and `notification_deliveries.external_message_id LIKE 'idempotent-replay:%'` is a FLOOR on suppressed duplicates rather than a total. Because a replay's synthetic id breaks webhook correlation, the only sends allowed to produce one are those whose body is stable enough that a replay is rare. Two neighbouring Resend codes are deliberately NOT replays and still throw: `concurrent_idempotent_requests` (first request still in flight — not proof of acceptance, and swallowing it drops a real email) and `invalid_idempotency_key` (the key we built is malformed — our bug). *(coined in #1363)*
- **Deployment lane** (the "lane") — which of the three environments a running process is in, in CLAUDE.md's existing "Three lanes" sense (*preview* / *staging* / *production*). Resolved by the single authoritative owner `src/lib/config/deployment-lane.ts` from `RAILWAY_ENVIRONMENT_NAME` (the Railway-injected system variable — wins whenever present), falling back to `NODE_ENV`, then `'development'`. **A lane is not `NODE_ENV`**: staging runs with `NODE_ENV=production` and production leaves `NODE_ENV` unset, so `NODE_ENV` cannot name the lane (#610/#611). It is also **not a feature flag** — it reports where the process runs and never gates a product behaviour, which is why it lives outside `src/lib/config/flags.ts`. The separate `requiresProductionConfig()` answers "must this process satisfy production-grade config?" and is deliberately the *union* of the two signals, never their precedence. *(coined in the #610/#611 deployment-lane fix; ADR 0013)*
