## Review QR — locked 2026-08-26 (roadmap Phase 0 pull-forward, feat-qr-review-request)

- **Review QR**: the per-location printable QR code the owner downloads (PNG ~2048px) or prints (browser print view) from `/dashboard/requests/qr` (**moved from `/settings/review-qr` by #1092**; the old path redirects and is not deleted, because owners bookmark it). It encodes the **QR redirect** URL — never the Google URL itself — so the destination can be re-pointed server-side without a reprint. One identical code per location for every customer: no contact capture, no sentiment gating, no interstitial (roadmap Phase 0 lock). A location is QR-eligible iff its `google_place_id` passes `isPlaceId` (hex CIDs refused, the `buildReviewLink` precedent) and it is not archived; an ineligible location gets an explanatory card, never a QR that dead-ends. The surface is visible to every owner — deliberately NOT behind `shouldShowLocationsSettings`. Since #1092 it hangs from **Requests**, not Settings: a sidebar child on desktop and a third routed pill below the 768px breakpoint, because the sidebar is hidden there and a sidebar-only entry would be unreachable on a phone (#1089). **Requests is gated on `SOLICITATION_WATCH_ENABLED`, which is OFF in production, so with watch-mode off Review QR is promoted to a TOP-LEVEL row in both navs** — nesting it under a hidden parent would have left it with no entry point at all, contradicting "visible to every owner" in the same breath as stating it (owner decision 2026-09-03). _Avoid_: QR token (the key is the business UUID, nothing is minted), scan code, review-link QR. *(coined in feat-qr-review-request grilling, owner decisions 2026-08-26)*
- **QR redirect**: the public hop `GET /q/<businessId>` that resolves a scan server-side and 302s to `https://search.google.com/local/writereview?placeid=<validated place id>`. Resolution lives in `src/lib/locations/review-qr.ts` (`resolveQrRedirect` — pure result object, no side effects); the route orchestrates only. The gate is the named predicate `subscriptionAllowsQrRedirect` = `{active, trialing, past_due}` (invariant #11 — `past_due` stays alive so a card failure never kills a printed counter code mid-grace); `pending_payment`/`cancelled`, archived, missing rows, and non-canonical place ids all render the scanner-facing unavailable page (scanner copy, no dashboard CTA) with one reason-coded log line — never a redirect, never an error leak. Each successful redirect best-effort-records one `qr_scan_redirected` analytics event AFTER resolve; an insert failure never blocks the 302. `Cache-Control: no-store` on every response. _Avoid_: QR landing page (there is none — the hop is a straight 302), scan tracker, short link. *(coined in feat-qr-review-request grilling; gate set chosen by owner 2026-08-26)*
