# RepWorth Domain Glossary (seed) — accounts, channels & admin

_Context file of the RepWorth domain glossary — the index of contexts and the file that owns each term is [`CONTEXT-MAP.md`](../../CONTEXT-MAP.md)._

_Core context 3 of 3 — the Account/Business split, subscription access, owner notification reachability, the mobile-channel actor, and the admin business query. Core 1 is `core-platform-runtime.md`; core 2 is `core-reviews-responses.md`._

- **Account**: the billing parent (subscription, quotas, stored tier prices). **Business**: one Google Business Profile location under an account. *(draft — to be sharpened in grilling sessions)*
- **Full access**: subscription statuses (`active`, `trialing`) that `subscriptionGrantsFullAccess` treats as entitled; workers gate on it, never on a raw status literal. *(draft — to be sharpened in grilling sessions)*

- **Owner-unreachable outcome** — the notification result when an approval draft's account/location has zero verified channel enrollments at send time (`no_verified_enrollments`), recorded as `job_outbox.completion_reason='owner_unreachable'` on the completed `send_notification` row, and *current* only while that is the **latest** completed `send_notification` for the response. Distinct from **all-failed** (a delivery was attempted on an enrolled channel and every attempt failed) and **stale** (delivered but the owner hasn't acted). The draft stays `pending_approval` and is retried on the `NotificationFailoverPoller` cadence until a channel appears. *(coined in the F1 owner-unreachable escalation effort)*

- **Channel actor**: the resolved identity a mobile-channel enrollment action runs as — `{ businessId, accountId, actorUserId, surface }` (`src/app/api/_shared/channels/resolve-actor.ts`), where `surface ∈ {'admin','dashboard'}` reusing `disconnectChannel`'s existing union. It is the **only axis that varies** between the two portals' 12 enrollment routes, which is why it is the seam: `resolveAdminActor` reads `businessId` from the request **body** behind `requireAdminWithAal2`, `resolveOwnerActor` reads `locationId` from the **session** behind `requireRoleOr401` and never from the body — and that asymmetry is a security boundary, not an implementation detail, so the two resolvers must never be collapsed into one function that accepts either source. The resolver also owns each portal's **gate outcome**: admin `start` applies `subscriptionGrantsFullAccess` (via `requireFullAccess`) while admin `cancel`/`disable` deliberately apply none, and owner applies `resolveWritableAccountForLocation` on all three; the runners consume the outcome and never second-guess it (spec §4.2). `surface` is not decoration — it drives the `disconnectChannel` audit tag and the `safeInvalidateChannelCache` label, so `admin.telegram.cancel` and `dashboard.telegram.cancel` stay distinct in the audit log and the cache. _Avoid_: principal, caller identity, auth context, channel session. *(coined in the PR 2 channel-route unification; spec `docs/superpowers/specs/2026-08-15-portal-audit-remediation-design.md` §4.1)*
- **Business summary**: the per-location admin DTO (`BusinessSummary`) that combines three things a caller would otherwise assemble itself — the base row (name, category, subscription status, last sync, the all-time pending-approval and pending-reconnect counts, last activity), the **trailing-30-day** response metrics (`responseRate`, `avgResponseTimeHours`, whose window is surfaced as `responseMetricsWindowDays` so no header hardcodes `30`), and the `churnScore` from `computeChurnRiskScore`. Single owner `src/lib/admin/business-summary.ts`, one exported function — `getBusinessSummaries(sql, opts?: { limit, offset })` — serving both admin surfaces: `/admin/overview` calls it unpaginated and ranks the result into the **At-risk list**, `/admin/businesses` calls it with a page and gets metrics for that page's ids only. Having one owner is the whole point: the two pages cannot disagree on how a business is counted, scored or labelled. `total` is the unfiltered `COUNT` on the paginated path and `businesses.length` on the unpaginated one, because a caller holding every row does not need a second query to be told how many it has. _Avoid_: business row (that is the DB row, one of three inputs), businesses list (named the deleted `businesses-list-service.ts`). *(coined in PR 3 of the portal audit remediation, 2026-08-15; spec `docs/superpowers/specs/2026-08-15-portal-audit-remediation-design.md` §5.2)*
- **At-risk list**: the `/admin/overview` landing list of businesses that need a look — `OverviewData.atRisk`, built by `getAdminOverview` (`src/lib/admin/overview-service.ts`) and rendered under `At risk (N of M)` beside a `View all →` link to `/admin/businesses`, where N is `atRisk.length` and M is the unfiltered `totalBusinesses`. It is **filtered, then capped, in that order**: eligibility is `churnScore.level !== 'healthy'`, and only then are the top `OVERVIEW_AT_RISK_LIMIT` (**5**) by score kept. It is **not "top 5 by score"** — an all-healthy account yields `[]` and the client renders its `EmptyState`, never five healthy businesses under an "At risk" heading; capping first would surface healthy rows whenever the first five happen to be healthy. Ordering is the pre-existing four-level comparator, moved unchanged: churn score desc → `pendingApprovalCount` desc → name asc → id asc. §5.1's "ties break on name" is the **stability** guarantee (the same data gives the same order across refreshes), not a mandate to drop the pending tier. Ranking is computed in **TypeScript and must never become `ORDER BY … LIMIT`**: `computeChurnRiskScore` is a weighted TS composite and account age contributes, so *every* business carries a non-zero score and no cheap SQL predicate is a provable superset of "at risk" — SQL ranking means reimplementing the risk model in SQL (§5.1). `OVERVIEW_AT_RISK_LIMIT` is declared and exported by the module that applies it, `overview-service.ts`, **not** `src/app/admin/page-sizes.ts` as §5.1 asks: `src/lib/**` may not import `@/app/**` (eslint `APP_LEAF_IMPORT_BAN`), and the disagreement that placement was meant to prevent cannot occur because nothing on the app side reads the number — `page-sizes.ts` carries a pointer comment instead of a second declaration (reasoning: `docs/superpowers/plans/refactor-overview-spec-alignment-deviations.md`). **Overview still reads every business row, and that is a recorded, deliberate limitation** (§5.1), not an oversight: the named rejected alternative is a SQL-ranked attention proxy (past-due, reconnect backlog ≥ 3, oldest pending, stale activity), which is genuinely bounded but drops the churn model from the landing page and would disagree with the Health column on `/admin/businesses`. Trivial at the **Capacity target** (250 locations) — do not "fix" it. _Avoid_: top 5, the churn table (names the deleted paginated `DataTable`), risk list, watchlist. *(coined in PR 3 of the portal audit remediation, 2026-08-15; spec §5.1/§5.3)*
- **Admin app**: the admin UI as a separate deployment — its own repo under the RepWorth GitHub org, its own Vercel project on the founder's team, built by a second developer who has no read access to this repo. It holds no domain code, no `SUPABASE_SERVICE_KEY` and no database URL; it signs admins in with Supabase Auth directly (same project, anon key, MFA challenge run in-app) and reaches data only through the **Admin API** with the Supabase access token as a bearer. It links OUT to the main app for impersonation, which never moves (ADR 0024 D5). _Avoid_: admin portal (that is today's `src/app/admin`, see **Legacy admin portal**), admin frontend, admin microservice, admin service. *(coined at wayfinder charting for the admin split, 2026-09-07; ADR `docs/adr/0024-admin-app-split.md`)*
- **Admin API**: the routes under `src/app/api/admin/**` plus the services under `src/lib/admin/**`, which STAY in this repo on the main Vercel app and are the contract the **Admin app** consumes. Runs in **dual mode** during the migration — the canonical admin gates (`requireAdminWithAal2`, `requireAdminJson`, `resolveAdminActor`, the only three shapes `ci:admin-aal2` credits) accept EITHER the session cookie (same-origin, the legacy portal, CSRF-checked by `withSameOrigin`) OR a bearer (cross-origin, the Admin app, no CSRF check because a bearer carries no ambient credential). Cookie mode is removed when the last legacy page is deleted. Every request re-checks `users.role = 'admin'` and AAL2 server-side. _Avoid_: admin backend, admin service, admin-v1 (the rejected second prefix). *(coined at wayfinder charting for the admin split, 2026-09-07; ADR 0024 D2/D4)*
- **Legacy admin portal**: the pages under `src/app/admin/**` as they exist at 2026-09-07 — frozen (no new admin feature lands there) and retired page by page as the **Admin app** reaches parity, each deletion taking its path-pinning CI tests with it (`console-admin-palette`, `admin-aal2-audit` fixtures, `docs/directory/app-admin.md`). **The end state is exact** (ADR 0029 D5), and it is a FILE set, not just a page list. Five of the twenty-one pages survive — `/admin/impersonate` and `/admin/impersonate/[sessionId]/view`, `/admin/login`, `/admin/forgot-password`, `/admin/reset-password` — plus `/mfa/challenge` outside `/admin`. The surviving chrome is `src/app/admin/{layout,providers,error}.tsx`, `AdminShellFrame`, `ImpersonationBanner`, `EndImpersonationButton`, `src/lib/admin/shell-context.ts` and `src/lib/admin/impersonation/**`; **`AdminShellFrame` keeps identity, the banner and the end-session button, DROPS the sidebar, and gains one "Open Admin app" link** — a one-item sidebar was rejected because it keeps `AdminSidebar`, `nav-config`, `nav-counts-query` and their tests alive to draw a single link. `/admin/security` and `/admin/runbook` are NOT survivors: both read nothing and need no route, so both move (ADR 0027 D3), and a factor enrolled in the **Admin app** is on the same `auth.users` row, which is what keeps `/mfa/challenge` working here afterwards. Eleven sites name `/admin/overview` as a destination and all switch on the day it is deleted (ADR 0029 D2) — ten to `ADMIN_APP_URL`, and `src/app/admin/error.tsx` to `/admin/impersonate` instead, because an error boundary is a client component with no server parent to take the value from. _Avoid_: old admin, admin v1. *(coined at wayfinder charting for the admin split, 2026-09-07; ADR 0024 D6; end state ADR `docs/adr/0029-admin-link-ownership-and-legacy-shell.md` D1/D2/D3/D5)*
- **Admin transport**: the two ways a request to the **Admin API** carries its credential — `cookie` (the session cookie, same-origin, the **Legacy admin portal**, CSRF-checked by `withSameOriginUnlessBearer`) and `bearer` (a Supabase access token in `Authorization: Bearer`, cross-origin, the **Admin app**, no CSRF check because a bearer is not an ambient credential). **A bearer wins**: when the header is present the cookie is ignored entirely. **One predicate owns the choice** and both `src/proxy.ts` and the identity seam import it — two copies of that test can disagree, and a disagreement is either a bypass or a dead route. The transport is resolved BELOW the gates, by a seam that returns `{ authUserId, aal, transport }` and decides nothing; `requireRole` stays cookie-only so the owner API's auth surface does not widen. Cookie mode is removed when the last legacy page dies (ADR 0024 D4). _Avoid_: auth mode, credential type, cookie-or-token. *(coined resolving #1161; ADR `docs/adr/0025-dual-mode-admin-gate.md` D1/D2/D6/D7)*
- **Verified admin**: the `AppUser` with `role='admin'` that a canonical admin gate returns once it has proved, from EITHER **Admin transport**, that the credential is authentic, live and `aal2`. "Verified" names all three proofs, and each has one owner: authentic and `aal` come from `auth.getClaims(jwt)` (local, ES256) in bearer mode and from the cookie client's `getAuthenticatorAssuranceLevel()` in cookie mode; live comes from a `getUser` round-trip in both, which is why bearer mode is **not** cheaper than cookie mode and must not be made so — a locally-verified-only bearer keeps working for up to `JWT_EXP` (3600 s) after sign-out or revoke. `aal2` is the STRICT test (`currentLevel === 'aal2'` / `claims.aal === 'aal2'`), never the proxy's lenient `nextLevel` form, and `MFA_ENFORCEMENT_ENABLED` gates the proxy only — it never reaches the gate. Refusals reuse one vocabulary: 401 `Unauthorized` (no/bad/expired/revoked token), 403 `Forbidden` (verified but not an admin), 403 `mfa_required`, 403 `mfa_check_failed`. _Avoid_: principal (already avoided on **Channel actor**), admin session, admin caller, admin context, gated admin. *(coined resolving #1161; ADR 0025 D3/D9/D10)*
- **Admin origin allowlist**: the set of web origins allowed to call the **Admin API** cross-origin, owned in ONE place — `src/proxy.ts`, which writes every `Access-Control-*` header, short-circuits the `OPTIONS` preflight before any auth work, and puts `Vary: Origin` on every `/api/admin/**` response. It is `ADMIN_APP_ORIGINS`, a comma list of EXACT origins with one value per environment (production: the **Admin app**'s domain; staging: its staging domain), server-only and never a `NEXT_PUBLIC_*` companion. **No entry is a pattern** — an entry containing `*` throws at read — plus two rules that are not list entries: `http://localhost` and `http://127.0.0.1` on any port, inert in the production lane; and this app's own origin, implicitly allowed so the **Legacy admin portal**'s same-origin mutations (which carry an `Origin` header) keep working. An `Origin` that matches neither is refused `403 {error:'origin'}` on every method, before any Supabase work. The allowlist is a **CSRF control**: it is what replaces "no CORS exists on this app" as the reason ADR 0025 D7's bearer-wins rule is safe, because only an allowlisted origin gets a preflight that permits `Authorization`. It is a BROWSER control only — a non-browser caller with a stolen bearer is unaffected, and closing that is the **Verified admin** gate's job. _Avoid_: CORS config, allowed origins, origin whitelist, CORS policy. *(coined resolving #1162; ADR `docs/adr/0026-admin-api-cors.md` D1/D2/D4/D7)*
- **Admin API contract**: the generated, committed description of the **Admin API**'s request and response shapes that the **Admin app**'s developer codes against, because they have no read access to this repo. It is `docs/admin-api/` and it has three parts, ALL derived from code that already exists and none written twice: `admin-api.d.ts`, emitted by `tsc --emitDeclarationOnly` from the barrel `src/lib/admin/api-contract.ts` (an index of the ~40 response DTO interfaces, not an abstraction); `schemas/<route>.json` from `z.toJSONSchema()` for the 14 routes that already declare a request schema, with the other 21 recorded truthfully as having none; and `README.md`, one row per route giving path, methods, gate, request schema, response type and status codes. **`ci:admin-contract` regenerates and diffs it** — the `ci:directory-map` posture — and rides two completeness checks the diff cannot see: every `src/app/api/admin/**/route.ts` has a row, and every gate column is derived by `admin-aal2-audit.ts`'s own provenance resolver rather than a second reader of the same shape. The diff proves the artifact matches the code; it does NOT classify a change as breaking, and a human reads it in the PR. **Errors are status codes plus `{ error: string }` prose, not a code vocabulary** — 37 distinct strings live in admin routes, `errorResponse()` is used in none of them, so there is nothing to enumerate; normalizing them is a separate ticket outside the split. `src/proxy.ts` branch 4's three bodies are contract too and are listed by hand. **No versioning** (ADR 0024 D4, dual mode on the same paths). A GitHub Action on merge to `main` opens a PR carrying the same files into the Admin app repo — the #1167 export precedent with the manual step automated, which is what keeps ADR 0024 D8's single owner. _Avoid_: API spec, OpenAPI doc (the rejected vehicle), types package, SDK. *(coined resolving #1164; ADR `docs/adr/0028-admin-api-contract.md` D1/D2/D3/D4/D5)*
