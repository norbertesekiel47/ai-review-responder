## Refusal ledger — locked 2026-08-29, map #994 (schema #1001, migration 116)

Carried and **corrected** from the parked branch `feat/refusal-log`, whose
definitions predate #998 and #1003. Three of its claims are now false and are
called out below rather than quietly dropped, because a stale glossary is worse
than none.

- **Refusal**: something RepWorth **decided not to do** and recorded **when it decided** — a draft held for the owner, an auto-post revoked before it posted, an autonomy suspension, an Ask withheld at build, an Outreach withheld at send, a batch we halted, a draft a policy gate held. It is a *decision*, which is what excludes every neighbour that resembles one: an **owner act** (`owner_veto`, `owner_halt`, `owner_excluded`, `owner_withdrawn`) is the owner's decision and reporting it back as our restraint lies about who decided; a **delivery failure** (`send_failed`, `send_exhausted`) is an act that did not land; an **elapsed clock** (`batch_expired`, `send_window_elapsed`) weighed nothing; `superseded` is a replacement, `send_indeterminate` an unknown, `velocity_banked` volume shaping the next batch is expected to return. **A judge verdict is NOT a refusal**: the Judge runs on already-posted replies (`judge-store.ts`, `WHERE r.status = 'posted'`), so a verdict is a post-publication observation, and counting one would also double-count the autonomy suspension a flag triggers. **It is RECORDED, never re-derived** — the parent effort tried to project this surface over seven tables and could not order it, because two lanes carry no immutable timestamp of their own; that failure is why `refusal_events.occurred_at` exists and why it is writer-supplied. **CORRECTION to the parked text**, which said "the Refusal Log reports THAT a draft was held for the owner, never WHY": #1003 closed that. The `policy_gate_held` lane records the winning `AutoApprovalBlockReason` in `refusal_code` and the full co-occurring set in `all_refusal_codes` — server-side only, never owner-facing (ADR 0023). _Avoid_: skip, block, rejection, failure, "blocked reason". *(coined in the refusal-log grilling; scope corrected by #1003)*
- **Refusal source**: the lane a **Refusal** came from plus the **verbatim code** it carries inside that lane, so one code can mean different things in different lanes and the map is per-lane rather than global. **The term spans TWO columns, and the naming is a trap**: `refusal_events.refusal_source` holds only the LANE, and the verbatim code lives in `refusal_events.refusal_code` (with the co-occurring set in `all_refusal_codes` for one lane). A writer or support query built from this term's name alone selects half of it. **SEVEN lanes, not the parked text's six** — `policy_gate_held` joined them in #1003 and is the highest-volume of all BY DESIGN CAPACITY, though silent in production until `AUTO_APPROVAL_ENABLED` is on (see below): `held_draft`, `auto_post_revoked`, `autonomy_suspended`, `ask_withheld`, `outreach_withheld`, `batch_halted`, `policy_gate_held`. Two traps the per-lane split exists for: **`held_draft` has no code axis at all** (`flagged_responses.reason` is moderation prose that may never leave the server, and the row exists only for a `high`-severity flag, so the lane itself is the whole fact — `refusal_events` enforces this as CHECK C4, `refusal_code IS NULL` ⇔ `held_draft`); and **`admin_halt` means opposite things in two lanes** — `latchHalt` writes a batch's halt reason through to every cancelled Outreach row, so those copies map to `null` while the same code on `batch_halted` maps to `autonomy_paused`. Counting both would report one halt once at the batch and again per recipient. **`autonomy_suspended` is account-wide**: it has no location key, so its row carries `business_id IS NULL` — enforced biconditionally by CHECK C3, because joining the audit log through `businesses` multiplied one event by the location count and that is the defect the constraint exists to make unrepresentable. **ALL SEVEN LANES NOW HAVE WRITE SITES** — #1013 landed the last two, both in `worker/jobs/response-generation/persist.ts` on the single transaction that persists the draft. **`policy_gate_held` is silent whenever `AUTO_APPROVAL_ENABLED` is off**, which is production today: the flag off makes `auto_approval_disabled` a STRUCTURAL gate, so no policy row is read and the candidacy narrowing is unevaluable — a count of zero on that lane means the flag, not an absence of decisions. The ticket's and #1003's claim of a row on that path is false against the code and was deliberately not implemented. `held_draft` is unconditional and live from merge. **THIS INVALIDATES #1014's STATED PREMISE, and #1014 must not be built on it.** That ticket says "merge ordering is the gate, not a flag" and renders **Coverage start** as `accounts.created_at` on the strength of it. For `policy_gate_held` that is FALSE — merging every write site does not start the lane, the flag does — so an account created before the go-live flip accumulates real held drafts the ledger never recorded, and #1002 forbids a backfill. The tab must render `max(accounts.created_at, that lane's activation)` for this lane, or state the lane separately; it may NOT claim account-created coverage for it. Owner decision 2026-08-31: **disclose rather than repair** — #1013 ships as built and adds no coverage-start marker. _Avoid_: refusal origin, source table (the lane is named for the act, not the table), event type. *(locked in #995/#997; `policy_gate_held` added by #1003; write sites completed by #1013)*
- **Refusal category**: the owner-facing axis, **frozen at write** alongside the `vocabulary_version` that froze it. **EIGHT members, not the parked text's seven** — `owner_review_required` was coined in #998: `unsafe_content`, `watchdog_unavailable`, `below_our_bar`, `no_permission`, `wrong_moment`, `autonomy_paused`, `missing_information`, `owner_review_required`. Every source code maps to exactly one category **or to explicit `null`**, and `null` is the recorded decision "not a refusal", **never an omission** — a member with no entry is a member nobody decided about, which is why `Object.hasOwn` and not truthiness is the test, and why a `null`-mapped draft writes no row at all rather than a row with a null category. **Two owners, one fact each**: the closed set lives in a storage CHECK (migration-bearing on ADD and on nothing else — retiring softly needs no migration, renaming is forbidden, reordering is presentation), and the code→category MAP lives in TypeScript. A CHECK pinning `held_draft` to `unsafe_content` was rejected for exactly that reason: true today, but it would make a future lane re-map migration-bearing. **An unrecognised code is a fault, not a category** — the resolver throws rather than defaulting, because a default files an unmapped refusal under a plausible-looking heading and the owner cannot tell the difference. **AND THE FAULT IS NOW SIGNALLED WHEN THE LEDGER IS OFF (#1105), which is a different act from throwing.** With `REFUSAL_LEDGER_ENABLED` off, guard 4 returns before the resolver can throw (#1079), so the fault used to be invisible: `wouldRecordRefusal` is `every(mapped && non-null)`, so an unmapped member made IT false too and even the ledger-dark line stayed silent. `noteUnmappedBlockReasons` now raises its own Sentry event at level `error`, tagged `fault=unmapped_block_reason`, latched per code and bounded. It is NOT a ledger gap and must never be reported as one — an unmapped member would have thrown rather than written, so no **Refusal** row was lost. **The fault CLASS is not closed codebase-wide**: five lanes index a category map directly (`MAP[reason]` yields `undefined` rather than throwing) and remain unsignalled; different mechanism, separate ticket. _Avoid_: refusal type, refusal code (that is the **Refusal source**'s verbatim value), bucket, reason group. *(locked in #995; eighth member from #998; the unmapped-code signal from #1105)*
- **Restraint tab**: the second of the two tabs `/dashboard/analytics` WILL carry — `Metrics` and `Restraint` — routed at `/dashboard/analytics/restraint`. **Not built yet**: #1014 ships it, and the route today has no Metrics/Restraint page-level tabs — two of its cards carry per-card view tabs in the all-locations scope, which are a different LEVEL rather than a different control — so every sentence below describes the locked target rather than current behaviour. It states the window's total **Refusal** count and its breakdown by **Refusal category**, newest first within each. **Links only, no writes** — a held draft links to its review and shows no draft text, no review text and no moderation reason; `autonomy_paused` links to `/settings/auto-approval`; `no_permission` links to the contacts list; the rest carry none. It **drops the link, never the row**: the category and `occurred_at` are always true, only the link is contingent on a subject that may no longer resolve. It never selects `all_refusal_codes`, and deny-all RLS is what makes that a guarantee rather than a convention — **RLS filters rows, not columns** (ADR 0023). The empty window reads as a plain sentence, never an error or an empty grid. **CORRECTION to the parked text**, which said this surface "adds no migration": it does now — migration **116** creates `refusal_events`, and the tab reads that ledger rather than re-deriving one. Per-location scope is `account_id = $1 AND (business_id = $2 OR business_id IS NULL)`, so an account-wide suspension appears under every location once each and **once** in the account total; a per-location sum therefore legitimately exceeds the account total whenever a suspension is in the window, and the tab must state which number it shows. _Avoid_: refusals dashboard, restraint report (that is the **Spoilage report**, a different surface on `/dashboard/requests`), "what we blocked". *(locked in the refusal-log intake; migration corrected by #1001)*
- **Coverage start**: the instant from which the **Restraint tab** may claim it was watching — `accounts.created_at` in the account view, `businesses.created_at` in a location view — rendered as a stated line and never implied by an empty result. It is a CLAIM ABOUT THE LEDGER, not about the account, which is why archive and reactivate touch neither value: an archived location's Refusals survive their full 180 days (#996, `VAL-LOC-044`), so the record does not restart when the location comes back. It exists because #1002 decided there is **never a backfill**, leaving the ledger's history to begin the day it shipped; without a stated start an empty window reads as "nothing was held back" when it means "we were not recording". **It is NOT honest per-lane, and #1014 does not claim it is.** `policy_gate_held` is silent while `AUTO_APPROVAL_ENABLED` is off, so an account created before the go-live flip accumulates real held drafts the ledger never recorded. Owner decision 2026-09-01: **disclose, do not date** — the tab renders one account-wide Coverage start plus a separate line naming that lane as not yet recording, shown only while the flag is off, and adds no activation marker (#1013 declined one, and a hand-maintained date whose wrongness is undetectable is worse than a stated gap). The <=90-day period AFTER the flip, during which a selectable window can still overlap the pre-flip hole, is a declared non-goal of #1014 and needs its own ticket. A `businesses.created_at` of NULL is representable (migration 001 leaves it nullable) and the tab OMITS the line rather than naming a date it does not have. _Avoid_: watching since, start date, ledger epoch, "since we began". *(coined in #1014; the no-backfill premise from #1002; the per-lane correction from #1003 and #1013)*
- **Ledger attribution**: tagging a Refusal-ledger fault so an operator can tell it from a fault in **the decision the Refusal was recording**. Every capture carries `subsystem: 'refusal_ledger'`, `refusal_lane`, and `flag: REFUSAL_LEDGER_ENABLED` — the last because the whole point is to name the lever. Without it a ledger fault reaches Sentry as an ordinary job failure and the operator cannot know which subsystem to reach into; #1083 found five of seven lanes in exactly that state. **DO NOT CONFUSE IT WITH THE `Attribution` FAMILY** — **Attribution window** and **Attribution match** are outreach-to-review matching and share nothing with this but the word; a grep for "attribution" returns two unrelated subsystems. **TWO FAULT CLASSES, TWO OWNERS, AND THEY ARE MUTUALLY EXCLUSIVE.** The **write fault** — a migration-116 CHECK violation, or a failure materializing the row — is owned by `captureLedgerWriteFault` in `src/lib/refusals/write.ts`, private to that module, called by both write arms, covering all seven lanes. The **vocabulary fault** — `resolvePolicyGateRefusal` throwing on an unmapped or unranked block reason — is owned by the surviving `withLedgerAttribution` in `worker/jobs/response-generation/persist.ts`, which is narrowed to that one resolve and that one lane. They can never both fire for one failure, because the resolve throws BEFORE the writer is reached. **IT LIVES ON THE WRITER'S SIDE OF THE SEAM, and that is the whole lesson of #1083**: a fault in `INSERT INTO refusal_events` is a property of that statement, and `write.ts` is its only owner (#1001). While attribution was a caller's job it sat on the far side of a seam that already existed, so five lanes omitted it and nothing stopped a sixth. Reporting it in the writer adds zero interface members and zero parameters and makes the omission unspellable. **IT IS ATTRIBUTION, NEVER RECOVERY**: the same error instance is rethrown immediately, the deciding transaction still aborts, and no caller observes anything it did not before — this is the propagating side of the module's "facts propagate, observations swallow" rule, not an exception to it. The capture itself carries its own `try/catch`, because a broken reporter must never replace the writer bug it was reporting. **THE KILL SWITCH STILL CONTAINS EVERYTHING**: both write arms return before the guard and guard 4 returns before the resolve, so with `REFUSAL_LEDGER_ENABLED` off none of this code runs (#1079). **The set arm's tag is the DISTINCT sources, sorted, comma-joined** — sorted so one cohort cannot open two Sentry facets — computed in the `catch` from `inputs` and never from the rows, which may not exist when materialization is what failed. **EVERY CAPTURE ALSO CARRIES A `fault` TAG, AND WITHOUT IT THIS TERM DOES NOT DO ITS JOB**: `fault=ledger_write` on the writer, `fault=ledger_vocabulary` on the wrapper. Round 1 of #1083's review found the two BYTE-IDENTICAL in every tag on `policy_gate_held`, separated only by `extra` — and a Sentry alert rule cannot filter on `extra`, so the two classes this term exists to distinguish were indistinguishable to the one consumer that matters. It is also this module's own convention (`fault=unmapped_block_reason`), stated as a rule in `beta-launch-alerting.md`. **`extra` IS A CLOSED KEY SET ON BOTH ARMS, asserted EXACTLY rather than by presence** — the eval compares sorted key lists, because red team proved a presence-asserted payload accepts a smuggled `refusal_codes` (gate prose, unbounded, one per row) with 146/146 still green. Single-row: `{ subject_type, subject_id, account_id, business_id }`. Set arm: `{ row_count, account_id, account_count }`, `account_id` being the single distinct value or `null`; both BOUNDED, never a joined list of up to 5,000 ids and never per-row subject ids, because `ask_withheld` can propose that many in one build. **Neither arm repeats its lane into `extra` — the tag carries it, and a tag is filterable where `extra` is not.** An earlier version of this entry justified duplicating the lane by claiming a tag value truncates at 200 characters; all seven lanes sorted and joined is **108**, so that rationale was arithmetically unreachable, and three review axes caught it independently. The set arm's tenant identity is there because the writer legitimately cannot see the batch or the run and a rolled-back transaction may leave neither row — without an account an operator has "this lane failed for N rows" and nothing to join on. _Avoid_: ledger logging, refusal telemetry, error tagging, ledger blame. *(coined in #1083; the wrapper and its first two lanes from #1079)*
