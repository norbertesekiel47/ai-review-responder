## 2026-09-19 — #1102: a worktree nobody created with `pnpm worktree:new` has no `.env*.local`

- [2026-09-19] WHAT FAILED → `pnpm test` in a harness-created worktree reported
  one failure — `worker/jobs/__tests__/onboarding-drip.integration.test.ts`,
  "the live-DB eval executes against migration-head Postgres",
  `expected '' not to be ''` — beside 110 skipped suites. The tree was clean and
  the change under test touched only `src/app/(public)/`.
  WHY → `.env*.local` is gitignored, so it does not ride along with a checkout.
  `scripts/new-worktree.sh` copies it (perms preserved — `.env.staging.local` is
  0600); the harness worktree tools, `EnterWorktree` and Agent
  `isolation:'worktree'`, do not. With `TEST_DATABASE_POOL_URL` unset every
  DB-gated suite skipped, and #719's precondition test exists precisely so that
  a silent skip cannot read as a pass. The failure was the guard working.
  CORRECT APPROACH → copy them before the first gate run, exactly as the script
  does: `for f in <main-checkout>/.env*.local; do cp -p "$f" ./; done`. Then
  re-run. A DB-gated lane that skips is not evidence, whatever the exit code
  says. Do NOT read the skip as "this machine has no test DB" without checking
  `docker ps` — the container may be up and only the env file missing.

## 2026-09-19 — #1102: `git push` then `gh pr ready` seconds apart can leave a PR with NO CI run

- [2026-09-19] WHAT FAILED → After `git push` and an immediate `gh pr ready`,
  every required check on the PR read `skipping` and no run was in progress.
  Waiting did not help; the state was terminal.
  WHY → `ci.yml` declares `concurrency: { group: ci-${{ github.ref }},
  cancel-in-progress: true }`. The `synchronize` run from the push and the
  `ready_for_review` run from `gh pr ready` were created one second apart, and
  one cancelled the other. The survivor was the draft-time run, whose jobs carry
  `if: github.event.pull_request.draft == false` and therefore skip. Re-running
  it does not help: a re-run replays the ORIGINAL event payload, which still
  says `draft: true`. Skipped required checks do not block a merge, so the PR
  looks mergeable while nothing has been tested.
  CORRECT APPROACH → push FIRST, then mark ready as a separate step, and confirm
  a live run: `gh run list --branch <branch> --limit 3`. If the newest run is
  `skipped`, `gh pr close <n>` then `gh pr reopen <n>` — `reopened` is in the
  trigger list and its payload carries `draft: false`. Never read `gh pr checks`
  alone as proof CI ran; a skipped required check and a passing one both print
  a non-failing state.

## 2026-09-19 — #1329: a snapshot cannot authorize; single-owner applies to the CALCULATION, not the OBSERVATION

- [2026-09-19] WHAT FAILED → To make the release scan's cap arm exact, the first
  cut read every account's cap once per tick and served BOTH the scan's fairness
  arm and the per-account gate from that one map — arguing it guaranteed the two
  could never disagree. Adversarial review showed the cost: nothing downstream
  re-checks the cap (`resolveAccountDailySendCap` and
  `countAccountDispatchAttemptsToday` exist nowhere outside `release.ts`), so an
  owner contracting the dial mid-tick was obeyed one tick late and the cycle
  could release past the new number.
  WHY → Two consumers wanted different things from one value. The scan needs a
  SET of numbers in one statement to decide who may hold candidate slots — a
  discovery bound, safe to lag. The gate AUTHORIZES a send and needs current
  state. Collapsing them looked like de-duplication and was actually a freshness
  regression. A second review axis simultaneously asked to finish the
  de-duplication, which would have deepened it.
  CORRECT APPROACH → A single owner of the CALCULATION does not require a single
  OBSERVATION of mutable data. Keep the shared resolver, let each consumer read
  at the moment its decision binds, and state why disagreement is safe in both
  directions (a stale-high arm hands the account to a gate that refuses it; a
  stale-low arm delays it one tick). Also the review lesson: read the WHOLE
  findings table before fixing anything — two axes proposed opposite edits to
  the same line.

## 2026-09-19 — #616: asserting a class is closed is not the same as enumerating it

- [2026-09-19] WHAT FAILED → One droppable argument, `outboxAttempt`, was found
  at a FOURTH call site by red-team round 3, after rounds 1 and 2 had each fixed
  one and each declared the class closed. The round-2 commit message said "this
  is the last of the three". It was not.
  WHY → Two ordinary habits combine into a blind spot. `expect.objectContaining`
  passes whether or not a key is present, and a shared harness default of
  `attempt: undefined` makes a DROPPED forward byte-identical to a correct one.
  So each site's own test passed against its own mutant while saying nothing
  about its siblings. The root cause is the claim, not the code: completeness was
  asserted rather than enumerated, three times.
  CORRECT APPROACH → When a value is forwarded to more than one collaborator and
  its absence is legal, assert it POSITIONALLY or exactly, give each site a
  DISTINCT nonzero fixture value so a cross-wired forward fails as well as a
  dropped one, and close the class with a command whose output is the proof —
  here `grep -n outboxAttempt <file>` returning exactly four forwards. A fifth
  site then shows up in the same grep.

## 2026-09-19 — #616: `fallow` assumes 40% coverage when no coverage file is present

- [2026-09-19] WHAT FAILED → A decomposition measured at cognitive 9 /
  cyclomatic 10 still failed the complexity check, on CRAP 31.6. The same tree
  reported different numbers in the main checkout and in the sibling worktree.
  WHY → CRAP is `cyclomatic² × (1 − coverage)³ + cyclomatic`. With no
  `coverage/coverage-final.json` present, `fallow` assumes 40%, so
  10² × 0.6³ + 10 = 31.6, over the threshold. The main checkout had a stale
  coverage file and the fresh worktree had none, which is why the two disagreed.
  CORRECT APPROACH → Do not let the proof depend on a coverage file being current
  inside a parallel gate. At the 40% default, cyclomatic must reach **9 or below**
  to hold CRAP under 30 — so drive the cyclomatic number down until the check
  passes with no coverage data at all, and treat a worktree-versus-checkout
  disagreement as a stale `coverage/` file rather than a real difference.

## 2026-09-19 — #1338: `git rev-parse` echoes an option it does not know and exits 0

- [2026-09-19] WHAT FAILED → The first fix for #1338 probed
  `git rev-parse --path-format=absolute --git-common-dir` with a `|| <older git
  fallback>`. Review found it inverted the guard on git < 2.31: every checkout,
  the primary one included, was classified as a linked worktree, so the blessed
  primary-to-worktree edit direction was blocked.
  WHY → `git rev-parse` does not fail on an unrecognised option. It PRINTS the
  option and exits 0 — `git rev-parse --totally-bogus-flag` writes
  `--totally-bogus-flag` and returns 0. So `A || B` never reaches B, and the
  caller reads the flag back as part of the value.
  CORRECT APPROACH → Do not version-gate a `rev-parse` flag behind its own exit
  status. Compare `--git-dir` with `--git-common-dir` instead: both ship since
  git 2.5, both come from ONE invocation with one cwd, so they compare as
  written with no absolute/relative normalising. They are equal in the primary
  checkout and differ in a linked worktree. Test the hazard with a PATH shim
  that emulates the old binary, not by pinning a git version
  (`scripts/ci/__tests__/edit-surface-guard-worktree.test.ts`).

## 2026-09-20 — Batch A gate tooling (#1345): six lessons from fixing checks that lied

- [2026-09-20] THE LOCAL GATE RAN A DIFFERENT BASH THAN CI, so a whole class of
  defect was invisible → macOS ships bash 3.2.57; the CI runner uses bash 5.x.
  bash >= 4.3 performs backslash processing on the UNQUOTED replacement of
  `${var//pat/rep}`, so `\\` collapses to `\`. A doubled-backslash candidate
  therefore equalled its input, a dedupe guard suppressed it, and the test was
  green locally and RED in CI. Quoting the replacement is NOT the fix — bash
  3.2 then inserts the quote characters themselves. Measured for `a \ b escape`:
  `${t//"$bs"/$esc}` → 3.2 `a \\ b escape`, 5.2 `a \ b escape`;
  `${t//"$bs"/"$esc"}` → 3.2 `a "\\" b escape`, 5.2 `a \\ b escape`;
  `printf | sed 's/\\/\\\\/g'` → identical on both.
  CORRECT APPROACH → For any substitution whose REPLACEMENT contains a
  backslash, use `sed`, not bash parameter expansion. A replacement that is a
  backslash before a character the processing does not consume (`\'`, `\"`,
  `` \` ``) is version-stable and can stay. And assert the EXACT emitted list
  rather than a boolean, so a collapsed replacement reads as a missing item
  instead of a silent false.
- [2026-09-20] A RECENCY CHECK ANCHORED ON A FILE THAT IS COPIED FIRST IS
  ALWAYS TRUE → `/feature`'s ladder carry compared the parent ladder's
  `updatedAt` against `.feature/intake.json`'s mtime, but `feature-setup.sh`
  creates that file with `cp` moments earlier, so the intake is always newer
  than a ladder written in steps 0-1. EVERY legitimate carry was refused.
  CORRECT APPROACH → Anchor on the AUTHORED source (`$SRC`), never on an
  installed copy. `cp` stamps copy time; only the original carries author time.
- [2026-09-20] A FIXTURE THAT INVERTS PRODUCTION ORDERING PROVES THE OPPOSITE
  OF REALITY → the suite for the carry above backdated the intake by 60s, the
  exact inverse of what production does, so it passed against code that could
  never work. It was written that way to fix a real wall-clock flake, and the
  fix hid the bug.
  CORRECT APPROACH → When a fixture controls an ordering the production code
  depends on, model the PRODUCTION order and drive the real entry point end to
  end. Backdating is legitimate for flake control only when the order it
  imposes is the one production produces.
- [2026-09-20] A FIX NOBODY CAN FAIL IS NOT YET A FIX → reverting the whole
  watcher-scoping change (`mutation-runner.mjs`) left the suite 248/248 GREEN,
  because both new tests called the helper directly with an injected lookup and
  nothing pinned the PRODUCTION call site.
  CORRECT APPROACH → Before claiming a fix is covered, REVERT it and watch the
  suite go red. Pin at the wiring point, not only at the helper. Probe both
  directions when narrowing a gate — over-narrowing turns a false RED into a
  false GREEN, which is worse.
- [2026-09-20] A PROCESS SCAN CLAIMING WORKTREE SCOPE WAS MACHINE-GLOBAL →
  `validateOperatorAdmission` matched `WATCHER_PATTERNS` against every process
  on the machine while its docstring said "serving or watching THIS worktree".
  An ORPHANED `next-server` whose worktree had been deleted that morning
  blocked an unrelated gate row. `vitest --watch` matches too, so a watch-mode
  run fails itself. Introduced by `3c9620440`, never passed on a machine with a
  dev server.
  CORRECT APPROACH → Scope by reading each match's process cwd
  (`lsof -a -p <pid> -d cwd -Fn`) and FAIL CLOSED when it cannot be read: a
  safety gate must never treat "unknown" as "safe". In fixture mode, inject the
  cwd lookup on the same ternary that neutralises `selfAncestry` — otherwise a
  hermetic test silently shells out to real `lsof`.
- [2026-09-20] ONE FUSED `OR` MESSAGE MAKES NEIGHBOURING ASSERTIONS VACUOUS →
  `cmdRun` rejected eight conditions with a single string naming all of them,
  so the two tests asserting "this specific bad input is refused" passed on any
  machine with a watcher running: they were observing a rejection that was
  happening for an unrelated reason.
  CORRECT APPROACH → A refusal path may keep one exit code, but the MESSAGE
  must name the condition that fired. Otherwise a test cannot tell which
  precondition it actually exercised.
- [2026-09-20] A FIX WRITTEN UNDER REVIEW PRESSURE GETS LESS SCRUTINY THAN THE
  CODE IT CORRECTS → on #1359 three red-team rounds each found fault with the
  PREVIOUS round's fixes: round 1's triage created two P0s, and round 2's fix
  for one of them closed only half the defect while the test cited as proof
  never reached the branch it claimed to pin. Every time, the suite was green.
  The original code had TDD, a plan gate and three review axes; the fixes had
  none of that until the next round caught them.
  CORRECT APPROACH → Treat a review fix as new code, not as a patch: it needs a
  test that fails without it, and the test must be shown to exercise the branch
  it names. Prefer corrections that change the SHAPE over ones that add a
  condition — computing a value once instead of aligning two predicates, or
  keying a UI claim on the server fact it asserts instead of on an incidentally
  empty list. A third filter clause is a defect waiting for its fourth case.
- [2026-09-20] A MUTATION CAN KILL A TEST FOR THE WRONG REASON, WHICH LOOKS
  EXACTLY LIKE COVERAGE → the RT2-2 regression test was verified by re-applying
  the bug and watching it fail (2 failed / 58 passed). It failed because the
  mutation keyed on `posting.blocked`, which the fixture happened to set — the
  test never reached the `tone === 'blocked'` branch it claimed to pin, because
  its fixture had `threshold: null` and no overrides.
  CORRECT APPROACH → When a test claims to cover a branch, PROVE it reaches
  that branch rather than inferring it from a passing mutation. A probe writing
  the live value to a scratch file and a `sort | uniq -c` settles it in two
  minutes (here: `blocked` ×2, `off`, `suspended`). A mutation kill is evidence
  the test is sensitive to SOMETHING, not evidence of what.
- [2026-09-20] A HUNG SUBAGENT IS INDISTINGUISHABLE FROM A THOROUGH ONE → a
  verification subagent sat for 4.5 hours after reporting 63/63, having written
  165 bytes. No error, no notification. It was killed and the question it was
  asked — a measurement, not a judgement — took two minutes inline.
  CORRECT APPROACH → `ls -la` the task output file before waiting on a long
  agent; a static size with an old mtime is hung, not thinking. And do not
  delegate a measurement: delegation is for questions needing judgement. The
  review axes earned their cost because their findings were judgements the
  orchestrator could not reach alone.
- [2026-09-20] AN INTAKE THAT TOUCHES PRODUCTION CODE UNDER-DECLARES ITS
  WORKFLOW ARTIFACTS → #1359 spent five surface amendments, four of them on

- [2026-09-20] "TOPIC X ALREADY DOES THIS, SO IT IS SAFE" IS NOT A SAFETY
  ARGUMENT → #1378 widened the outbox Watchdog's terminal arm from `agent_turn`
  to every topic and proposed keeping `agent_turn`'s 2-minute window, on the
  stated grounds that `agent_turn` had run it safely for months. It had — but
  only because it alone has a rollback valve: `reconcileTurnForFailedOutbox`
  returns `'deferred'` and rolls a wrongly-terminalized row back to
  `dispatched`. The other ~30 topics have none. `dispatchBatch` walks topic
  groups SERIALLY with `markDispatched` per group, so the claim→dispatched gap
  reaches ~6 min while the 60 s overlap guard lets a superseding cycle's
  watchdog run; at 2 minutes the widened arm terminalizes live work, and the
  row then drops out of every `status IN ('pending','dispatching','dispatched')`
  dedup guard — for `publish_response`, a reply posted to Google twice. Two
  review axes found it independently, after the owner had already signed the
  2-minute window off on the incomplete argument.
  CORRECT APPROACH → When copying a predicate from one caller to many, name the
  property that made it safe for the original, then prove the new callers have
  it. A window is only safe against the WORST-CASE duration of the work it
  judges. Where the two risks are asymmetric — a premature retry costs an
  idempotent duplicate, a premature terminalization is unrecoverable — give the
  terminal arm the wider window instead of sharing one constant.

- [2026-09-21] A PINNED-HASH FIXTURE MAKES ANY EDIT TO THE PINNED FILE

## 2026-09-21 — `/feature-swarm` (#1415, #1417): four lessons about running a swarm from a worktree

- [2026-09-21] WHAT FAILED → Every `/feature-swarm` lead was blocked on its FIRST

## 2026-09-21 — #1415: gitleaks 8.30.1, measured — an empty report is not a pass

- [2026-09-21] WHAT FAILED → The first cut of `ci:secret-scan` read `[]` on
  stdout as "clean". A range containing a real private key passed green.
  WHY → gitleaks 8.30.1 exits **0** with `[]` on stdout whenever its own
  `git log` writes ANYTHING to stderr — an uninstalled `.gitattributes` textconv
  driver, a partial clone that cannot fetch a blob, a `warning:` from a damaged
  commit-graph. It prints `ERR error="stderr is not empty"` and
  `INF 0 commits scanned.` and still exits 0, which is byte-identical in shape to
  a real, valid, empty range. The same family covers an unknown base ref:
  `--log-opts="<missing-ref>..HEAD"` also prints ERR and exits 0.
  CORRECT APPROACH → A pass is a conjunction of four conditions, never a read of
  stdout alone: exit 0, `[]` on stdout, gitleaks' own `N commits scanned` count
  at or above a computed minimum, and no `ERR`/`FTL`/`fatal:` marker on stderr.
  Resolve the base ref yourself with `git rev-parse --verify` BEFORE invoking
  gitleaks. "A gate that cannot see must never pass."
- [2026-09-21] WHAT FAILED → An exact count match against `git rev-list --count`
  was wrong, and so was an equality against "commits that add a line" — the
  second one false-failed honest pushes twice.
  WHY → Measured with a `git` shim on PATH: gitleaks counts a commit when
  `git log -p -U0` yields a hunk on a file that SURVIVES the commit — added OR
  removed lines. It does not count empty commits, whole-file deletions,
  100%-similarity renames, mode-only changes or binary-only changes, all of
  which `rev-list --count` does count. In the other direction, a commit that only
  REMOVES lines from a surviving file (a revert, a dead-code deletion) IS counted
  by gitleaks and is NOT counted by an added-line counter — and that shape is
  ordinary in an unsquashed `origin/main..HEAD`.
  CORRECT APPROACH → A **lower bound**, not an equality: fail only when gitleaks
  scanned FEWER commits than the number of commits that add a text line over the
  SAME `--diff-merges` flag. Equal or greater passes. A sufficient count proves
  the scan did not stop short; it does NOT prove every byte was read — a file
  `.gitattributes` marks `-diff` or `binary` is invisible to gitleaks and to
  `--numstat` alike, so the minimum does not rise either. That is a documented
  limit, not a closed hole.
- [2026-09-21] WHAT FAILED → A secret pasted into a merge RESOLUTION — present in
  neither parent — was invisible to the scan.
  WHY → `git log -p` shows no diff for a merge commit at all.
  CORRECT APPROACH → `--diff-merges=remerge` is the only variant that works, and
  it was chosen by measurement against a scratch repo, not by reading docs: `-m`
  finds the key but double-reports it (once per parent), `--cc` and `-c` find
  nothing, `--first-parent -m` finds it but drops every side-branch commit from
  the scan. It needs git ≥ 2.35; an older git fails both the count read and
  gitleaks' log, which fails closed rather than silently skipping.
- [2026-09-21] WHAT FAILED → A `[[allowlists]]` path block in `.gitleaks.toml`
  silently disabled ~200 rules, `private-key` included, in six live test suites —
  and nothing reported it.
  WHY → An allowlist with no `targetRules` applies to EVERY rule, not just the
  one whose false positives motivated it.
  CORRECT APPROACH → Scope every allowlist block with
  `targetRules = ["<rule-id>"]`. Verify by planting a runtime-constructed fake
  key in an allowlisted path and checking the scan still reports it.
- [2026-09-21] WHAT FAILED → The secret-scan branch **failed its own scan**. The
  rotation-drill paragraph in `docs/runbooks/secrets-rotation-api-keys.md` wrote a
  literal PEM opening/closing marker pair, and gitleaks reported `private-key` in
  the commit that added it.
  WHY → The `private-key` rule matches from an opening marker to the next closing
  marker across ordinary PROSE, roughly 64+ characters apart — it does not
  require anything key-shaped in between. And because the scan reads COMMITS, a
  later commit cannot clear the finding.
  CORRECT APPROACH → A doc that explains the shape must DESCRIBE the markers,
  never spell them — say how to construct the value at run time instead. When a
  finding is already committed on an unpushed branch, undo the commit
  (`git reset --soft`) and rewrite it so the pair never enters branch history; a
  follow-up fix commit does not help. Never write a literal marker pair, or any
  key-shaped value, into a doc that a commit-reading scan will see.
