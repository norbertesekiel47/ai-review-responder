## 2026-09-19 — #1102: a worktree nobody created with `pnpm worktree:new` has no `.env*.local`

- [2026-09-19] WHAT FAILED → `pnpm test` in a harness-created worktree reported
  one failure — `worker/jobs/__tests__/onboarding-drip.integration.test.ts`,
  "the live-DB eval executes against migration-head Postgres",
  `expected '' not to be ''` — beside 110 skipped suites. The tree was clean and
  the change under test touched only `src/app/(public)/`.
  WHY → `.env*.local` is gitignored, so it does not ride along with a checkout.
  `scripts/new-worktree.sh` copies it (perms preserved — `.env.staging.local` is
  0600); the harness worktree tools, `EnterWorktree` and Agent
  `isolation:'worktree'`, do not. With `TEST_DATABASE_POOL_URL` unset every
  DB-gated suite skipped, and #719's precondition test exists precisely so that
  a silent skip cannot read as a pass. The failure was the guard working.
  CORRECT APPROACH → copy them before the first gate run, exactly as the script
  does: `for f in <main-checkout>/.env*.local; do cp -p "$f" ./; done`. Then
  re-run. A DB-gated lane that skips is not evidence, whatever the exit code
  says. Do NOT read the skip as "this machine has no test DB" without checking
  `docker ps` — the container may be up and only the env file missing.

## 2026-09-19 — #1102: `git push` then `gh pr ready` seconds apart can leave a PR with NO CI run

- [2026-09-19] WHAT FAILED → After `git push` and an immediate `gh pr ready`,
  every required check on the PR read `skipping` and no run was in progress.
  Waiting did not help; the state was terminal.
  WHY → `ci.yml` declares `concurrency: { group: ci-${{ github.ref }},
  cancel-in-progress: true }`. The `synchronize` run from the push and the
  `ready_for_review` run from `gh pr ready` were created one second apart, and
  one cancelled the other. The survivor was the draft-time run, whose jobs carry
  `if: github.event.pull_request.draft == false` and therefore skip. Re-running
  it does not help: a re-run replays the ORIGINAL event payload, which still
  says `draft: true`. Skipped required checks do not block a merge, so the PR
  looks mergeable while nothing has been tested.
  CORRECT APPROACH → push FIRST, then mark ready as a separate step, and confirm
  a live run: `gh run list --branch <branch> --limit 3`. If the newest run is
  `skipped`, `gh pr close <n>` then `gh pr reopen <n>` — `reopened` is in the
  trigger list and its payload carries `draft: false`. Never read `gh pr checks`
  alone as proof CI ran; a skipped required check and a passing one both print
  a non-failing state.

## 2026-09-19 — #1329: "unreachable today" in a deferred review finding is a claim with a shelf life

- [2026-09-19] WHAT FAILED → #900's round 2 deferred the sub-default send-cap
  gap on the ground that it was unreachable: "no TypeScript writes
  `daily_send_cap`". At HEAD that was false. `upsertSolicitationAccountDefault`
  (`src/lib/auto-approval/solicitation-settings.ts`) writes it through
  `PATCH /api/settings/auto-approval`, `DailySendCapSchema` admits 1..50, and
  **lowering** the dial is an exposure *contraction* that passes no readiness
  gate — so only the autonomy flags stood between the gap and production.
  WHY → The premise was true when written and nothing re-checked it. The
  reachability argument named a code fact ("nothing writes X"), which any later
  feature can invalidate silently, instead of a mechanism that would notice.
  CORRECT APPROACH → When deferring a finding as unreachable, say WHAT WOULD
  MAKE IT REACHABLE and give that a guard, or re-derive the premise at the next
  touch. Discovered by building the tripwire meant to guard the premise: the
  tripwire fired on the settings lane immediately. A check that fails the moment
  you write it has already paid for itself.

## 2026-09-19 — #1329: a snapshot cannot authorize; single-owner applies to the CALCULATION, not the OBSERVATION

- [2026-09-19] WHAT FAILED → To make the release scan's cap arm exact, the first
  cut read every account's cap once per tick and served BOTH the scan's fairness
  arm and the per-account gate from that one map — arguing it guaranteed the two
  could never disagree. Adversarial review showed the cost: nothing downstream
  re-checks the cap (`resolveAccountDailySendCap` and
  `countAccountDispatchAttemptsToday` exist nowhere outside `release.ts`), so an
  owner contracting the dial mid-tick was obeyed one tick late and the cycle
  could release past the new number.
  WHY → Two consumers wanted different things from one value. The scan needs a
  SET of numbers in one statement to decide who may hold candidate slots — a
  discovery bound, safe to lag. The gate AUTHORIZES a send and needs current
  state. Collapsing them looked like de-duplication and was actually a freshness
  regression. A second review axis simultaneously asked to finish the
  de-duplication, which would have deepened it.
  CORRECT APPROACH → A single owner of the CALCULATION does not require a single
  OBSERVATION of mutable data. Keep the shared resolver, let each consumer read
  at the moment its decision binds, and state why disagreement is safe in both
  directions (a stale-high arm hands the account to a gate that refuses it; a
  stale-low arm delays it one tick). Also the review lesson: read the WHOLE
  findings table before fixing anything — two axes proposed opposite edits to
  the same line.

## 2026-09-19 — #1329: a test whose expectation derives from the code under test cannot fail

- [2026-09-19] WHAT FAILED → Two tests passed while asserting nothing. (a) A
  "lockstep pin" checked `FULL_ACCESS_SUBSCRIPTION_STATUSES` against
  `Object.values(SubscriptionStatus).filter(subscriptionGrantsFullAccess)` — but
  the predicate is now IMPLEMENTED over that array, so deleting `TRIALING` moved
  both sides and the pin stayed green. (b) A cap-gate case expected
  `released: 2` with the default `perTickBudget`, which is also 2, so the BUDGET
  satisfied the assertion and the gate could be deleted.
  WHY → Both derived the expected value from something the mutation also changes.
  Red-team mutation testing found each; neither was visible by reading.
  CORRECT APPROACH → Pin against an INDEPENDENT oracle — literals for a
  membership claim, and a fixture where the subject is the only thing that can
  produce the number. Then prove it: apply the mutant and watch the named case
  fail. On this branch five mutants were re-run after fixing, and two of them
  had survived the first attempt.

## 2026-09-19 — #1329: `red-team-status.mjs` binds its evidence to a TREE, so everything else commits first

- [2026-09-19] WHAT FAILED → After the final red-team round, appending a summary
  to the run's own triage record broke the `reviewed` transition: "the tree moved
  since <sha> outside this run's own two artifacts".
  WHY → The checker runs `git diff --quiet <sidecar head_sha> HEAD -- .` with
  only `findings.md` and `findings.json` excluded. ANY other change — a new file
  included — invalidates the binding, because the pass reviewed a specific tree.
  Round 2's fixes also move HEAD past the pass that reviewed them, which is why
  a third round needs an owner grant recorded in the sidecar BEFORE it opens
  (the runner's comment: otherwise the only ways out are leaving a known defect
  unfixed or hand-editing `head_sha`, "an evidence file rewriting its own
  provenance").
  CORRECT APPROACH → Commit every artifact except the sidecar before the last
  round opens. Anything learned afterwards goes in `findings.md`, the one file
  the checker permits to change, or waits for the post-merge sweep. A grant entry
  needs `date` and `finding_ids` or the schema check rejects it.

## 2026-09-19 — #616: asserting a class is closed is not the same as enumerating it

- [2026-09-19] WHAT FAILED → One droppable argument, `outboxAttempt`, was found
  at a FOURTH call site by red-team round 3, after rounds 1 and 2 had each fixed
  one and each declared the class closed. The round-2 commit message said "this
  is the last of the three". It was not.
  WHY → Two ordinary habits combine into a blind spot. `expect.objectContaining`
  passes whether or not a key is present, and a shared harness default of
  `attempt: undefined` makes a DROPPED forward byte-identical to a correct one.
  So each site's own test passed against its own mutant while saying nothing
  about its siblings. The root cause is the claim, not the code: completeness was
  asserted rather than enumerated, three times.
  CORRECT APPROACH → When a value is forwarded to more than one collaborator and
  its absence is legal, assert it POSITIONALLY or exactly, give each site a
  DISTINCT nonzero fixture value so a cross-wired forward fails as well as a
  dropped one, and close the class with a command whose output is the proof —
  here `grep -n outboxAttempt <file>` returning exactly four forwards. A fifth
  site then shows up in the same grep.

## 2026-09-19 — #616: `fallow` assumes 40% coverage when no coverage file is present

- [2026-09-19] WHAT FAILED → A decomposition measured at cognitive 9 /
  cyclomatic 10 still failed the complexity check, on CRAP 31.6. The same tree
  reported different numbers in the main checkout and in the sibling worktree.
  WHY → CRAP is `cyclomatic² × (1 − coverage)³ + cyclomatic`. With no
  `coverage/coverage-final.json` present, `fallow` assumes 40%, so
  10² × 0.6³ + 10 = 31.6, over the threshold. The main checkout had a stale
  coverage file and the fresh worktree had none, which is why the two disagreed.
  CORRECT APPROACH → Do not let the proof depend on a coverage file being current
  inside a parallel gate. At the 40% default, cyclomatic must reach **9 or below**
  to hold CRAP under 30 — so drive the cyclomatic number down until the check
  passes with no coverage data at all, and treat a worktree-versus-checkout
  disagreement as a stale `coverage/` file rather than a real difference.

## 2026-09-19 — #616: the red-team round cap has a case with no exit, and `CLEAR` can be unreachable

- [2026-09-19] WHAT FAILED → A round-3 finding was fixed correctly, and the fix
  moved the tree past the sidecar's `head_sha`. There was no round 4 to measure
  it, so `red-team-status.mjs` stayed red and the `reviewed` transition could not
  run. Separately, the same sidecar could not reach `CLEAR` at all.
  WHY → Two independent limits. (1) `cmdRoundStart` caps rounds at 3 outside the
  Run C grant, and the checker re-checks the same condition — the right stop
  against a looping agent, but it leaves the round-2 staleness argument
  unanswered one round later. Generalising the rule does NOT work: raising the
  cap was tried on this branch and reverted, because `RUN_C_FOURTH_TEXT` contains
  the literal phrase "approve the scoped fourth round", so a prose match on
  "fourth round" matches a TAMPERED Run C admission and twelve tampering checks
  turn red. (2) `recomputeStatus` ranks `INCOMPLETE_ORACLE` above `OPEN_P1`, and
  an `oracle`-class inconclusive row is only resolved by "a later valid
  mutation" — which a type-only annotation can never produce, since its only
  oracle is `tsc`.
  CORRECT APPROACH → Do not hand-edit `head_sha`; `red-team/SKILL.md` names that
  as an evidence file rewriting its own provenance. Land the fix, record the
  owner authorization in the sidecar's `authorizations` array with `date` and
  `finding_ids`, set the finding `accepted-risk` with the file:line of its fix so
  a reviewer can check the diff, and leave the residual errors visible rather
  than edited away. Structural fixes are filed as #1342 and #1343 — until they
  land, a branch that adds a type-only annotation cannot pass step 7.5.
## 2026-09-19 — #1338: `git rev-parse` echoes an option it does not know and exits 0

- [2026-09-19] WHAT FAILED → The first fix for #1338 probed
  `git rev-parse --path-format=absolute --git-common-dir` with a `|| <older git
  fallback>`. Review found it inverted the guard on git < 2.31: every checkout,
  the primary one included, was classified as a linked worktree, so the blessed
  primary-to-worktree edit direction was blocked.
  WHY → `git rev-parse` does not fail on an unrecognised option. It PRINTS the
  option and exits 0 — `git rev-parse --totally-bogus-flag` writes
  `--totally-bogus-flag` and returns 0. So `A || B` never reaches B, and the
  caller reads the flag back as part of the value.
  CORRECT APPROACH → Do not version-gate a `rev-parse` flag behind its own exit
  status. Compare `--git-dir` with `--git-common-dir` instead: both ship since
  git 2.5, both come from ONE invocation with one cwd, so they compare as
  written with no absolute/relative normalising. They are equal in the primary
  checkout and differ in a linked worktree. Test the hazard with a PATH shim
  that emulates the old binary, not by pinning a git version
  (`scripts/ci/__tests__/edit-surface-guard-worktree.test.ts`).

## 2026-09-19 — #1338: the worktree edit guard matched a path shape, not a worktree

- [2026-09-19] WHAT FAILED → Both edit-surface guards blocked a cross-checkout
  edit only when the session root matched `*-worktrees/*`,
  `*/.claude/worktrees/*` or `*/.worktrees/*`. An Orca workspace at
  `~/orca/workspaces/<repo>/<slug>` is a real linked worktree and matched none,

  before and after: exit 0 before, exit 2 now.
  WHY → The three patterns are the layouts `scripts/new-worktree.sh` and the

  CORRECT APPROACH → Ask git what a directory IS. The Codex copy also gained

  `pnpm worktree:new` gets its `.env.local` from `.worktreeinclude` and its
  dependencies from `orca.yaml`'s setup script — NOT from
  `worktree.sharedDirectories`, which shares one `node_modules` by symlink and
  would make a lockfile change on one branch reach every other worktree.
